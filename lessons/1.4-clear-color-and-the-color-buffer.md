## Concept: the color buffer, and why a frame starts by erasing

The **color buffer** (a.k.a. the back buffer) is just a rectangle of memory on the GPU — one RGBA value per pixel, `1280 × 720` of them for your window. "Rendering a frame" means writing colors into that rectangle. When the frame is done, `SwapBuffers` (which the base `Run()` loop calls for you after `OnRenderFrame` returns) hands that rectangle to the monitor and gives you the *other* one to draw the next frame into. Two buffers, ping-ponging — that's the double buffering from 1.1.

Here's the thing that trips people up: **the GPU never erases that buffer for you.** When you get the back buffer at the start of a frame, it still holds whatever was in it *two frames ago* (because of the ping-pong). Draw a moving ship without erasing first and you get a smear — every past position still sitting there. Draw nothing, as you've been doing, and you're staring at uninitialized memory. So every frame begins by wiping the slate: **clear the color buffer to a known color, then draw on top of it.** That's not a game-engine convention, it's the base rule of immediate-mode-style rendering — the frame is redrawn from scratch, every time, and step one is erase.

Now the OpenGL-specific twist, and it's the real lesson: clearing is **two calls that do different kinds of thing**, and telling them apart is how you start to understand GL as a state machine.

- **`GL.ClearColor(r, g, b, a)` sets state.** It tells the driver "*from now on*, the clear color is this." It doesn't touch a single pixel. It's a value you park in the context — like setting a default — and it persists until you change it. You set it **once**.
- **`GL.Clear(mask)` issues a command.** It says "*right now*, fill the buffer(s) named by `mask` with their configured clear values." *This* is the call that writes 921,600 pixels. You issue it **every frame**, at the top, before you draw anything.

That split — sticky state you configure once vs. commands you issue per frame — is the shape of nearly every OpenGL call you'll write for the next 100 lessons. `ClearColor`/`Clear` is the gentlest possible first example of it. (Color values here are **normalized floats**, `0.0`–`1.0`, not `0`–`255` bytes — OpenGL speaks in normalized channels almost everywhere; get used to it now.)

One honest aside on *why clear is also cheap*: telling the GPU "the whole buffer is now this constant" lets it throw away the old contents wholesale — on tiled/mobile GPUs a clear is genuinely faster than *not* clearing, because it skips loading the previous frame back in. So the erase you need for correctness is also the fast path. You'll rarely have a reason to skip it.

## Step 1 — set the clear color once, in `OnLoad`

`ClearColor` is state, so it belongs somewhere that runs **once**, not per frame. `GameWindow` gives you exactly that hook: `OnLoad`, called a single time after the GL context is live and before the first frame. Add this override to **`Firmament.Core/FirmamentWindow.cs`**:

```csharp
protected override void OnLoad()
{
	base.OnLoad();

	GL.ClearColor(0.2f, 0.3f, 0.3f, 1.0f);
}
```

And add the `GL` namespace to the usings at the top of the file:

```csharp
using OpenTK.Graphics.OpenGL4;
```

## Step 2 — clear the buffer every render frame

`Clear` is a per-frame command, so it goes at the **top** of `OnRenderFrame`, right after the base call and before anything else. In your committed file, drop it in immediately after `base.OnRenderFrame(args);`:

```csharp
protected override void OnRenderFrame(FrameEventArgs args)
{
	base.OnRenderFrame(args);

	GL.Clear(ClearBufferMask.ColorBufferBit);

	secondsSinceLastReport += args.Time;
	rendersSinceLastReport++;

	// ... your existing peak / report / reset logic, unchanged ...
}
```

Your timing block is untouched — the only new line is `GL.Clear(...)`. The clear happens, *then* you do your bookkeeping; the order between them doesn't matter here because the bookkeeping issues no GL, but keeping the clear at the very top is the habit you want: **erase first, draw second, forever.**

Every piece, justified:

| Piece | Why |
|---|---|
| `using OpenTK.Graphics.OpenGL4` | This is the GL 4.x binding — the modern core-profile API. OpenTK also ships `OpenTK.Graphics.OpenGL` (legacy) and `...ES` (embedded); those are the wrong `GL`. You asked for a 4.6 Core context in `Program.cs`, so `OpenGL4` is the matching binding. |
| `ClearColor` in `OnLoad`, not `OnRenderFrame` | It's sticky state. Setting it every frame would be a harmless waste — you'd re-park the same value 5,000 times a second. Set it once, where "once" lives. |
| `OnLoad` at all (vs. the constructor) | You can't call `GL.*` until the context exists and is current on this thread. `OnLoad` is the first moment that's guaranteed true; the constructor runs too early. |
| `base.OnLoad()` first | Same rule as the frame callbacks — `GameWindow` raises its `Load` event from the base method. Call it, then do your work. |
| `0.2f, 0.3f, 0.3f, 1.0f` | A deliberately **obvious, not-black** dark teal, so the checkpoint is unambiguous: black could be mistaken for the old uninitialized garbage, but nobody's screen defaults to teal. (It's also the classic LearnOpenGL clear color, the reference the README points you at.) The values are normalized `0–1` floats: ~20% red, ~30% green, ~30% blue. Alpha `1.0` = fully opaque; the default framebuffer ignores window alpha, but `1.0` is the honest value and matters the day you clear a render-to-texture target in Part 7. |
| `GL.Clear` in `OnRenderFrame` | It's a per-frame command that actually writes the pixels. Miss it and you're back to garbage. |
| `ClearBufferMask.ColorBufferBit` | Names *which* buffers to wipe. You only have a color buffer worth clearing today, so just that bit. There's also a depth buffer (`DepthBufferBit`) and stencil buffer (`StencilBufferBit`) — you'll `OR` those in the day you turn on depth testing (that's **8.2**, in 3D). Not now; clearing buffers you aren't using is wasted work. |

`Program.cs` needs **no changes**. And note there's still no `SwapBuffers()` call anywhere in your code — the base `Run()` loop presents the buffer for you after `OnRenderFrame` returns, exactly as it has since 1.1.

## 🐛 Common failure modes

1. **Still garbage / undefined contents (no color change).** Your `GL.Clear` isn't running. Either it's in the wrong method (it must be in `OnRenderFrame`, not `OnLoad`), or `OnRenderFrame` returns early before reaching it — make sure `GL.Clear` sits **above** the `if (secondsSinceLastReport < ReportIntervalSeconds) return;` guard, right after `base.OnRenderFrame(args)`.
2. **`AccessViolationException` / crash on the first GL call.** You called `GL.ClearColor` too early — from the constructor or before `base.OnLoad()` — so there was no current GL context yet. Move it into `OnLoad`, after the base call.
3. **Window is black, not teal.** Two candidates: you set the clear color to black by accident, or (subtler) you called `GL.Clear` but never `GL.ClearColor`, so it's clearing to the *default* clear color, which is `(0, 0, 0, 0)` — black. Confirm the `OnLoad` override is actually being called (a signature typo makes it a new method the base loop never invokes, same trap as 1.2 failure #1).
4. **`GL` doesn't resolve / red squiggle.** Missing or wrong `using`. It must be `using OpenTK.Graphics.OpenGL4;` — not `OpenTK.Graphics.OpenGL` (legacy) and not `...ES`. If you picked the wrong one, `ClearBufferMask` or the `GL` overloads won't match.
5. **Color looks washed out / too bright / wrong hue.** You passed `0–255` byte values as floats — e.g. `GL.ClearColor(51f, 76f, 76f, 255f)`. Anything above `1.0` clamps to full intensity, so you get near-white. These are **normalized** channels: divide by 255, or just pick floats directly.

## 🔧 Exercises

1. **Pick your own clear color.** Change the three floats and re-run. Try pure red `(1f, 0f, 0f, 1f)`, then a color you'd actually want as a game background. Confirms you understand the channels are normalized and that `ClearColor` is the knob.
2. **Animate it — badly, on purpose.** In `OnRenderFrame`, *before* `GL.Clear`, call `GL.ClearColor` with a value that changes each frame (e.g. cycle green with a field you bump by `args.Time`). Watch it pulse. This works, but you're now setting state every frame — note that it *feels* wrong even though it renders fine. **1.5** is exactly this, done deliberately (animating the clear color as proof-of-life), so don't polish it here; just feel the difference between "set once" and "set per frame."
3. **Delete the `GL.Clear` line (keep `ClearColor`).** Run it. The window goes back to garbage/stale contents even though the clear *color* is set — driving home that `ClearColor` writes nothing and `Clear` is the call that touches pixels. Put it back.
4. **Add a bit you don't own yet.** Change the mask to `ClearBufferMask.ColorBufferBit | ClearBufferMask.DepthBufferBit` and run. It works and looks identical — you have no depth buffer to see, so clearing it is invisible (and wasted) today. This is a preview of the two-line clear you'll write in **8.2**; revert to just `ColorBufferBit` for now.
