# Lesson 1.5 — Pivot to DirectX 11 (Silk.NET)

> Part 1 — A Window and a Heartbeat
> *Swap the OpenTK/OpenGL foundation for a Direct3D 11 device + swap chain, keep the exact same game loop (animating the clear color proves it's alive)*

**Where you already are:** your committed `FirmamentWindow` is an OpenTK `GameWindow` subclass that runs an uncapped loop, splits `OnUpdateFrame`/`OnRenderFrame`, tracks a peak frame time, and writes an `FPS | ms avg | ms peak | updates` line to the title bar once a second. That loop is good and it's staying — we're not rebuilding *it*. We're pulling the floor out from under it.

**Why this lesson is not like the others.** This is a deliberate **foundation swap**, decided out-of-band: cross-platform is off the table (you're Windows-only, this is a hobby), you already know OpenGL, and you want to spend your time on the *loop, input, and gameplay* — not re-learn a pipeline you know. So the engine moves to **Direct3D 11**, driven through **Silk.NET** (windowing + loop + input + D3D bindings, one ecosystem). Two consequences up front, stated plainly so nothing's a surprise:

- **OpenTK comes out entirely.** It's a GL/GLFW stack; it can't host a D3D device. Lessons 1.1–1.4 remain as the OpenGL foundation you built, but from here the rendering stack is D3D11.
- **This lesson has one unavoidable lump of setup** — device, swap chain, render-target view — that GL handed you for free behind `GameWindow`. It's a one-time cost. I'm going to map each piece to the GL concept you already own rather than teach it from zero, because you don't need "what is a back buffer" explained. After this, you rarely touch it again.

Controllers — the thing you actually want — are **1.6**, the very next lesson, using `Silk.NET.Input`. This lesson gets you a window, the loop, and a cleared screen on D3D11 so that lesson has a foundation to stand on.

## Concept: the same picture, a different set of nouns

Everything you did in GL still happens — it just has different names and a different *shape*. Two shifts matter, and both are things you'll feel immediately.

**GL was a global state machine; D3D is an object model.** In GL you bound things into hidden global slots (`glBindBuffer`, the current framebuffer) and hoped. D3D hands you explicit objects and you call methods on them. Concretely, the GL context splits into **two** objects: an `ID3D11Device` (the resource *factory* — it creates buffers, textures, views) and an `ID3D11DeviceContext` (the *command issuer* — it binds things and records draws/clears). Roughly: *device = "make me a thing," context = "do a thing."* GL fused those into one implicit context; D3D makes the split explicit, and it's honestly clearer once it clicks.

**Here's the map from what you know to what you're about to type:**

| OpenGL / OpenTK | Direct3D 11 / Silk.NET | What it is |
|---|---|---|
| The GL context | `ID3D11Device` + `ID3D11DeviceContext` | Factory vs. command issuer, split in two |
| The default framebuffer's color buffer | Swap-chain back buffer + an `ID3D11RenderTargetView` | The texture you draw into, plus an explicit "treat it as a color target" view |
| `glClearColor` + `glClear(GL_COLOR_BUFFER_BIT)` | `ClearRenderTargetView(view, color)` | The erase — but D3D takes the color as an **argument**, not sticky state (more on this below) |
| `SwapBuffers()` (GLFW, hidden by `Run()`) | `swapChain.Present(sync, 0)` | Show the back buffer; `sync` is your VSync knob |
| `GameWindow` you **subclass** | `IWindow` you **compose** | Ownership flips from inheritance to composition |

That last row is a real design change, and a welcome one. In 1.1 I flagged that subclassing OpenTK's fat `GameWindow` would eventually bite (lesson 4.1). Silk.NET removes the temptation: you don't inherit a window, you *own* one and subscribe to its `Load` / `Update` / `Render` events — each of which hands you a `double delta` that is exactly your old `args.Time`. Your loop, your timing math, your title readout: all of it ports over almost line-for-line, now living in event handlers instead of overrides.

One contrast worth savoring, since you just would've written the GL version: **D3D11 has no `ClearColor` state.** In GL, "clear color" is sticky state you set once and `glClear` reads it later — the state-machine tax. In D3D you pass the color straight into `ClearRenderTargetView`. There's simply no hidden state to forget to set. That difference — command takes its data as arguments vs. command reads global state — is the whole GL-vs-D3D personality in one call.

## Step 1 — swap the packages in `Firmament.Core`

D3D lives in the engine, same as GL did. Edit **`Firmament.Core/Firmament.Core.csproj`**: drop the OpenTK reference, add the three Silk.NET packages, and turn on unsafe blocks (the raw D3D bindings pass native pointers, so `unsafe` is mandatory):

```xml
<PropertyGroup>
	<TargetFramework>net10.0</TargetFramework>
	<ImplicitUsings>enable</ImplicitUsings>
	<Nullable>disable</Nullable>
	<LangVersion>default</LangVersion>
	<RootNamespace>Firmament.Core</RootNamespace>
	<AssemblyName>Firmament.Core</AssemblyName>
	<PlatformTarget>x64</PlatformTarget>
	<AllowUnsafeBlocks>true</AllowUnsafeBlocks>
</PropertyGroup>
<ItemGroup>
	<!-- remove: <PackageReference Include="OpenTK" Version="4.9.4" /> -->
	<PackageReference Include="Silk.NET.Windowing" Version="2.23.0" />
	<PackageReference Include="Silk.NET.Direct3D11" Version="2.23.0" />
	<PackageReference Include="Silk.NET.DXGI" Version="2.23.0" />
</ItemGroup>
```

| Package | Why |
|---|---|
| `Silk.NET.Windowing` | The window + the loop. Gives you `IWindow` with `Load`/`Update`/`Render` events and `Run()` — the OpenTK `GameWindow` role, minus the inheritance. |
| `Silk.NET.Direct3D11` | The D3D11 API surface: `D3D11.GetApi`, `ID3D11Device`, `ID3D11DeviceContext`, views. |
| `Silk.NET.DXGI` | DXGI owns the swap chain and `Present`. D3D renders; DXGI presents. They're separate libraries because DXGI is shared across D3D11/12. |
| `<AllowUnsafeBlocks>true` | Silk.NET's D3D bindings mirror the C API — native pointers and `ComPtr<T>`. Without this the project won't compile. |

`Silk.NET.Input` (controllers) is deliberately **not** here yet — that's 1.6.

## Step 2 — rewrite `FirmamentWindow` as a composed D3D11 host

Replace **`Firmament.Core/FirmamentWindow.cs`** entirely. It's no longer a `GameWindow` subclass — it *owns* an `IWindow`, sets up D3D11 once on load, and clears + presents each render frame. Your 1.3 timing/readout logic is ported verbatim into the render handler:

```csharp
using System.Runtime.CompilerServices;
using Silk.NET.Core.Native;
using Silk.NET.Direct3D11;
using Silk.NET.DXGI;
using Silk.NET.Maths;
using Silk.NET.Windowing;

namespace Firmament.Core;

public unsafe class FirmamentWindow : IDisposable
{
	private const double ReportIntervalSeconds = 1.0;

	private readonly IWindow window;

	private DXGI dxgi;
	private D3D11 d3d11;
	private ComPtr<ID3D11Device> device;
	private ComPtr<ID3D11DeviceContext> deviceContext;
	private ComPtr<IDXGISwapChain1> swapChain;
	private ComPtr<ID3D11RenderTargetView> renderTargetView;

	private double secondsSinceLastReport;
	private int updatesSinceLastReport;
	private int rendersSinceLastReport;
	private double peakRenderSeconds;

	public FirmamentWindow(int width, int height, string title)
	{
		var options = WindowOptions.Default with
		{
			API = GraphicsAPI.None,
			Size = new Vector2D<int>(width, height),
			Title = title,
		};

		window = Window.Create(options);
		window.Load += OnLoad;
		window.Update += OnUpdate;
		window.Render += OnRender;
	}

	public void Run()
	{
		window.Run();
	}

	private void OnLoad()
	{
		dxgi = DXGI.GetApi(window);
		d3d11 = D3D11.GetApi(window);

		SilkMarshal.ThrowHResult(
			d3d11.CreateDevice(
				default(ComPtr<IDXGIAdapter>),
				D3DDriverType.Hardware,
				default,
				(uint)CreateDeviceFlag.None,
				null,
				0,
				D3D11.SdkVersion,
				ref device,
				null,
				ref deviceContext
			)
		);

		var swapChainDesc = new SwapChainDesc1
		{
			BufferCount = 2,
			Format = Format.FormatB8G8R8A8Unorm,
			BufferUsage = DXGI.UsageRenderTargetOutput,
			SwapEffect = SwapEffect.FlipDiscard,
			SampleDesc = new SampleDesc(1, 0),
		};

		ComPtr<IDXGIFactory2> factory = default;
		SilkMarshal.ThrowHResult(dxgi.CreateDXGIFactory2(0, out factory));
		SilkMarshal.ThrowHResult(
			factory.CreateSwapChainForHwnd(
				device,
				window.Native.DXHandle.Value,
				in swapChainDesc,
				null,
				ref Unsafe.NullRef<IDXGIOutput>(),
				ref swapChain
			)
		);
		factory.Dispose();

		ComPtr<ID3D11Texture2D> backBuffer = default;
		SilkMarshal.ThrowHResult(swapChain.GetBuffer(0, out backBuffer));
		SilkMarshal.ThrowHResult(device.CreateRenderTargetView(backBuffer, null, ref renderTargetView));
		backBuffer.Dispose();
	}

	private void OnUpdate(double delta)
	{
		updatesSinceLastReport++;
	}

	private void OnRender(double delta)
	{
		float[] clearColor = [0.2f, 0.3f, 0.3f, 1.0f];

		deviceContext.OMSetRenderTargets(1, ref renderTargetView, (ComPtr<ID3D11DepthStencilView>)default);
		deviceContext.ClearRenderTargetView(renderTargetView, ref clearColor[0]);

		swapChain.Present(0, 0);

		secondsSinceLastReport += delta;
		rendersSinceLastReport++;

		if (delta > peakRenderSeconds)
		{
			peakRenderSeconds = delta;
		}

		if (secondsSinceLastReport < ReportIntervalSeconds)
		{
			return;
		}

		ReportPerformance();
		ResetWindow();
	}

	private void ReportPerformance()
	{
		var framesPerSecond = rendersSinceLastReport / secondsSinceLastReport;
		var avgMilliseconds = secondsSinceLastReport / rendersSinceLastReport * 1000.0;
		var peakMilliseconds = peakRenderSeconds * 1000.0;

		window.Title =
			$"Firmament - {framesPerSecond:F0} FPS | {avgMilliseconds:F2} ms avg | {peakMilliseconds:F2} ms peak | {updatesSinceLastReport} updates";
	}

	private void ResetWindow()
	{
		secondsSinceLastReport = 0.0;
		updatesSinceLastReport = 0;
		rendersSinceLastReport = 0;
		peakRenderSeconds = 0.0;
	}

	public void Dispose()
	{
		renderTargetView.Dispose();
		swapChain.Dispose();
		deviceContext.Dispose();
		device.Dispose();
		window.Dispose();
	}
}
```

Every non-obvious value, justified:

| Piece | Why |
|---|---|
| `API = GraphicsAPI.None` | Tells Silk.NET's windowing **not** to create a GL/Vulkan context — D3D brings its own device and DXGI does the presenting. Leave it default and Silk spins up an OpenGL context you'd fight. This is *the* line that makes it a D3D window. |
| `Window.Create` + event subscriptions (composition) | The inheritance→composition flip from the concept. `Load` fires once (your setup), `Update`/`Render` each carry `delta` seconds — your old `args.Time`. |
| `device` vs `deviceContext` | Factory vs. command issuer. `device.Create*` builds resources; `deviceContext.OMSetRenderTargets/Clear*` issues commands. The `deviceContext` here is the **immediate** context — commands execute as issued, exactly like the GL command stream. |
| `D3DDriverType.Hardware` | Use the real GPU. The software fallback is WARP (`D3DDriverType.Warp`) — relevant only in the "device creation fails" failure mode below. |
| `D3D11.SdkVersion` | A required constant handshake for `CreateDevice`. Always this value; not a knob. |
| `BufferCount = 2` | Double buffering — front + back. The flip model requires **≥ 2**. This is the two-buffer ping-pong you know from GL, now explicit. |
| `Format.FormatB8G8R8A8Unorm` | 8-bit **B**GRA, normalized `0–1`. BGRA (not RGBA) is the conventional Windows swap-chain byte order. `Unorm` = the `0–1` float channels you know. |
| `BufferUsage = DXGI.UsageRenderTargetOutput` | We render *into* this buffer (vs. using it as a shader input). |
| `SwapEffect.FlipDiscard` | The modern DXGI flip-model present path (efficient on Win10+). "Discard" = don't preserve back-buffer contents after present — fine, we clear every frame. |
| `SampleDesc(1, 0)` | 1 sample per pixel, quality 0 — i.e. **no MSAA**. Anti-aliasing is a later concern. |
| `CreateSwapChainForHwnd(..., window.Native.DXHandle.Value, ...)` | Binds the swap chain to the Win32 window handle (`HWND`). This is the DXGI↔OS bridge — GLFW did this invisibly when it attached the GL context. `Native.DXHandle` is the window's native handle Silk.NET exposes for exactly this. |
| `ref Unsafe.NullRef<IDXGIOutput>()` | The "restrict to this monitor for fullscreen" parameter — we pass a null reference for windowed. `Unsafe.NullRef<T>()` is how you spell a `null` `ref` argument. |
| RTV via `GetBuffer(0)` → `CreateRenderTargetView` | Fetch back buffer #0, then make a **render-target view**: metadata that says "interpret this texture as a color target I can clear/draw into." GL gave you the default framebuffer's color attachment for free; D3D makes you name it. Created **once** here (not per frame — recreating it every frame is a common tutorial wart and pure waste). |
| `OMSetRenderTargets(1, ref rtv, default)` | Bind the RTV as the output of the **O**utput-**M**erger stage. The `default` `ID3D11DepthStencilView` = no depth buffer yet (that's a 3D concern). GL's default-framebuffer binding was implicit; here it's one explicit call. |
| `ClearRenderTargetView(rtv, ref clearColor[0])` | The erase. Note the color is an **argument** — no `ClearColor` state call exists in D3D. `ref clearColor[0]` hands over a pointer to the 4 floats (RGBA order in the API, even though the buffer is stored BGRA — the runtime maps it). |
| `Present(0, 0)` | Swap front/back — your `SwapBuffers`. First arg is the **sync interval**: `0` = no VSync (uncapped, will tear), `1` = VSync to the monitor. We run `0` to match your uncapped OpenTK loop; flipping it to `1` is your VSync lever (exercise 2). |
| `ComPtr<T>` + `Dispose()` | D3D objects are COM — reference-counted. `ComPtr` is Silk.NET's smart handle; `Dispose` releases the ref. Releasing in reverse creation order in `Dispose()` is the tidy habit (and the seed of lesson 4.3, GL/GPU object lifetimes). |

## Step 3 — construct it from the game

Replace **`Firmament.Asteroids2D/Program.cs`**. No more OpenTK `NativeWindowSettings` — the window's size/title are constructor args now:

```csharp
using Firmament.Core;

namespace Firmament.Asteroids2D;

public static class Program
{
	public static void Main()
	{
		using var window = new FirmamentWindow(1280, 720, "Firmament");

		window.Run();
	}
}
```

`using var` because `FirmamentWindow` now owns disposable COM objects plus the window — same discipline as the old `GameWindow`, just ours to honor explicitly.

## ✅ Checkpoint

- A 1280×720 window titled **Firmament** opens, filled with a steady **dark teal** (`0.2, 0.3, 0.3`) — no garbage, no flicker. That solid color is your D3D11 clear working.
- The **title bar updates once a second**, identical in shape to your OpenTK build: `Firmament - 8500 FPS | 0.12 ms avg | 2.10 ms peak | 8500 updates`. Your loop survived the transplant intact.
- Uncapped, expect thousands of FPS and a sub-millisecond average — `Present(0, 0)` means no VSync yet, same as before.
- Closing the window exits cleanly, code 0; `Dispose` releases the device/swap chain/window.
- One CPU core is pegged — still uncapped. Exercise 2 (or a later lesson) puts the lid on with `Present(1, 0)`.

## 🐛 Common failure modes

1. **`error CS0227: unsafe code may only appear if compiled with /unsafe`.** You missed `<AllowUnsafeBlocks>true</AllowUnsafeBlocks>` in `Firmament.Core.csproj`. The D3D bindings are pointer-based; it's mandatory.
2. **`NullReferenceException` on `window.Native.DXHandle.Value` in `OnLoad`.** Almost always `API` isn't `GraphicsAPI.None`, or you're reading the handle before `Load` fires. The native handle only exists once the window is created — do all D3D setup inside the `Load` handler, never in the constructor.
3. **`SharpGen`/`COMException` HRESULT thrown from `CreateDevice`.** The driver can't give a hardware D3D11 device — typically a VM, RDP session, or stale GPU driver (the D3D analog of 1.1's "3.3 context not available"). Update the GPU driver; to confirm it's environmental, temporarily pass `D3DDriverType.Warp` (software renderer) — if that works, it's your driver/display, not your code.
4. **Window is black, not teal.** You're presenting a buffer you never bound or cleared. Check that `OMSetRenderTargets` runs *before* `ClearRenderTargetView`, that `renderTargetView` was actually created in `OnLoad` (the `GetBuffer`→`CreateRenderTargetView` pair), and that `Present` is being called.
5. **Resizing the window corrupts or freezes rendering.** Expected and deferred. The RTV is tied to the original back-buffer size; a resize needs `swapChain.ResizeBuffers` + rebuilding the RTV. That's the D3D equivalent of the viewport/resize work the OpenGL track parked in 1.7 — don't chase it here. Keep the window at its start size for now.
6. **`ms avg` prints `0.00`.** You wired the timing to something other than the `delta` the `Render` event hands you. Use that `delta` — it's the per-frame seconds, same contract as `args.Time`.

## 🔧 Exercises

1. **Animate the clear color (proof of life).** This is the old curriculum 1.5, and it's a two-line change now: add a `double elapsed;` field, do `elapsed += delta;` in `OnRender`, and set `clearColor[1] = (float)(Math.Sin(elapsed) * 0.5 + 0.5);`. The window pulses green — visible proof the loop is alive, no title bar needed. Note you're passing the color as an argument every frame; there's no state to fight.
2. **Find your VSync knob.** Change `Present(0, 0)` to `Present(1, 0)` and re-run. FPS collapses to your monitor's refresh (~60/144), `ms avg` snaps to `16.67`/`6.94`, and the pegged core relaxes. That one integer is the entire VSync lesson the OpenGL track saved for 1.8 — you got it for free in the present call.
3. **Turn on the D3D debug layer.** Change the `CreateDevice` flag to `(uint)CreateDeviceFlag.Debug` and run with the Graphics Tools feature installed. D3D now validates every call and writes warnings to the debugger output — the D3D equivalent of `glGetError`/`KHR_debug`, and worth wiring in a `Debug`-only build (foreshadows lesson 2.10's spirit). Note it's slower; gate it to debug builds.
4. **Prove the device/context split.** Try to call `ClearRenderTargetView` on `device` instead of `deviceContext`. It won't compile — clears are *commands* (context), not *resource creation* (device). Feel where the line is; it's the mental model that keeps D3D straight.

## ⚠️ Curriculum divergence (the whole README, honestly)

The README from Part 2 onward is written in OpenGL: VBOs, VAOs, GLSL, `GL.DrawArrays`, `GL.GetError`. Those concepts all have exact D3D11 counterparts — vertex buffers become `ID3D11Buffer`, `VertexAttribPointer`/VAO becomes an **input layout**, GLSL becomes **HLSL**, `DrawArrays` becomes `deviceContext.Draw`, the debug callback becomes the debug layer. Nothing conceptual is lost by the pivot; the *nouns* change. Since you already know the pipeline, you'll likely skim or skip much of Parts 2–3 and spend your time where you said the interest is: the loop, input, entities, and gameplay. **Re-scoping the curriculum text to D3D11 is a separate task** — say the word and I'll rewrite the README's lesson list to match this new foundation. For now, treat every "GL"/"GLSL" mention past this lesson as "its D3D11 equivalent."
