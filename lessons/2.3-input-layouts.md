## Concept: the buffer is bytes, the layout is the schema

A vertex buffer is a featureless run of bytes. The GPU has no idea that byte 8 begins a color. It doesn't know how many bytes one vertex occupies. It doesn't know there are three vertices in there rather than five. `CreateBuffer` allocates memory and copies your bytes into it, and that is the entire extent of what the GPU learns from that call.

Three separate pieces of information supply the missing meaning, and — this is the part that trips people — they are supplied at three different times through three different APIs:

1. **The stride** — how many bytes one vertex occupies — is given to `IASetVertexBuffers` at bind time. This is the input assembler's step size. It walks the buffer in stride-sized hops, and hop *n* is vertex *n*.
2. **The offset** — where in the buffer vertex 0 starts — is also given to `IASetVertexBuffers`. Almost always 0 until you start suballocating one big buffer for many meshes.
3. **The element descriptions** — what lives at which byte offset *within* one stride, and in what format — are an array of `InputElementDesc` baked into an `ID3D11InputLayout` object.

The picture to hold: the buffer is a strip of film, the stride is the frame height, and the input layout is the sprocket-and-mask assembly that says "positions are in this window of each frame, colors in that one." Change the mask and the same film reads as different geometry.

Now the part with no OpenGL analogue. In GL you bind attributes by *number* — `layout(location = 0)`. D3D11 binds them by **semantic**: a name plus an index, `POSITION0`, `COLOR0`, `TEXCOORD3`. Your `InputElementDesc` says "the 8 bytes at offset 0 are called POSITION0"; your HLSL vertex shader (2.4) declares a parameter tagged `: POSITION`. D3D matches them **by name, not by position in the array**. That's why `CreateInputLayout` demands compiled shader bytecode as an argument — it isn't being polite, it's *validating* your description against the shader's declared input signature and failing the call if a semantic the shader wants isn't described. You get an error at layout-creation time instead of garbage on screen, which is a genuinely good trade and the reason this lesson can't finish the job alone.

## Your vertex, byte by byte

Five floats, in declaration order:

```
 offset  0     4     8    12    16    20
         ├──X──┼──Y──┼──R──┼──G──┼──B──┤
         └──POSITION─┘└─────COLOR──────┘
           R32G32Float   R32G32B32Float
                stride = 20 bytes
```

Two things worth noticing before you write any code:

- **The stride is 20, not 16 or 32.** D3D11 imposes no power-of-two or 16-byte requirement on vertex stride — that rule belongs to *constant* buffers and it will bite you in 2.11. Element offsets must be 4-byte aligned, which 0 and 8 both are. 20 is fine. Do not pad it.
- **Position is 2D.** `FormatR32G32Float`, two components, because Asteroids is 2D. The vertex shader will supply z and w itself. A `float3` position here would waste 4 bytes per vertex forever.

## Steps — what to write and where

### Step 1 — Tighten `Vertex` (optional, but argue with me)

What you have compiles and produces the right 20 bytes. Everything below this lesson needs is already true. So this step is a recommendation, not a correction — take it or push back:

```csharp
using System.Runtime.InteropServices;

namespace Firmament.Core.Types;

[StructLayout(LayoutKind.Sequential)]
public readonly struct Vertex(float x, float y, float r, float g, float b)
{
	public readonly float X = x;

	public readonly float Y = y;

	public readonly float R = r;

	public readonly float G = g;

	public readonly float B = b;
}
```

Three changes, each with a reason that only applies to types whose byte offsets are load-bearing:

- **`readonly`, and no setters.** A vertex is a value; once it's in the buffer, mutating the C# copy means nothing anyway. `in`-passing a `readonly struct` also skips the defensive copy. Your current version has public setters on a type that is conceptually immutable data.
- **Public fields instead of auto-properties.** This is the one worth arguing about, because your version genuinely works: Roslyn emits backing fields in source declaration order and sequential layout follows. But that ordering is a compiler implementation detail, not a language guarantee, and this is the one type in the engine where field order *is* the contract with the GPU. Fields state the layout in source rather than inferring it from codegen. `dotnet format` won't object — IDE0032 only fires on a hand-written field/property pair, never on plain public fields.
- **`[StructLayout(LayoutKind.Sequential)]`, which is redundant** — C# already defaults structs to sequential. It's a tripwire, not a behaviour change: it makes the layout dependency visible so nobody later "tidies up" by reordering fields without noticing what they broke.

If you'd rather keep auto-properties for consistency with the rest of the codebase, that's a defensible call and nothing downstream breaks. Just don't reorder them.

### Step 2 — Create the vertex buffer

`FirmamentWindow` already has `unsafe` on the class, so pointers are available. Add the fields:

```csharp
	private ComPtr<ID3D11Buffer> vertexBuffer;
	private InputElementDesc[] vertexLayoutDescription;
	private readonly List<nint> unmanagedSemanticNames = [];
```

and the import, since `Vertex` lives in another namespace:

```csharp
using Firmament.Core.Types;
```

Then the method:

```csharp
	private void CreateVertexBuffer()
	{
		Vertex[] vertices =
		[
			new Vertex(0.0f, 0.5f, 1f, 0f, 0f),
			new Vertex(0.5f, -0.5f, 0f, 1f, 0f),
			new Vertex(-0.5f, -0.5f, 0f, 0f, 1f),
		];

		var bufferDescription = new BufferDesc
		{
			ByteWidth = (uint)(sizeof(Vertex) * vertices.Length),
			Usage = Usage.Immutable,
			BindFlags = (uint)BindFlag.VertexBuffer,
		};

		fixed (Vertex* vertexData = vertices)
		{
			var initialData = new SubresourceData { PSysMem = vertexData };

			SilkMarshal.ThrowHResult(device.CreateBuffer(in bufferDescription, in initialData, ref vertexBuffer));
		}
	}
```

The constructor calls assume step 1. If you kept auto-properties, use object initializers instead — `new Vertex { X = 0.0f, Y = 0.5f, R = 1f, G = 0f, B = 0f }` — and nothing else in the lesson changes.

Those coordinates are already in **clip space** — the [-1, 1] box the rasterizer works in — because there is no vertex shader yet to transform anything. Part 3 replaces them with world units and a projection matrix. Until then, the triangle is hard-coded into the space the GPU already speaks.

`fixed` pins the array so the GC can't move it while `CreateBuffer` copies out of it. The copy completes before the call returns, which is why nothing needs to stay pinned afterward.

### Step 3 — Describe the layout

```csharp
	private byte* AllocateSemanticName(string semanticName)
	{
		var pointer = SilkMarshal.StringToPtr(semanticName, NativeStringEncoding.LPStr);

		unmanagedSemanticNames.Add(pointer);

		return (byte*)pointer;
	}

	private void DescribeVertexLayout()
	{
		vertexLayoutDescription =
		[
			new InputElementDesc
			{
				SemanticName = AllocateSemanticName("POSITION"),
				SemanticIndex = 0,
				Format = Format.FormatR32G32Float,
				InputSlot = 0,
				AlignedByteOffset = 0,
				InputSlotClass = InputClassification.PerVertexData,
				InstanceDataStepRate = 0,
			},
			new InputElementDesc
			{
				SemanticName = AllocateSemanticName("COLOR"),
				SemanticIndex = 0,
				Format = Format.FormatR32G32B32Float,
				InputSlot = 0,
				AlignedByteOffset = 8,
				InputSlotClass = InputClassification.PerVertexData,
				InstanceDataStepRate = 0,
			},
		];
	}
```

`InputElementDesc.SemanticName` is a `byte*` to a null-terminated ANSI string — a raw C string, not a .NET one. `SilkMarshal.StringToPtr(..., NativeStringEncoding.LPStr)` allocates that; nothing frees it automatically. The strings must stay alive until `CreateInputLayout` reads them in 2.5, so they're tracked in `unmanagedSemanticNames` and released in `Dispose`. This is the first unmanaged allocation in the engine that isn't a COM object, and it is exactly the kind of thing 4.3 exists to systematise.

### Step 4 — Wire it into `OnLoad` and `Dispose`

In `OnLoad`, after `GetGamepad()`:

```csharp
		CreateVertexBuffer();
		DescribeVertexLayout();
```

In `Dispose`, before `deviceContext.Dispose()` — COM objects go down in reverse order of creation:

```csharp
		vertexBuffer.Dispose();

		foreach (var semanticName in unmanagedSemanticNames)
		{
			SilkMarshal.Free(semanticName);
		}
```

### Step 5 — Bind it, with the stride and offset

```csharp
	private void BindVertexBuffer()
	{
		var stride = (uint)sizeof(Vertex);
		uint offset = 0;

		deviceContext.IASetVertexBuffers(0, 1, ref vertexBuffer, in stride, in offset);
	}
```

Call it from `OnRender`, right after `ClearRenderTargetView`. Nothing on screen will change — there is no shader and no `Draw`, so the IA has a buffer bound and no reason to read it. That is the correct outcome for this lesson.

`sizeof(Vertex)` and never `20`. The whole point of step 1 was to make the struct the single source of truth for the stride; hard-coding the number puts a second copy of it somewhere the compiler can't check, and the day you add a UV to `Vertex` the two disagree silently.

## Why `CreateInputLayout` isn't here

The signature is:

```
CreateInputLayout(in InputElementDesc descriptions, uint elementCount,
                  void* shaderBytecodeWithInputSignature, nuint bytecodeLength,
                  ref ComPtr<ID3D11InputLayout> inputLayout)
```

That third argument is compiled vertex shader bytecode. You have no shader (2.4) and no compiler — `Silk.NET.Direct3D.Compilers` isn't even a package reference yet (2.5). So `CreateInputLayout` and `IASetInputLayout` land in **2.5**, one call each, using the `vertexLayoutDescription` array you just built. This lesson ends with the description written and the buffer bound, which is genuinely everything that can be done before the shader exists.

## Per-value justification

| Value | Why |
|---|---|
| `ByteWidth = sizeof(Vertex) * count` | The device allocates in bytes and has no concept of your struct. Derived, never typed by hand. |
| `Usage.Immutable` | Contents are set once at creation and never written again. Immutable lets the driver place it in the fastest GPU-local memory it has. `Usage.Default` also works; it just reserves an update path we'll never use. `Immutable` requires non-null initial data — you cannot create an empty one. |
| `BindFlag.VertexBuffer` | Bind flags declare which pipeline stages may ever see this buffer. Without it, `IASetVertexBuffers` is an invalid binding. |
| `(uint)BindFlag.VertexBuffer` cast | Silk.NET types `BufferDesc.BindFlags` as `uint`, not as the enum, because the native field is a bitmask of `D3D11_BIND_FLAG`. The cast is required, not stylistic. |
| `SemanticName = "POSITION"` | The name D3D matches against the HLSL parameter's `: POSITION` tag. Case-insensitive, but the SDK convention is uppercase. |
| `SemanticIndex = 0` | Disambiguates repeats of one semantic — `TEXCOORD0`, `TEXCOORD1`. One of each here, so 0. |
| `FormatR32G32Float` | Two 32-bit floats. Fixes both the byte count (8) *and* how the IA converts them for the shader. |
| `FormatR32G32B32Float` | Three 32-bit floats, 12 bytes. The shader sees `float3`; the missing alpha arrives as 1.0 if it asks for a `float4`. |
| `InputSlot = 0` | Both elements come from the single buffer bound to slot 0. D3D11 offers 32 slots; the second one shows up in 9.4 for per-instance data. |
| `AlignedByteOffset = 0` / `8` | Byte offset *within one vertex*, not into the buffer. Color starts after two 4-byte floats. |
| `InputClassification.PerVertexData` | Advance this element once per vertex. `PerInstanceData` advances once per instance — 9.4 again. |
| `InstanceDataStepRate = 0` | Must be 0 for per-vertex elements. Non-zero is a validation error. |
| `offset = 0` in `IASetVertexBuffers` | Vertex 0 starts at the beginning of the buffer. Non-zero when many meshes share one buffer. |

## ✅ Checkpoint

The solution builds clean, the window runs exactly as it did after 1.8 — color cycling, **V** toggling sync, **Space** pausing — and **no exception is thrown**. `SilkMarshal.ThrowHResult` around `CreateBuffer` is the real test here: a bad `BufferDesc` returns `E_INVALIDARG` and you'd know immediately.

To confirm the layout arithmetic, break on the `fixed` statement and evaluate `sizeof(Vertex)` in the debugger. **Expect exactly 20.** Anything else — 24, 40, 8 — means `Vertex` picked up a field you didn't intend, or stopped being an unmanaged value type; see failure mode 1.

Nothing new appears on screen. Correct. The pipeline still has no shaders bound and `Draw` is never called.

## 🐛 Common failure modes

1. **`CS0208: Cannot take the address of, get the size of, or declare a pointer to a managed type ('Vertex')`.** `Vertex` is a `class` again, or picked up a reference-typed field. `sizeof(Vertex)` and `fixed (Vertex* ...)` both require an unmanaged type — every field, transitively, must be a value type. You already hit and fixed this one. Worth noting how it surfaced: a build error rather than a GPU quietly rendering garbage. That's the payoff for pinning the memory layout in the type system instead of in a comment.
2. **`E_INVALIDARG` (`0x80070057`) out of `CreateBuffer`.** Either `BindFlags` is 0 (forgot the flag, or assigned the enum where a `uint` was wanted and it silently became something else), or `ByteWidth` is 0 because you sized off `vertices.Length` alone.
3. **`AlignedByteOffset` counting elements instead of bytes** — writing `2` for COLOR because it's "after two floats". The IA would then read color starting mid-`Y`. This produces no error anywhere; you'd see it as wrong colors in 2.6 and spend an hour on it. Offsets are always bytes.
4. **Semantic name pointers freed too early.** Freeing them at the end of `DescribeVertexLayout` instead of in `Dispose` leaves `InputElementDesc.SemanticName` dangling. Everything looks fine until `CreateInputLayout` in 2.5 reads freed memory and fails with an unhelpful HRESULT.
5. **Struct field order edited without touching the descriptions.** Move `Red` above `Y` and the offsets in step 3 are now lies. Nothing warns you. This is precisely the coupling the `[StructLayout]` attribute is there to advertise.

## 🔧 Exercises

1. Replace `AlignedByteOffset = 8` with `D3D11.AppendAlignedElement` (which is `0xFFFFFFFF`). Behaviour is identical — it tells D3D to compute the offset by packing this element immediately after the previous one in the same slot. Then say why you'd still sometimes want the literal: what does the sentinel do if someone inserts an element above it?
2. Add a sixth float to `Vertex` and re-check `sizeof` in the debugger — 24. Leave the input layout untouched. Convince yourself the app is still correct: the IA reads what the descriptions name and steps by the stride, so trailing bytes nobody described are simply never read. Wasted bandwidth, not a bug.
3. Change COLOR's format to `FormatR32G32B32A32Float` and reason it through on paper without running it: the buffer holds 12 bytes of color per vertex, the description now claims 16. What does the IA read as alpha for vertex 0? For vertex 2, the last one in the buffer? (This is a real out-of-bounds read that D3D will not stop you from describing. The debug layer in 2.10 is the thing that eventually catches it.)
4. Swap the two entries in the `vertexLayoutDescription` array so COLOR is first. Nothing changes, because matching is by semantic name and offset, not array position. Then predict what *would* have to change if this were OpenGL.
