# Lesson 2.2 — Vertex Buffer Objects

> Part 2 — The Pipeline and the First Triangle
> *Vertex Buffer Objects: getting floats onto the GPU*

**Where you already are:** `FirmamentWindow` opens a Win32 window, creates a D3D11 `ID3D11Device` / `ID3D11DeviceContext`, binds a render target, clears it, and presents. Nothing so far has bound per-vertex data to the IA; that is what this lesson teaches.

## Concept (≈220 words)

A vertex buffer is simply a contiguous blob of bytes the GPU reads as vertex attributes when a draw call runs. It is not typed: the GPU does not know a chunk of bytes means "three floats for position" until you describe the layout (that's the job of the input layout in 2.3). Creating a vertex buffer is therefore two steps: (1) allocate GPU memory and upload your bytes, and (2) later bind that GPU buffer to the input assembler with an explicit stride and offset when you draw.

Think physically: a VBO is a pallet of vertex data sitting in GPU memory. The input layout is the label on the pallet telling the loader how to unpack each package. You can update the pallet in-place (dynamic streaming) or make it immutable for speed. The two common patterns are:

- Static upload: create a buffer with the vertex data once (Usage = Default) and reuse it.
- Dynamic stream: create it with CPU write access or use staging updates each frame (Usage = Dynamic + Map/Unmap) when vertices change frequently.

In Direct3D 11 / Silk.NET the object is an `ID3D11Buffer` created via `CreateBuffer`. The key facts you must get right:

- ByteWidth = sizeof(vertex) * vertexCount (one-line reason: GPU needs bytes count to allocate memory)
- BindFlags includes `BindFlag.VertexBuffer`
- Usage/CPUAccessFlags determine how and how often you can update the buffer (Default = GPU-only; Dynamic = CPU-writable with Map)

## Steps — what to write and where

1) Define a vertex shape in your game project (new or in `Firmament.Asteroids2D/Types`):

```csharp
// File: Firmament.Asteroids2D/Vertex.cs
namespace Firmament.Asteroids2D;

public struct Vertex
{
    public float X { get; set; }
    public float Y { get; set; }
    public float R { get; set; } // optional vertex color
    public float G { get; set; }
    public float B { get; set; }
}
```

Reason: keep a single compact POD struct; its layout (3 floats pos + 3 floats color) defines the byte stride you will give the IA.

2) Write the snippet that creates a static vertex buffer near your renderer initialization (example shown; adapt to your `ID3D11Device` variable names):

```csharp
// Pseudocode / template to type into your renderer setup
// Ensure the device variable is the Silk.NET ID3D11Device you already create in FirmamentWindow

var vertices = new Vertex[] { new Vertex { X=-0.5f, Y=-0.5f, R=1,G=0,B=0 }, /* ... */ };
var byteWidth = (uint)(Unsafe.SizeOf<Vertex>() * vertices.Length);

// BufferDesc: ByteWidth=byteWidth, BindFlags=BindFlag.VertexBuffer, Usage=Usage.Default
// SubresourceData: pSysMem = pointer to vertices array
// device.CreateBuffer(ref desc, ref initData, out ID3D11Buffer vertexBuffer);

// Later, at draw time:
// uint stride = (uint)Unsafe.SizeOf<Vertex>();
// uint offset = 0;
// deviceContext.IASetVertexBuffers(0, 1, ref vertexBuffer, ref stride, ref offset);
// deviceContext.Draw(vertexCount, 0);
```

Notes:
- The exact `CreateBuffer` and `IASetVertexBuffers` call signatures are the Silk.NET wrappers around D3D11 methods; copy the names above and the SDK will show the parameter order and `ref`/`out` requirements in IntelliSense. The important API facts are the names of the concepts (ByteWidth, BindFlags.VertexBuffer, stride, offset) and their reasons.
- Use `Unsafe.SizeOf<T>()` (System.Runtime.CompilerServices.Unsafe) or `Marshal.SizeOf<T>()` to compute byte widths; avoid magic numbers.

3) Where to put it: a small `InitializeBuffers()` method in your existing renderer/firmament window file is the least invasive place. This lesson deliberately does not introduce a new Buffer helper class — that comes in 2.7 when we build a `Shader` helper and then a small `GpuBuffer` abstraction.

## Per-value justification

- BindFlag.VertexBuffer: the GPU must know this buffer will be read as vertices, not as a constant buffer or index buffer.
- ByteWidth computed from struct size: the device needs an exact byte count to allocate backing store.
- Usage.Default vs Dynamic: Default is fastest for static geometry; Dynamic is for per-frame updates. Pick Default until you need streaming.

## ✅ Checkpoint

When you run, a call to `Draw` with a correctly-created vertex buffer + input layout (2.3) will produce geometry instead of a blank screen. At this stage, expect a single unshaded triangle if you uploaded three vertices.

## 🐛 Common failure modes

1. Wrong byte stride/offset → triangle appears garbled or stretched. (Most common.)
2. Forgot to set BindFlag.VertexBuffer → nothing reads the buffer; draw emits garbage or nothing.
3. Using `Usage.Dynamic` but never mapping/unmapping → driver errors or stale data.
4. Computing size with `sizeof(float) * N` and later changing `Vertex` → mismatch; prefer `Unsafe.SizeOf<Vertex>()`.
