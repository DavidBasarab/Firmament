# Lesson 1.6 — Keyboard Input and ESC to Quit

> Part 1 — A Window and a Heartbeat
> *Keyboard input basics: ESC to quit, snapshot (polling) vs. event*

**Where you already are:** your committed `FirmamentWindow` is a composed D3D11 host — it owns an `IWindow`, sets up the device/swap chain/RTV once in `OnLoad`, and every `OnRender` it lerps a clear color through a list of ten `System.Drawing.Color`s (that's the cycling system you built past the 1.5 exercise — the `AdvanceColorTransition` / `InterpolateClearColor` machinery). The loop is honest and the screen is alive. What it can't do yet is *listen*. Right now the only way to close the window is the title-bar X. This lesson gives the engine its first sense: the keyboard.

---

## Concept: two ways to ask "is this key down?"

Every input system in every engine offers the same two flavors, and picking the right one per situation is the whole skill. Silk.NET is no exception.

**Events — "tell me the moment it changes."** You subscribe a handler to `KeyDown` / `KeyUp`. It fires **once**, at the instant the key crosses from up→down (or down→up). That single edge is exactly what you want for a *discrete* action: quit, jump, fire, toggle pause. If you held ESC for three seconds, `KeyDown` fired **one** time. You never ask "is it down?" — you're told when it flips.

**Polling (a snapshot) — "what's the state right now?"** You call `keyboard.IsKeyPressed(Key.W)` and get the live truth this instant. You ask it *every frame*, inside the loop. That's what you want for *continuous* input: thrust while W is held, steer while ← is held. The state is level, not edge — it's true for all 180 frames you hold the key, and you re-check it each one.

> **README wording note.** The curriculum calls this "`KeyboardState` snapshot vs event" — that's the OpenTK noun. OpenTK handed you an immutable `KeyboardState` struct you'd snapshot each frame. Silk.NET has no such struct: instead `IKeyboard` is a **live object** you poll via `IsKeyPressed`. Same two paradigms, one fewer type. Per the 1.5 pivot, read every OpenTK noun past 1.4 as "its Silk.NET equivalent."

The trap people fall into is using the wrong one: polling for a discrete action gives you the ugly "if I hold the key it re-triggers every frame" bug (menu scrolls 60 items in one press); events for continuous movement gives you a ship that lurches once and stops. Rule of thumb: **edge → event, level → poll.** ESC-to-quit is the purest edge action there is, so we wire it as an event. Then we'll poll a held key to freeze your color cycle, so you feel the level style too.

One thing we are *not* doing yet: "was this key pressed **this frame**?" via polling — detecting the edge yourself by comparing this frame's snapshot to last frame's. That `WasPressed` / `WasReleased` distinction, plus action mapping (bind "Thrust" to a key instead of hard-coding `Key.W`), is **lesson 4.7**. Today: raw keys, one event, one poll.

## Step 1 — add the input package to `Firmament.Core`

Input rides on its own Silk.NET package. Edit **`Firmament.Core/Firmament.Core.csproj`** and add one line to the existing Silk.NET `ItemGroup`:

```xml
<PackageReference Include="Silk.NET.Windowing" Version="2.23.0" />
<PackageReference Include="Silk.NET.Direct3D11" Version="2.23.0" />
<PackageReference Include="Silk.NET.DXGI" Version="2.23.0" />
<PackageReference Include="Silk.NET.Input" Version="2.23.0" />   <!-- new -->
```

| Piece | Why |
|---|---|
| `Silk.NET.Input` | The input API surface: `CreateInput()`, `IInputContext`, `IKeyboard`, the `Key` enum. |
| Why the **meta**package, not `Silk.NET.Input.Common` | `Common` holds only the interfaces. The metapackage *also* pulls in the GLFW input **backend** (`Silk.NET.Input.Glfw`). `CreateInput()` finds a platform by looking for a registered backend assembly — reference only `Common` and it throws "couldn't find a suitable input platform" at runtime. Your window is a GLFW window under the hood (that's what Silk.NET windowing uses on Windows, even with `API = GraphicsAPI.None`), so the GLFW input backend is the right match. |

Version `2.23.0` to lock-step with the three packages already there — mixed Silk.NET versions are a needless source of load errors.

## Step 2 — create the input context and wire ESC (the event)

Input, like the swap chain, needs the window to exist first — so it's created in `OnLoad`, right alongside the D3D setup. Edit **`Firmament.Core/FirmamentWindow.cs`**.

Add the using at the top, with the other Silk.NET usings:

```csharp
using Silk.NET.Input;
```

Add two fields next to `window` (near the other private fields):

```csharp
private IInputContext input;
private IKeyboard keyboard;
```

At the **end of `OnLoad`** (after the render-target view is built — order doesn't matter, but keep D3D setup together), create the context and subscribe:

```csharp
input = window.CreateInput();
keyboard = input.Keyboards[0];
keyboard.KeyDown += OnKeyDown;
```

Then add the handler (a new method — mind the blank line between methods):

```csharp
private void OnKeyDown(IKeyboard source, Key key, int scancode)
{
    if (key == Key.Escape)
    {
        window.Close();
    }
}
```

| Piece | Why |
|---|---|
| `window.CreateInput()` | Extension method that spins up an `IInputContext` bound to this window. Returns the hub for every input device. Must run after the window's native handle exists — i.e. in/after `Load`, never in the constructor (same rule the DXGI handle taught you in 1.5). |
| `input.Keyboards[0]` | `Keyboards` is an `IReadOnlyList<IKeyboard>` — a machine can have several (laptop keyboard + USB). Index `0` is the primary; fine for a game. (If it's empty you'll get an `IndexOutOfRange` — see failure modes.) |
| `keyboard.KeyDown += OnKeyDown` | Subscribe to the press **edge**. The handler signature is fixed by Silk.NET: `Action<IKeyboard, Key, int>` — the source keyboard, the logical `Key`, and the raw hardware `scancode` (which we ignore via a named-but-unused parameter; it's for layout-independent binding, a 4.7 concern). |
| `window.Close()` | Ends the run loop cleanly — the programmatic equivalent of the title-bar X. `Dispose` then runs and tears down D3D + input. |
| `Key.Escape` | The `Key` enum is *logical* (`Escape`, `Space`, `W`, `Left`…), not physical scancodes — so it's keyboard-layout-friendly out of the box. |

## Step 3 — poll a held key (the snapshot) to freeze the color cycle

Now the level-style counterpart, so you feel the difference in the same build. Your color cycle advances every frame via `AdvanceColorTransition(delta)` in `OnRender`. We'll gate that call on the **live** state of the SPACE key: hold SPACE, the cycle freezes on the current color; release, it resumes.

In **`OnRender`**, wrap the existing advance call:

```csharp
if (!keyboard.IsKeyPressed(Key.Space))
{
    AdvanceColorTransition(delta);
}
```

| Piece | Why |
|---|---|
| `keyboard.IsKeyPressed(Key.Space)` | The snapshot: the key's truth *at this call*. Asked once per rendered frame, it reads `true` for every frame SPACE is held — that's the level behavior. No subscription, no edge — you pull the state when you need it. |
| Why gate the transition, not close on it | This is a *continuous* effect (freeze while held), the exact case polling is for. Doing the same with an event would need a `KeyDown`→pause / `KeyUp`→resume pair holding a bool — more moving parts for the same result. Level input → poll. |
| Why poll here in `OnRender` | Because that's where the color advances. Conventionally you poll *gameplay* input in `OnUpdate` (it's the logic tick), and once the fixed-timestep split lands in **4.2** that distinction starts to matter. `IsKeyPressed` reads live state, so it's correct in either handler; we poll where the thing it controls lives. |

## Step 4 — dispose the input context

`IInputContext` is `IDisposable`. Release it in `Dispose`, before the window (the window owns the native handle input is bound to). Edit **`Dispose`**:

```csharp
public void Dispose()
{
    renderTargetView.Dispose();
    swapChain.Dispose();
    deviceContext.Dispose();
    device.Dispose();
    input.Dispose();      // new — before window
    window.Dispose();
}
```

## ✅ Checkpoint

- The window opens and cycles colors exactly as before — nothing about the visuals changed on its own.
- **Press ESC** → the window closes immediately and the process exits clean (code 0). That's your `KeyDown` event firing on the edge and calling `window.Close()`.
- **Hold SPACE** → the color cycle **freezes** on whatever color it's mid-lerp toward; **release** → it resumes from there. That's `IsKeyPressed` polled every frame, reading the live held state.
- Tapping SPACE quickly gives a brief stutter in the cycle, not a toggle — because you're reading level state, not an edge. (Tapping ESC once is enough to quit, because that *is* an edge.)
- The title-bar FPS/ms readout keeps updating throughout — input added zero measurable per-frame cost.

## 🐛 Common failure modes

1. **`System.Exception` / "couldn't find a suitable input platform" from `CreateInput()`.** You referenced `Silk.NET.Input.Common` instead of the `Silk.NET.Input` metapackage, so the GLFW input backend assembly isn't present. Reference `Silk.NET.Input` (Step 1) and rebuild.
2. **`IndexOutOfRangeException` on `input.Keyboards[0]`.** Either `CreateInput()` ran before the window existed (it must be in `OnLoad`, not the constructor), or genuinely no keyboard is enumerated (rare on desktop). Confirm the create call sits inside `OnLoad`.
3. **`NullReferenceException` in `OnRender` on `keyboard`.** `OnRender` fired before `OnLoad` finished wiring `keyboard` — normally impossible (`Load` runs first), but happens if you moved the input setup out of `OnLoad` or into a branch that didn't run. Keep `input`/`keyboard` assignment unconditional at the end of `OnLoad`.
4. **ESC does nothing.** The `KeyDown += OnKeyDown` line is missing or you subscribed on a different `IKeyboard` than `Keyboards[0]`. Also check you compared against `Key.Escape` (the logical enum), not a char or scancode.
5. **SPACE doesn't freeze the cycle.** The poll is guarding the wrong thing, or you inverted the condition. It must be `if (!keyboard.IsKeyPressed(Key.Space))` wrapping the `AdvanceColorTransition(delta)` call — freeze means *skip* the advance while held.
6. **Holding ESC "spams" close / weird repeats.** You wired ESC as a poll (`IsKeyPressed` in the loop) instead of the `KeyDown` event. A discrete action polled every frame re-triggers each frame — use the event for quit.

## 🔧 Exercises

1. **Add a second discrete key.** In `OnKeyDown`, also handle `Key.F1` to log a line (`Console.WriteLine`) — prove the event fires exactly once per press, no matter how long you hold. Remove the log before committing (per the logging rules).
2. **Toggle instead of hold.** Make SPACE *toggle* the freeze rather than requiring a hold: flip a `bool colorCyclingPaused` field inside `OnKeyDown` when `key == Key.Space`, and gate the advance on that bool. Notice this needs the **event** (an edge) — a poll would flip the bool 60×/second and it'd flicker. This is the edge-vs-level lesson in your own hands.
3. **Reach the other devices.** `input.Mice[0]` and `input.Gamepads` hang off the same `IInputContext`. Log `input.Gamepads.Count` in `OnLoad` — plug in a controller and watch it change. (The 1.5 doc teased controllers; they ride this exact hub. A full gamepad lesson is 13.7.)
4. **Two keyboards, one truth.** If you have a second keyboard, subscribe `OnKeyDown` to *every* entry in `input.Keyboards` (a `foreach` in `OnLoad`) so ESC works from either. A hint at why 4.7's input manager centralizes this instead of scattering subscriptions.
