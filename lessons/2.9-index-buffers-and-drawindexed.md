# Lesson 2.9 — Index Buffers: A Quad from Four Vertices, and `DrawIndexed`

> Part 2 — The Pipeline and the First Triangle
> *Index buffers: drawing a quad with 4 vertices instead of 6, and `DrawIndexed`*

**Where you already are:** one triangle, drawn well. `Shader` (in `Firmament.Core/Shaders/`) owns the compile, both shader objects and the input layout. `TriangleDrawer` owns an `Usage.Immutable` vertex buffer of three `Vertex` structs, the `InputElementDesc[]`, the topology and `Draw(3, 0)`. `pass-through.hlsl` is an embedded resource, still passing `COLOR` straight through with `linear` interpolation. 2.8 established that the rasterizer's three barycentric weights are what turn three vertex colors into ~180,000 pixel colors.

This lesson adds exactly **one** new D3D11 object — a second `ID3D11Buffer`, bound to a different slot with a different flag — and swaps one draw call for another. That is the whole API surface. The interesting part is what the indirection buys you, why the number "4 instead of 6" is a *terrible* advertisement for it, and the one thing about indices that trips up everybody who assumes they deduplicate positions.

## Concept: what an index buffer actually is

You have two ways to tell the input assembler which vertices make up which triangles.

**Without indices** (`Draw`), the answer is "in order". The IA walks the vertex buffer from element `StartVertexLocation`, and under `TriangleList` topology it chops the stream into groups of three. Triangle 0 is elements 0,1,2; triangle 1 is elements 3,4,5. There is no way to say "reuse element 1" — if two triangles share a corner, you store that corner twice.

**With indices** (`DrawIndexed`), you add one level of indirection. You bind a second buffer holding nothing but integers, and the IA walks *that* instead. For each index it reads, it fetches the vertex at that position in the vertex buffer. The index buffer is the topology; the vertex buffer is just a pool of vertices the topology points at. Two triangles can name the same vertex, and it exists once.

That is the entire mechanism. Two buffers, one bound to `IASetVertexBuffers`, one to `IASetIndexBuffer`, and a draw call that says "read 6 indices" rather than "read 6 vertices".

### The quad, concretely

A quad is two triangles. Four corners, and the two triangles share two of them — the ends of the diagonal.

```
        0 ────────── 1          Triangle A: 0, 1, 2
        │ ╲     A    │          Triangle B: 0, 2, 3
        │   ╲        │
        │     ╲      │          Indices: [0, 1, 2,  0, 2, 3]
        │  B    ╲    │          Shared:  0 and 2 — the diagonal
        3 ────────── 2
```

Six indices, four vertices. Vertices 0 and 2 each appear twice in the index list and once in the vertex buffer.

### Why "4 instead of 6" undersells it, badly

Let us do the arithmetic honestly. `Vertex` is 20 bytes. A 16-bit index is 2 bytes.

| | Vertex bytes | Index bytes | Total |
|---|---|---|---|
| `Draw(6, 0)`, six vertices | 6 × 20 = 120 | — | **120** |
| `DrawIndexed(6, 0, 0)`, four vertices | 4 × 20 = 80 | 6 × 2 = 12 | **92** |

You saved 28 bytes and added an API call, a buffer, and a field to dispose. For one quad, indices are a net loss in complexity. Anyone who sells you index buffers on a single quad is selling you the wrong thing.

The savings are **asymptotic**, and they arrive fast. Take an N×N grid of quads — a terrain patch, a tilemap, a subdivided sprite:

- **Non-indexed:** 2 triangles per cell × 3 vertices = 6N² vertices = **120N² bytes**.
- **Indexed:** (N+1)² vertices, because interior corners are shared by four cells ≈ 20N² bytes, plus 6N² indices × 2 = 12N² bytes = **≈ 32N² bytes**.

That is a **~3.7× reduction**, and it holds for any mesh where vertices are genuinely shared. For a 100×100 grid: 1.20 MB becomes 0.32 MB. The general rule for a closed triangle mesh is that each vertex is shared by roughly six triangles, so triangle count is about twice vertex count — meaning a non-indexed version stores every vertex about six times over.

The memory is not even the main prize. The main prize is upstream of memory.

### The real prize: the vertex shader runs fewer times

`Draw(6, 0)` runs your vertex shader **six times**. Guaranteed. Six transforms, six of whatever lighting or skinning math you eventually put in there.

`DrawIndexed(6, 0, 0)` over four unique indices runs it **four times** in practice. The GPU tracks which indices it has already transformed within the draw and reuses the result instead of re-running the shader — historically a small FIFO called the *post-transform vertex cache*, and on modern hardware a vendor-specific reuse window over a batch of indices. This is why index buffers are not an optimization you consider; they are the default way meshes are drawn.

**Performance honesty, per the rules:** the exact reuse behavior is not part of the D3D11 contract and is not something you can portably predict. Two consequences worth knowing now: (1) the *order* of your indices matters, because reuse only helps if a repeated index shows up again before it falls out of the reuse window — which is why mesh optimizers reorder triangles for cache locality, and why you should never hand-reorder indices for "performance" without measuring; (2) you can measure it directly, on your own GPU, with a pipeline statistics query — `VSInvocations` versus `IAVertices`. That is 11.2's lesson, and it is Exercise 3 here because a four-vertex quad is the smallest possible experiment that shows a real difference.

### The thing that trips everyone: indices deduplicate *vertices*, not positions

This is the one misconception worth killing now, before Part 8 makes it expensive.

"A cube has 8 corners, so a cube is 8 vertices and 36 indices." That is true only if a vertex is *nothing but a position*. Add per-face normals (8.8) and each corner belongs to three faces pointing three different directions — so it needs three different vertices that happen to share a position. A cube with flat-shaded faces is **24 vertices**, not 8. Add a texture atlas (5.7) where adjacent faces sample unrelated regions and you get seams that split vertices again.

The IA fetches one index and gets one *complete vertex* — every attribute in the layout, together. Two triangles can share a vertex only when they agree on **all** of it: position, color, normal, UV, everything. The moment any attribute differs, you need two vertices.

This has a very practical consequence you will hit head-on in 8.12: the OBJ format stores **separate indices per attribute** (`f 1/5/3` means position 1, UV 5, normal 3). D3D11 has no such thing — one index stream, period. So every OBJ loader ever written does the same job: walk the faces, and for each unique *(position, UV, normal)* triple, emit one vertex and remember its number in a dictionary. You are not writing that today. You are learning now why it is unavoidable.

### 16-bit or 32-bit, and the number that will bite you

`IASetIndexBuffer` takes a `Format`, and exactly two values are legal:

- **`Format.FormatR16Uint`** — `ushort`, addresses vertices 0…65,535. Half the bandwidth.
- **`Format.FormatR32Uint`** — `uint`, addresses ~4.3 billion.

Use 16-bit until you cannot. Indices are read for every vertex of every triangle, so halving them halves real traffic on a bus that is genuinely a bottleneck for large meshes.

The number that bites: `0xFFFF` is reserved as the **strip-cut index** for strip topologies (`0xFFFFFFFF` for 32-bit), which restarts the strip rather than referencing a vertex. So treat **65,535** as your ceiling, not 65,536. A 255×255 grid of quads needs 256² = 65,536 vertices — one too many — and you will meet that exact wall the first time you build a terrain patch. Split the mesh or move to 32-bit; do not get clever.

### One slot, not an array

`IASetVertexBuffers` takes a start slot and a count because the IA has 32 vertex buffer slots — that is how per-instance data arrives in 9.4. `IASetIndexBuffer` takes no slot and no count: there is exactly **one** index buffer bound to the context at a time, with one format and one byte offset. Nothing to enumerate.

And it is sticky context state, like everything else in D3D11. Once bound it stays bound until you replace it. A plain `Draw` call issued afterwards ignores it completely — non-indexed draws do not consult the index buffer at all. That is a useful fact when you are debugging, and a trap when you forget you left one bound.

### Step 1 — Four vertices instead of three

In `QuadDrawer.CreateVertexBuffer`, replace the vertex array:

```csharp
Vertex[] vertices =
[
	new(-0.5f, 0.5f, 1f, 0f, 0f),
	new(0.5f, 0.5f, 0f, 1f, 0f),
	new(0.5f, -0.5f, 0f, 0f, 1f),
	new(-0.5f, -0.5f, 1f, 1f, 0f),
];
```

Nothing else in that method changes — `ByteWidth` is already `sizeof(Vertex) * vertices.Length`, so it follows along on its own.

Corner 0 is top-left and red, 1 top-right and green, 2 bottom-right and blue, 3 bottom-left and yellow. Clip space has **Y up** (the viewport flips it on the way to pixels), so `+0.5` is the top of the screen.

**The ordering is not arbitrary.** 0 → 1 → 2 → 3 walks the corners **clockwise on screen**. 2.8 established why that matters: you never call `RSSetState`, so you get the default rasterizer state, which culls back faces and treats clockwise as front. Wind either triangle the other way and it disappears. Your original triangle was clockwise too (top → bottom-right → bottom-left) — this is the same convention, continued.

### Step 2 — The index buffer

Add a field beside the vertex buffer:

```diff
 	private ComPtr<ID3D11Buffer> vertexBuffer;
+
+	private ComPtr<ID3D11Buffer> indexBuffer;
```

and a method that is deliberately the same shape as `CreateVertexBuffer`, so the differences stand out:

```csharp
private void CreateIndexBuffer()
{
	ushort[] indices = [0, 1, 2, 0, 2, 3];

	var bufferDescription = new BufferDesc
	{
		ByteWidth = (uint)(sizeof(ushort) * indices.Length),
		Usage = Usage.Immutable,
		BindFlags = (uint)BindFlag.IndexBuffer,
	};

	fixed (ushort* indexPointer = indices)
	{
		var initialData = new SubresourceData { PSysMem = indexPointer };

		SilkMarshal.ThrowHResult(Window.Device.CreateBuffer(in bufferDescription, in initialData, ref indexBuffer));
	}
}
```

The differences from `CreateVertexBuffer`: `BindFlag.IndexBuffer` instead of `VertexBuffer`, and `sizeof(ushort)` instead of `sizeof(Vertex)`. That is genuinely it. Same `Usage.Immutable` (the data never changes after creation, so let the driver put it in the fastest memory it has), same `SubresourceData` upload at creation, same `ThrowHResult`.

`CPUAccessFlags`, `MiscFlags` and `StructureByteStride` stay at their `0` defaults. `Usage.Immutable` *requires* `CPUAccessFlags = 0` — an immutable buffer the CPU can touch is a contradiction, and it is one of the cases D3D11 will reject outright. (Silently, until 2.10 turns on the debug layer and it starts telling you so in English.)

Then call it in `Load`, next to its sibling:

```diff
 	public void Load()
 	{
 		CreateVertexBuffer();
+		CreateIndexBuffer();
 		LoadShader();
 	}
```

### Step 3 — Bind it

```diff
 	private void BindVertexBuffer()
 	{
 		var stride = (uint)sizeof(Vertex);
 		var offset = 0u;
 
 		DeviceContext.IASetVertexBuffers(0, 1, ref vertexBuffer, ref stride, ref offset);
 	}
+
+	private void BindIndexBuffer()
+	{
+		DeviceContext.IASetIndexBuffer(indexBuffer, Format.FormatR16Uint, 0);
+	}
```

```diff
 	public void Render(double delta)
 	{
 		BindVertexBuffer();
+		BindIndexBuffer();
 		shader.Bind();
 
-		DrawTriangle();
+		DrawQuad();
 	}
```

`Format.FormatR16Uint` says "each index is a `ushort`", which must agree with the `ushort[]` you uploaded. Get this wrong and there is no error — the IA just reinterprets your bytes, reads garbage vertex numbers, and you get either nothing or a shape from another dimension. The trailing `0` is a **byte** offset into the index buffer; you are starting at the beginning.

### Step 4 — `DrawIndexed`

```diff
-	private void DrawTriangle()
+	private void DrawQuad()
 	{
 		DeviceContext.IASetPrimitiveTopology(D3DPrimitiveTopology.D3D11PrimitiveTopologyTrianglelist);
-		DeviceContext.Draw(3, 0);
+		DeviceContext.DrawIndexed(6, 0, 0);
 	}
```

Topology is unchanged: still `TriangleList`, still "every three make a triangle" — it is now every three *indices* rather than every three vertices.

```diff
 	public void Dispose()
 	{
+		indexBuffer.Dispose();
 		vertexBuffer.Dispose();
 		shader.Dispose();
 	}
```

Two COM objects, two releases. This hand-rolled discipline is what 4.3 replaces with something that can *prove* you leaked nothing (`ReportLiveDeviceObjects`). Until then, every `ComPtr<T>` field needs a matching line here, and it is on you to notice.

### Deliberately not in this lesson

- **A `Mesh` class** owning a vertex buffer, index buffer, stride and index count together. It is the obvious next abstraction and it is genuinely wrong to write today — you have one mesh. It arrives when there is a second one to justify it (Part 5).
- **`Map` / `Unmap` and dynamic buffers** — both buffers here are immutable. Geometry that changes per frame is 5.1.
- **`DrawIndexedInstanced`** — same index buffer, N copies with per-instance data. 9.4.
- **Verifying any of this with the debug layer** — next lesson, 2.10, and it is the lesson that makes every silent failure below loud.

## Per-value justification

| Value / call | Why |
|---|---|
| `ushort[] indices = [0, 1, 2, 0, 2, 3]` | Two clockwise triangles sharing the 0–2 diagonal. `ushort` because `Format.FormatR16Uint` is half the index bandwidth and four vertices is nowhere near the 65,535 ceiling. |
| Corner order 0=TL, 1=TR, 2=BR, 3=BL | Clockwise on screen. The default rasterizer state culls back faces with clockwise as front, and both triangles must agree. Counter-clockwise and the quad vanishes (8.7). |
| `BindFlag.IndexBuffer` (= 2) | Tells D3D11 this buffer will be bound to the IA's index slot. A buffer may legally carry `VertexBuffer` *and* `IndexBuffer` flags together; `ConstantBuffer` is the one flag that cannot be combined with anything else (Exercise 5). |
| `ByteWidth = sizeof(ushort) * indices.Length` = 12 | Size of the allocation in bytes. Six 2-byte indices. |
| `Usage.Immutable` | Written once at creation, GPU-read-only forever. Lets the driver place it in the fastest memory available, and requires `CPUAccessFlags = 0`. |
| `CPUAccessFlags` left at `0` | Mandatory for `Immutable`. A nonzero value here is a create-time rejection, invisible until 2.10. |
| `Format.FormatR16Uint` | The element type of the index buffer. Only this and `FormatR32Uint` are legal. Must match what you actually uploaded — a mismatch is silent garbage, not an error. |
| `0` (third argument of `IASetIndexBuffer`) | Byte offset to the first index. Zero = start of the buffer. **Bytes**, unlike `DrawIndexed`'s `StartIndexLocation`. |
| `DrawIndexed(6, …)` — `IndexCount` | How many indices to read: 6, giving two triangles under `TriangleList`. Not the vertex count. |
| `DrawIndexed(…, 0, …)` — `StartIndexLocation` | Index of the first index to read, in **elements** (not bytes — the classic off-by-N against `IASetIndexBuffer`'s offset). Lets several meshes share one index buffer. |
| `DrawIndexed(…, …, 0)` — `BaseVertexLocation` | An `int` added to every index before the vertex fetch. **Signed** on purpose, so a mesh's indices can stay 0-based while pointing anywhere inside a shared vertex buffer — including backwards. |
| `TriangleList` unchanged | Still three-at-a-time; the IA now groups indices rather than vertices. A strip would draw this quad in 4 indices, and costs you the ability to control winding per triangle (Exercise 2). |
| `0xFFFF` reserved | Strip-cut index for strip topologies. Why the practical 16-bit ceiling is 65,535 vertices, not 65,536. |

## ✅ Checkpoint

A **square** in the middle of the window, on the cycling background, with a smooth four-way color blend: red top-left, green top-right, blue bottom-right, yellow bottom-left. **Space** / **V** / **Esc** still work. `dotnet build` at **0 warnings**.

Then look closely at the diagonal running from the **top-left corner to the bottom-right corner**, and you should be able to pick out a faint **crease** — a line where the color gradient changes direction slightly.

That crease is the most informative thing on the screen, and it is not a bug. The rasterizer interpolates **linearly across a triangle** (2.8: it fits a plane, and a plane is all it has). Your quad is two triangles, so it is two planes per channel, joined along the diagonal. The values match exactly along the seam — that is why there is no visible gap or double-shaded line, courtesy of the top-left fill rule — but the *slopes* do not. A true bilinear blend across four corners is a curved (hyperbolic paraboloid) surface, and two flat triangles cannot be that. Every textured quad in every 2D engine ever shipped has this crease; it is invisible on real content and glaring on a four-color test quad, which is exactly why this is the test quad.

Exercise 1 makes it obvious rather than faint.

## 🐛 Common failure modes

1. **Nothing on screen at all.** Most likely you forgot `BindIndexBuffer()` in `Render`, or `CreateIndexBuffer()` in `Load`. An unbound index buffer means `DrawIndexed` reads from nothing. No exception, no message — D3D11 discards the draw silently. This is the single best argument for 2.10 existing.
2. **Only one triangle appears — the quad is a wedge.** Your indices are wrong. Count them: six, and the second triple must be `0, 2, 3` — reusing 0 and 2, not 2 and 3. `[0, 1, 2, 2, 3, 0]` also works (same triangles, rotated) but `[0, 1, 2, 1, 2, 3]` does not: that second triangle is TR/BR/BL, wound counter-clockwise, and gets culled.
3. **Half the quad is missing, and it is the half you did not touch.** Winding. One of your two triangles is counter-clockwise on screen and the default rasterizer state culled it. Walk each triple in order and check it goes clockwise with Y **up**. Quick confirmation: temporarily bind an `ID3D11RasterizerState` with `CullMode = CullMode.None` (2.8's Exercise 3) — if the missing half reappears, it is winding, full stop.
4. **A garbage shape, or a single stray triangle in a corner.** Format mismatch: `ushort[]` uploaded and `Format.FormatR32Uint` bound, or the reverse. Two `ushort` indices get read as one `uint`, so `[0, 1]` becomes vertex 65,536. The IA reads out of range and you get nonsense. There is no error for this.
5. **`ByteWidth` still says `sizeof(Vertex)`.** Copy-pasting `CreateVertexBuffer` and missing one word gives you a 120-byte index buffer holding 12 bytes of indices. It will actually *work* — the extra bytes are never read at `IndexCount = 6` — which makes it the kind of bug that surfaces three lessons later. Check it now.
6. **An exception out of `CreateBuffer`.** `ThrowHResult` doing its job. Nonzero `CPUAccessFlags` with `Usage.Immutable`, or `ByteWidth = 0` because you indexed an empty array. Both are create-time rejections.
7. **The quad is there but the colors are scrambled.** You reordered the fields in `Vertex`, or your corner coordinates do not match the colors you thought you assigned. Declaration order is byte layout, and `DescribeVertexLayout` hard-codes `AlignedByteOffset = 8` for `COLOR`.

## 🔧 Exercises

1. **Make the crease impossible to miss.** Set corners 0 and 2 (the two on the diagonal) to black `(0,0,0)` and corners 1 and 3 to white `(1,1,1)`. You get a sharp dark ridge along the shared diagonal with two bright corners either side — the two interpolation planes meeting at an angle, at full contrast. Now flip which diagonal the quad uses: change the indices to `[0, 1, 3, 1, 2, 3]` (both triples are still clockwise — verify that yourself before running). The four corner colors are pinned to the same four screen positions, and **the entire interior changes**, with the ridge jumping to the other diagonal. Same four vertices, same six indices, same draw call: the index buffer alone decided what surface you see. That is the lesson.
2. **Draw the same quad with four indices.** Switch to `D3D11PrimitiveTopologyTrianglestrip` and use `[0, 1, 3, 2]` with `DrawIndexed(4, 0, 0)`. A strip reuses the previous two vertices for each new triangle, so N+2 indices give N triangles — and it automatically alternates winding to keep facing consistent, which is why the index order is *not* 0,1,2,3. Fewer indices, and the strip is why. Then work out what you gave up: you no longer control winding per triangle, and stitching two unrelated strips together needs either a second draw call or the `0xFFFF` strip-cut index. Put it back on `TriangleList` afterwards — that is what the rest of the curriculum assumes.
3. **Count the vertex shader invocations.** Create an `ID3D11Query` with `QueryDesc.Query = Query.PipelineStatistics`, wrap the draw in `Begin`/`End`, then poll `GetData` into a `QueryDataPipelineStatistics` and print `IAVertices` alongside `VSInvocations`. Expect `IAVertices = 6` and `VSInvocations = 4`: six vertices requested, four actually transformed — the reuse from the Concept section, measured on your own GPU. Then temporarily switch back to a non-indexed `Draw(6, 0)` with six duplicated vertices and watch `VSInvocations` become 6. This is 11.2's material arriving early on purpose — a four-vertex quad is the smallest experiment where the number is unambiguous, and a hard number beats a paragraph. (`GetData` returns `S_FALSE` while the GPU is still behind; do not treat that as failure.)
4. **Get the index into the shader anyway.** Add `uint id : SV_VertexID;` to `vertex_input` in `pass-through.hlsl` — a system value, so there is **no** `InputElementDesc` for it; the IA supplies it. Output `float3(input.id / 3.0f, 0, 0)` as the color and you get four distinct red steps, one per corner: your own vertex numbering, read straight off the screen. Note what `SV_VertexID` reports under `DrawIndexed` — the **index value** plus `BaseVertexLocation`, not the draw's iteration count. Then set `BaseVertexLocation` to `1` and watch the quad shift: index 3 + 1 = 4 now reads off the end of a four-vertex buffer. Find out what your driver does about that. It is not defined, and 2.10 will have an opinion.
5. **One buffer, both jobs.** Build a single `ID3D11Buffer` with `BindFlags = (uint)(BindFlag.VertexBuffer | BindFlag.IndexBuffer)`, containing the four vertices followed by the six indices. Bind it to both slots, passing the byte offset of the index data (`sizeof(Vertex) * 4` = 80) as `IASetIndexBuffer`'s third argument. This is roughly how real engines pack geometry — one allocation, many meshes, offsets into it — and it is why `StartIndexLocation` and `BaseVertexLocation` exist at all. Mind the two units: `IASetIndexBuffer`'s offset is bytes, `DrawIndexed`'s `StartIndexLocation` is elements. Getting those confused is a rite of passage; do it here, where the whole buffer is 92 bytes and you can reason about every one of them.
