# Lesson 2.5 — Compiling HLSL, Reading the Error Blob, and Creating the Shader Objects

> Part 2 — The Pipeline and the First Triangle
> *Compiling with `D3DCompile`, reading the error blob, and creating the shader objects (do this now, thank yourself forever)*

**Where you already are:** `FirmamentWindow` stands up the device / context / swap chain, clears to a time-interpolated color, holds an immutable vertex buffer (three vertices), and describes the vertex layout as an `InputElementDesc[]` — bound each frame in `BindVertexBuffer`. As of 2.4 the HLSL for both pipeline stages exists as text. This lesson turns that text into three GPU objects — a vertex shader, a pixel shader, and the input layout that's been blocked since 2.3 — and gives you a readable compiler error the first time your HLSL is wrong (which will be soon, and often).

Still no triangle. Binding those objects to the pipeline and calling `Draw` is 2.6. This lesson's deliverable is: the solution references a shader compiler, `OnLoad` produces `vertexShader`, `pixelShader`, and `inputLayout` without throwing, and a deliberately broken shader prints the compiler's actual complaint instead of a black screen. That's the payoff the parenthetical in the curriculum line is promising — the hour you don't spend later staring at nothing.

## Divergences from your committed code — read this first, it's big

2.4 told you to paste a `const string ShaderSource` into `FirmamentWindow`. **You didn't, and you did something better.** Your committed code has:

- `Firmament.Core/Shaders/pass-through.hlsl` — the same two stages from 2.4, as a real `.hlsl` file, embedded into the assembly (`<EmbeddedResource Include="**\*.hlsl" />` in `Firmament.Core.csproj`).
- `IShaderLoader` / `ShaderLoader` — reads that embedded resource's text through `FatCat.Toolkit`'s `IEmbeddedResourceRepository`, caches it in an `IFatCatCache<ShaderCacheItem>`, and hands back the source string via `GetShaderSource("pass-through")`.
- `PreLoadShaders()` in `OnLoad`, which resolves `IShaderLoader` from `SystemScope.Container` and calls `PreLoadShader("pass-through")` to warm that cache before any device work.

This is genuinely ahead of where the doc left you — it's the front half of **lesson 2.7** ("compile from file"). Keep it. Two things follow from it:

1. **The source comes from the loader, not a field.** This lesson calls `loader.GetShaderSource("pass-through")` to get the HLSL text, then compiles it. `PreLoadShaders` already put it in the cache, so that call is a cache hit.
2. **Your entry points and identifiers are named differently than the 2.4 doc.** Your `.hlsl` declares `vertex_main` / `pixel_main` (snake_case), structs `vertex_input` / `vertex_output`, fields `position` / `color`. The doc used `VertexMain` / `PixelMain`. **This matters** — `D3DCompile` compiles *one named function*, so the strings you pass must be **your** names. Everything below uses `vertex_main` / `pixel_main`. If you rename them in the `.hlsl`, rename them here too.

What has **not** changed: the *semantics* in your `.hlsl` — `POSITION`, `COLOR`, `SV_POSITION`, `SV_TARGET` — still match the `InputElementDesc[]` from 2.3. That match is exactly what `CreateInputLayout` validates this lesson.

**On where the compile code lives:** it goes into `FirmamentWindow` as private methods, right next to `CreateVertexBuffer`. It does **not** go into `ShaderLoader`. The loader's job is *source text*; teaching it about the D3D device and bytecode would fold lesson 2.7's `Shader` class into it early and drag the graphics device into a text-loading service. Compile in the window for now; 2.7 extracts a proper `Shader` type. Staying in scope is the whole point.

## Concept: HLSL is source code, and the GPU can't run source code

The string in your `.hlsl` file is as inert to the GPU as a `.c` file is to a CPU. A GPU executes its own vendor-specific machine code, and every vendor's is different — NVIDIA, AMD, and Intel share no instruction set. So D3D11 uses a two-step compile:

1. **Offline-ish, in your process:** `D3DCompile` turns HLSL text into **DXBC** — DirectX Bytecode. This is a portable, vendor-neutral intermediate format, the same idea as .NET IL or JVM bytecode. It is *not* GPU machine code yet. This is the step you write today.
2. **At `CreateVertexShader` time:** the driver takes that DXBC and JIT-compiles it the rest of the way to *its* GPU's actual instructions, producing an `ID3D11VertexShader` you can bind. That final translation is the driver's job and you never see it.

So "compiling a shader" is two hops: **HLSL → DXBC** (the compiler) and **DXBC → GPU ISA** (the driver, inside `CreateVertexShader` / `CreatePixelShader`). Today you do the first hop yourself and hand the result to the device for the second.

The compiler's output is a **blob** — `ID3D10Blob`, a dumb `{ pointer, byteCount }` container D3D uses wherever it returns a variable-length chunk of bytes it owns. `D3DCompile` fills in *two* blobs: one for the bytecode on success, and a separate one for **error text** on failure. It's a COM API, so it doesn't throw — it returns an `HRESULT` and you inspect it. When compilation fails, the bytecode blob is null and the error blob holds a compiler message with a line number, the same text `fxc` would print. Reading that blob is the single highest-leverage thing in this lesson: the difference between *"error X3018: 'positon': undeclared identifier"* and a silent black screen you debug for an hour.

### Why the input layout has been waiting for this exact byte array

Back in 2.3 you built the `InputElementDesc[]` but couldn't call `CreateInputLayout`, because its third argument is *compiled vertex-shader bytecode*. Now you see why it's not being fussy. D3D reads the **input signature** baked into your vertex shader's DXBC — the list of semantics `vertex_main` actually declared it consumes (`POSITION`, `COLOR`) — and checks your description against it. Describe a `NORMAL` the shader never asked for, or misspell `POSITION`, and the call fails *now*, at load, with `E_INVALIDARG`, instead of feeding the shader garbage at draw time. The bytecode is the contract; the input layout is validated against it. This is also the moment your 2.4 semantic-name encoding gets tested for real — if those `byte*` names didn't marshal as clean ANSI `"POSITION"` / `"COLOR"`, this is the call that rejects them.

## Steps — what to write and where

### Step 1 — Reference the shader compiler

`D3DCompile` lives in a package you don't reference yet. Add it to `Firmament.Core.csproj`, matching your other Silk.NET packages at **2.23.0**:

```xml
<PackageReference Include="Silk.NET.Direct3D.Compilers" Version="2.23.0" />
```

That package is the managed wrapper over `d3dcompiler_47.dll`, which ships with Windows — no redistributable to bundle.

### Step 2 — Add the fields

Three COM objects survive past load and get bound in 2.6, so they're fields (like `vertexBuffer`). Next to the existing `vertexBuffer` / `vertexLayoutDescription`:

```csharp
	private ComPtr<ID3D11VertexShader> vertexShader;
	private ComPtr<ID3D11PixelShader> pixelShader;
	private ComPtr<ID3D11InputLayout> inputLayout;
```

And the imports at the top — `ID3D10Blob`, `ID3DInclude`, and `NativeStringEncoding` are already covered by your `using Silk.NET.Core.Native;`; you need the compiler namespace and `Encoding`:

```csharp
using System.Text;
using Silk.NET.Direct3D.Compilers;
```

### Step 3 — Compile one entry point, and actually read the error

This is the method that earns the lesson. It compiles a single named function to a bytecode blob, and on failure throws with the compiler's own message instead of a bare HRESULT:

```csharp
	private ComPtr<ID3D10Blob> CompileShader(D3DCompiler compiler, string source, string entryPoint, string target)
	{
		ComPtr<ID3D10Blob> bytecode = default;
		ComPtr<ID3D10Blob> errors = default;
		var sourceBytes = Encoding.ASCII.GetBytes(source);

		fixed (byte* sourcePointer = sourceBytes)
		{
			var result = compiler.Compile(
				sourcePointer,
				(nuint)sourceBytes.Length,
				(byte*)null,
				null,
				ref Unsafe.NullRef<ID3DInclude>(),
				entryPoint,
				target,
				0,
				0,
				ref bytecode,
				ref errors
			);

			if (result < 0)
			{
				throw new InvalidOperationException(DescribeCompileFailure(entryPoint, result, errors));
			}
		}

		errors.Dispose();

		return bytecode;
	}

	private string DescribeCompileFailure(string entryPoint, int result, ComPtr<ID3D10Blob> errors)
	{
		if (errors.Handle is null)
		{
			return $"Compiling '{entryPoint}' failed with HRESULT 0x{result:X8} and produced no error text.";
		}

		var message = SilkMarshal.PtrToString((nint)errors.GetBufferPointer(), NativeStringEncoding.LPStr);

		errors.Dispose();

		return $"Compiling '{entryPoint}' failed: {message}";
	}
```

Read the shape against the concept:

- **`ref Unsafe.NullRef<ID3DInclude>()`** and the two `null`s say "no `#include` handler, no `#define` macros, no source filename." You have none of those. The filename only ever appears inside error messages, so passing null just means messages say `(null)` instead of `pass-through.hlsl` — cosmetic today.
- **`entryPoint` / `target` as plain `string`s.** Silk.NET has an overload that marshals these for you, so — unlike the semantic names in 2.3 — there's no manual `StringToPtr`/`Free` to babysit here. `target` is the *shader profile*: `vs_5_0` or `ps_5_0`.
- **`result < 0`** is the failure test. An `HRESULT` is negative exactly when its top bit is set, which is the COM convention for failure. Don't wrap this in `SilkMarshal.ThrowHResult` — that throws before you can read `errors`, which defeats the entire point.
- **The bytecode blob is returned, not disposed.** The caller needs it to create the shader (and, for the vertex shader, the input layout). The *errors* blob is disposed on both paths — it's non-null even on some successful compiles (warnings).

### Step 4 — Turn bytecode into device objects

```csharp
	private void CreateShaders()
	{
		var loader = SystemScope.Container.Resolve<IShaderLoader>();
		var source = loader.GetShaderSource("pass-through");
		var compiler = D3DCompiler.GetApi();

		var vertexBytecode = CompileShader(compiler, source, "vertex_main", "vs_5_0");
		var pixelBytecode = CompileShader(compiler, source, "pixel_main", "ps_5_0");

		SilkMarshal.ThrowHResult(
			device.CreateVertexShader(
				vertexBytecode.GetBufferPointer(),
				vertexBytecode.GetBufferSize(),
				ref Unsafe.NullRef<ID3D11ClassLinkage>(),
				ref vertexShader
			)
		);

		SilkMarshal.ThrowHResult(
			device.CreatePixelShader(
				pixelBytecode.GetBufferPointer(),
				pixelBytecode.GetBufferSize(),
				ref Unsafe.NullRef<ID3D11ClassLinkage>(),
				ref pixelShader
			)
		);

		CreateInputLayout(vertexBytecode);

		vertexBytecode.Dispose();
		pixelBytecode.Dispose();
		compiler.Dispose();
	}
```

`SilkMarshal.ThrowHResult` is right *here* — a device that rejects valid DXBC is an unexpected failure with nothing readable to add, so throwing is the honest response. That's the split the error-handling rules ask for: read-and-report where there's a message to read (compilation), throw where there isn't (`CreateVertexShader`).

The blobs are disposed the moment the objects are made — the driver has already JIT'd the DXBC into the shader object and copied what it needs. `GetShaderSource` is a cache hit off `PreLoadShaders`, so resolving the loader again is cheap; 2.7 tidies the double resolve away when the `Shader` class owns this.

### Step 5 — The call that's been blocked since 2.3

```csharp
	private void CreateInputLayout(ComPtr<ID3D10Blob> vertexBytecode)
	{
		SilkMarshal.ThrowHResult(
			device.CreateInputLayout(
				ref vertexLayoutDescription[0],
				(uint)vertexLayoutDescription.Length,
				vertexBytecode.GetBufferPointer(),
				vertexBytecode.GetBufferSize(),
				ref inputLayout
			)
		);
	}
```

`ref vertexLayoutDescription[0]` hands D3D the address of the first element; `NumElements` tells it how many contiguous descriptions follow. The **vertex** bytecode — never the pixel — because it's the vertex shader that has an input signature to validate against. This is the one call that consumes the semantic names you allocated in 2.3; if it returns `E_INVALIDARG`, the fault is a name/format/offset mismatch between description and shader, not anything in this method.

### Step 6 — Wire into `OnLoad` and `Dispose`

In `OnLoad`, immediately after `DescribeVertexLayout();`:

```csharp
		CreateShaders();
```

Order matters: the device must exist (it does — it's created earlier in `OnLoad`), and `vertexLayoutDescription` must be populated (it is, one line up). In `Dispose`, add the three objects next to `vertexBuffer.Dispose();`, newest-created first:

```csharp
		inputLayout.Dispose();
		pixelShader.Dispose();
		vertexShader.Dispose();
```

## Per-value justification

| Value | Why |
|---|---|
| `Silk.NET.Direct3D.Compilers` @ `2.23.0` | Managed wrapper over `d3dcompiler_47.dll` (ships with Windows). Version-matched to your other Silk.NET packages so the shared `Silk.NET.Core` resolves to one version. |
| `Encoding.ASCII.GetBytes(source)` | `D3DCompile` reads source as raw bytes, not a .NET string. HLSL is ASCII, so ASCII avoids any BOM/multibyte surprise a UTF encoding could prepend. |
| `(nuint)sourceBytes.Length` | Byte count of the source. `nuint` because the native parameter is a pointer-width `SIZE_T`. |
| `(byte*)null` (source name) | No filename. Only ever surfaces inside error messages; null just means messages omit it. |
| `null` (defines) | No `#define` macros passed to the compiler. |
| `ref Unsafe.NullRef<ID3DInclude>()` | No `#include` resolver. Your shader includes nothing; this is the idiomatic Silk.NET way to pass a null COM ref. |
| `"vertex_main"` / `"pixel_main"` | **Your** entry-point function names from `pass-through.hlsl`. `D3DCompile` compiles one named function per call. |
| `"vs_5_0"` / `"ps_5_0"` | Shader Model 5.0 profiles — the target for D3D11 feature level 11_0. `vs` = vertex stage, `ps` = pixel stage. |
| `0` (Flags1) | Default codegen — no debug info, default optimization. Debug flags are exercise 3. |
| `0` (Flags2) | Effect (`.fx`) compilation flags. You're not compiling an effect, so 0. |
| `result < 0` | HRESULT failure test (top bit set = failure). Deliberately *not* `ThrowHResult`, so the error blob can be read first. |
| `errors.Handle is null` | The error blob can legitimately be null (a clean compile). Guard before dereferencing it. |
| `NativeStringEncoding.LPStr` | The compiler writes its message as a single-byte ANSI C string; `LPStr` reads it back as one. |
| `GetBufferPointer()` / `GetBufferSize()` | The blob's `{ pointer, byteCount }`. Together they *are* the DXBC handed to the device. |
| `ref Unsafe.NullRef<ID3D11ClassLinkage>()` | No dynamic shader linkage (a rarely-used D3D11 feature). Null. |
| `ref vertexLayoutDescription[0]` + count | Address of the first `InputElementDesc` and how many follow — D3D reads them as a contiguous array. |
| vertex bytecode into `CreateInputLayout` | Only the vertex shader carries an input signature to validate the layout against. Passing pixel bytecode is an error. |
| Blobs disposed right after object creation | The driver has JIT'd and copied what it needs; the DXBC bytes are no longer referenced. |

## 🐛 Common failure modes

1. **`SystemScope.Container` can't resolve `IShaderLoader`, or `GetShaderSource` returns empty.** The compiler then rejects an empty source. Confirm `PreLoadShaders()` still runs in `OnLoad` and that `pass-through.hlsl` is still marked as an `EmbeddedResource` (the `<EmbeddedResource Include="**\*.hlsl" />` item) — if the build action reverted to `None`, the resource isn't in the assembly and the loader reads nothing.
2. **`E_INVALIDARG` (`0x80070057`) out of `CreateInputLayout`.** Description vs shader mismatch: a semantic name that doesn't match (spelling, or the 2.4 encoding trap producing `"P"`/`"C"` instead of `"POSITION"`/`"COLOR"`), a format that doesn't fit the declared type, or an element the shader never declared. The bytecode is the source of truth; fix the `InputElementDesc[]` or the `.hlsl` to agree.
3. **Entry point / profile mismatch → `D3DCompile` fails with `error X3501: 'VertexMain': entrypoint not found`.** You passed a name the `.hlsl` doesn't define. Your functions are `vertex_main` / `pixel_main` — pass those, or an `X3501` names the function it couldn't find.
4. **You called `ThrowHResult` around `Compile` and now every shader typo is an opaque `0x80004005`.** That throws before `DescribeCompileFailure` can read the blob. Keep the `result < 0` check on the compile; reserve `ThrowHResult` for the device calls, which have no message to read.
5. **Access violation reading the error blob.** Dereferencing `errors` when it's null (a clean compile still enters some code paths). The `errors.Handle is null` guard exists for exactly this — don't remove it.
6. **`CompileShader` runs before the device exists.** If you called `CreateShaders()` too early in `OnLoad`, `CreateVertexShader` faults on a null device. It must come after device creation — placing it right after `DescribeVertexLayout();` satisfies that.

## 🔧 Exercises

1. **Read a real error, then a real warning.** Break the shader two ways: an *error* (misspell an identifier) and a *warning* (declare a local you never use, or force an implicit truncation like assigning a `float4` to a `float3`). Confirm the error throws with `X3018`-style text, and that the warning still compiles but leaves `errors` non-null — print the warning text without throwing. This is the whole reason the blob is separate from the return code.
2. **Prove the layout is validated against bytecode.** Add `float2 uv : TEXCOORD;` to `vertex_input` in the `.hlsl` and recompile — it builds. Now watch `CreateInputLayout` still succeed (your description doesn't mention `TEXCOORD`, and unused *shader inputs* are allowed to go unfed... or are they?). Then instead add a third `InputElementDesc` for `TEXCOORD` to `vertexLayoutDescription` *without* the shader declaring it, and see which direction actually trips `E_INVALIDARG`. Write down the rule you just discovered about which side may have extras.
3. **Turn on debug shaders.** Pass `Flags1 = D3DCOMPILE_DEBUG | D3DCOMPILE_SKIP_OPTIMIZATION` (`0x1 | 0x4`) when compiling. Nothing visibly changes now, but this is what makes shader source and variable names show up in a RenderDoc/PIX capture (Part 11). Gate it behind `#if DEBUG` so release builds get optimized bytecode, and note in a comment why the two flags travel together (optimized code has no stable line mapping to debug against).
4. **Time the compile.** Wrap the two `CompileShader` calls in a `Stopwatch` and log the milliseconds once. You'll see why real engines compile shaders offline into `.cso` files and ship the DXBC, not the HLSL — and why 4.4's hot-reload only pays for itself because it recompiles *one* shader on a file change, not all of them every frame. (Don't leave the log in; per the logging rules, remove the trace before committing.)
