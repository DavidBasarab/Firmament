# Lesson 2.7 — A `Shader` Class: Own the Compile, the Input Layout, and the Release

> Part 2 — The Pipeline and the First Triangle
> *A `Shader` class: compile from file, hold the input layout, release COM objects properly*

**Where you already are:** the triangle draws. Since 2.6 you pulled everything game-shaped out of `FirmamentWindow` and into `Firmament.Asteroids2D/Learning/`: `LearningGame` owns the window and wires its events, `ColorShifter` cycles the clear color, `TitleReporter` owns the title bar, and `TriangleDrawer` owns *all* of the Part 2 GPU work — the immutable vertex buffer, the `InputElementDesc[]` (with its unmanaged semantic-name strings), the two `D3DCompile` calls, `CreateVertexShader` / `CreatePixelShader` / `CreateInputLayout`, and the per-frame bind + `Draw(3, 0)`. `FirmamentWindow` is back to being a window: device, context, swap chain, render target view, viewport, input, `Present`. That split is the right shape, and it's what makes this lesson small.

This lesson takes the middle of `TriangleDrawer` — everything between "I have HLSL text" and "the pipeline has shaders bound" — and moves it into one class in `Firmament.Core` that owns those three COM objects for their whole life. Nothing new appears on screen. The deliverable is the same triangle, a `TriangleDrawer` that reads as *buffer + topology + draw*, a build with zero warnings, and an exit that releases exactly what it created, exactly once.

---

## Divergences from your committed code — read first

- **2.6 said the compile machinery lived in `FirmamentWindow`. It doesn't anymore — it's in `TriangleDrawer`.** This lesson refactors `TriangleDrawer` and touches one line of `LearningGame`. `FirmamentWindow` is not edited.
- **"Compile from file" is already half done, and 2.5 flagged it.** `pass-through.hlsl` is an embedded resource read through `IShaderLoader`. Keep it — but hear this now, per rule 10: an *embedded* resource is baked into `Firmament.Core.dll` at build time. **4.4's shader hot-reload cannot work against it** — there's no file on disk to watch, and `ShaderLoader` caches the text forever. When 4.4 arrives, the loader grows a "from disk, uncached, in Debug" path. Not today; today the `Shader` class only ever asks the loader for a string, so that swap will be invisible to it.
- **`TriangleDrawer` has two public teardown entry points.** `CleanUp()` releases everything, and `Dispose()` calls `CleanUp()`. `LearningGame.OnCleanUp` calls `CleanUp()`. If anything ever also disposes the drawer — a `using`, a container, a future resource manager — every COM object gets released **twice**. The Concept section explains exactly why that's not a harmless no-op with Silk.NET's `ComPtr<T>`. This lesson collapses it to one entry point.
- **`VSSetShader` / `PSSetShader` now pass `(ID3D11ClassInstance**)null`.** A bare `null` there resolves to the `ref readonly ID3D11ClassInstance*` overload, so the compiler materializes a temporary and passes *its address* — a non-null pointer to a null — and warns with `CS9193`. The typed null picks the raw-pointer overload, which is both warning-free and what the D3D docs actually ask for. That fix is already in your committed `TriangleDrawer`; the new `Bind` carries it over unchanged.
- **The `ConsoleLog` traces** in `CompileShader` / `CreateShaders` / `PreLoadShaders` — 2.6 flagged them; the `Shader` class below does not carry them over. Re-add any you want; they run once at load so they're not per-frame noise.

## Concept: what a "shader" is as an object, and who owns the input layout

To D3D11 there is no such thing as a shader *program*. There's a vertex-shader object and a separate pixel-shader object, and they know nothing about each other. The pairing that makes them "a shader" in the everyday sense is entirely your convention: same `.hlsl` file, `vertex_main` + `pixel_main`, a shared `vertex_output` struct that keeps the two signatures honest (2.4). A `Shader` class is where that convention gets a name.

**Why the input layout lives here and not on `Vertex`.** It's tempting to think the layout describes your vertex struct — and the `InputElementDesc[]` does. But the `ID3D11InputLayout` *object* is not that description. It's the result of `CreateInputLayout` checking the description against the **vertex shader's input signature**, which is why the call takes the vertex bytecode. The layout is a validated contract between one vertex format and one vertex shader. Recompile the vertex shader with a different `vertex_input` and the layout must be rebuilt. So the object that owns the vertex shader owns the layout — the thing that can invalidate it is the thing holding it. The *description* stays with the drawable that knows its vertex format; it's passed in at load and the shader doesn't keep it.

**What does *not* belong here: topology.** `IASetPrimitiveTopology` says how the *mesh's* vertices group into primitives. The same shader draws a triangle list today and a line list in 5.1. Topology stays next to `Draw`, with the buffer.

**Releasing COM objects, the short version (4.3 is the long one).** Every `Create*` hands you an object with reference count 1 that you own. `Release` decrements; at zero the runtime destroys it and the driver reclaims the GPU memory. Silk.NET's `ComPtr<T>` looks like a smart pointer but is a plain struct around a raw pointer, and two facts about it decide how you write `Dispose`:

1. `ComPtr<T>.Dispose()` is literally `Release()` — and **`Handle` is not cleared** afterward (only `Detach()` clears it; this is verified against the 2.23.0 IL, not assumed). A second `Dispose()` on the same struct calls `Release` on an object whose count may already be zero. Best case the debug layer (2.10) screams; worst case a still-bound object is destroyed under the pipeline, or you get an access violation at exit.
2. Copying a `ComPtr<T>` — assigning it, passing it by value, returning it from a property — **does not `AddRef`**. It's a struct copy of a pointer. Two copies, two `Dispose` calls, one object: same double-release.

So the rule that falls out: **one owner, one `Dispose`, made idempotent.** The `Shader` owns its three objects, releases them once, and guards against being told twice. Order matters too: everything created *from* the device must be released *before* the device. Your `FirmamentWindow.Dispose` already fires `CleanUp` before it disposes the context and device, so game-side objects die first — correct, and worth knowing it's deliberate.

## Steps — what to write and where

### Step 1 — New file: `Firmament.Core/Shaders/Shader.cs`

Same folder and namespace as `ShaderLoader`. The compile and error-blob code is 2.5's, moved and split so each stage owns its own bytecode blob's lifetime.

```csharp
using System.Runtime.CompilerServices;
using System.Text;
using Silk.NET.Core.Native;
using Silk.NET.Direct3D.Compilers;
using Silk.NET.Direct3D11;

namespace Firmament.Core.Shaders;

public unsafe class Shader(FirmamentWindow window, IShaderLoader loader, string shaderName) : IDisposable
{
	private const string PixelEntryPoint = "pixel_main";
	private const string PixelTarget = "ps_5_0";
	private const string VertexEntryPoint = "vertex_main";
	private const string VertexTarget = "vs_5_0";

	private ComPtr<ID3D11InputLayout> inputLayout;
	private bool isDisposed;
	private ComPtr<ID3D11PixelShader> pixelShader;
	private ComPtr<ID3D11VertexShader> vertexShader;

	public void Bind()
	{
		window.DeviceContext.IASetInputLayout(inputLayout);
		window.DeviceContext.VSSetShader(vertexShader, (ID3D11ClassInstance**)null, 0);
		window.DeviceContext.PSSetShader(pixelShader, (ID3D11ClassInstance**)null, 0);
	}

	public void Dispose()
	{
		if (isDisposed)
		{
			return;
		}

		isDisposed = true;

		inputLayout.Dispose();
		pixelShader.Dispose();
		vertexShader.Dispose();
	}

	public void Load(InputElementDesc[] vertexLayout)
	{
		var source = loader.GetShaderSource(shaderName);
		var compiler = D3DCompiler.GetApi();

		try
		{
			LoadVertexStage(compiler, source, vertexLayout);
			LoadPixelStage(compiler, source);
		}
		finally
		{
			compiler.Dispose();
		}
	}

	private ComPtr<ID3D10Blob> Compile(D3DCompiler compiler, string source, string entryPoint, string target)
	{
		var sourceBytes = Encoding.ASCII.GetBytes(source);

		ComPtr<ID3D10Blob> byteCode = default;
		ComPtr<ID3D10Blob> errors = default;

		try
		{
			fixed (byte* sourcePointer = sourceBytes)
			{
				var result = compiler.Compile(
					sourcePointer,
					(nuint)sourceBytes.Length,
					(byte*)null,
					null,
					ref Unsafe.NullRef<ID3DInclude>(),
					entryPoint,
					target,
					0,
					0,
					ref byteCode,
					ref errors
				);

				if (result < 0)
				{
					throw new InvalidOperationException(DescribeCompileFailure(entryPoint, result, errors));
				}
			}
		}
		finally
		{
			errors.Dispose();
		}

		return byteCode;
	}

	private string DescribeCompileFailure(string entryPoint, int result, ComPtr<ID3D10Blob> errors)
	{
		if (errors.Handle is null)
		{
			return $"Compiling `{shaderName}` `{entryPoint}` failed with HRESULT 0x{result:x8} and produced no error text.";
		}

		var message = SilkMarshal.PtrToString((nint)errors.GetBufferPointer());

		return $"Compiling `{shaderName}` `{entryPoint}` failed: {message}";
	}

	private void LoadPixelStage(D3DCompiler compiler, string source)
	{
		var byteCode = Compile(compiler, source, PixelEntryPoint, PixelTarget);

		try
		{
			SilkMarshal.ThrowHResult(
				window.Device.CreatePixelShader(
					byteCode.GetBufferPointer(),
					byteCode.GetBufferSize(),
					ref Unsafe.NullRef<ID3D11ClassLinkage>(),
					ref pixelShader
				)
			);
		}
		finally
		{
			byteCode.Dispose();
		}
	}

	private void LoadVertexStage(D3DCompiler compiler, string source, InputElementDesc[] vertexLayout)
	{
		var byteCode = Compile(compiler, source, VertexEntryPoint, VertexTarget);

		try
		{
			SilkMarshal.ThrowHResult(
				window.Device.CreateVertexShader(
					byteCode.GetBufferPointer(),
					byteCode.GetBufferSize(),
					ref Unsafe.NullRef<ID3D11ClassLinkage>(),
					ref vertexShader
				)
			);

			SilkMarshal.ThrowHResult(
				window.Device.CreateInputLayout(
					ref vertexLayout[0],
					(uint)vertexLayout.Length,
					byteCode.GetBufferPointer(),
					byteCode.GetBufferSize(),
					ref inputLayout
				)
			);
		}
		finally
		{
			byteCode.Dispose();
		}
	}
}
```

Two shape decisions to be honest about:

- **It takes `FirmamentWindow`, not a device.** `Load` needs the device and `Bind` needs the context, and today the window is the only thing that has both. A shader knowing about a *window* is a smell; 4.1 (engine vs game) is where the device grows its own home and this constructor changes. Said now so it isn't a surprise.
- **`IShaderLoader` is injected, not resolved inside.** That's the repo's constructor-injection rule. The `Factory.Get<IShaderLoader>()` moves to the one place a `Shader` is constructed — and there's now exactly one loader lookup instead of 2.5's two (that's the "double resolve" 2.5 promised this lesson would tidy).

### Step 2 — Rewrite `TriangleDrawer` around it

This is most of the file, so here it is in full. Everything compile-related is gone; what's left is a vertex buffer, the description of its layout, a topology, and a draw call.

```csharp
using Firmament.Core;
using Firmament.Core.Shaders;
using Firmament.Core.Types;
using Silk.NET.Core.Native;
using Silk.NET.Direct3D11;
using Silk.NET.DXGI;

namespace Firmament.Asteroids2D.Learning;

public unsafe class TriangleDrawer(LearningGame game) : IDisposable
{
	private readonly List<nint> unmanagedSemanticNames = [];

	private Shader shader;
	private ComPtr<ID3D11Buffer> vertexBuffer;

	private FirmamentWindow Window { get; } = game.Window;

	public void Dispose()
	{
		vertexBuffer.Dispose();
		shader.Dispose();
	}

	public void Load()
	{
		CreateVertexBuffer();
		LoadShader();
	}

	public void Render(double delta)
	{
		BindVertexBuffer();
		shader.Bind();

		DrawTriangle();
	}

	private byte* AllocatedSemanticName(string semanticName)
	{
		var pointer = SilkMarshal.StringToPtr(semanticName);

		unmanagedSemanticNames.Add(pointer);

		return (byte*)pointer;
	}

	private void BindVertexBuffer()
	{
		var stride = (uint)sizeof(Vertex);
		var offset = 0u;

		Window.DeviceContext.IASetVertexBuffers(0, 1, ref vertexBuffer, ref stride, ref offset);
	}

	private void CreateVertexBuffer()
	{
		Vertex[] vertices = [new(0.0f, 0.5f, 1f, 0f, 0f), new(0.5f, -0.5f, 0f, 1f, 0f), new(-0.5f, -0.5f, 0f, 0f, 1f)];

		var bufferDescription = new BufferDesc
		{
			ByteWidth = (uint)(sizeof(Vertex) * vertices.Length),
			Usage = Usage.Immutable,
			BindFlags = (uint)BindFlag.VertexBuffer,
		};

		fixed (Vertex* vertexPtr = vertices)
		{
			var initialData = new SubresourceData { PSysMem = vertexPtr };

			SilkMarshal.ThrowHResult(Window.Device.CreateBuffer(in bufferDescription, in initialData, ref vertexBuffer));
		}
	}

	private InputElementDesc[] DescribeVertexLayout()
	{
		return
		[
			new InputElementDesc
			{
				SemanticName = AllocatedSemanticName("POSITION"),
				SemanticIndex = 0,
				Format = Format.FormatR32G32Float,
				InputSlot = 0,
				AlignedByteOffset = 0,
				InputSlotClass = InputClassification.PerVertexData,
				InstanceDataStepRate = 0,
			},
			new InputElementDesc
			{
				SemanticName = AllocatedSemanticName("COLOR"),
				SemanticIndex = 0,
				Format = Format.FormatR32G32B32Float,
				InputSlot = 0,
				AlignedByteOffset = 8,
				InputSlotClass = InputClassification.PerVertexData,
				InstanceDataStepRate = 0,
			},
		];
	}

	private void DrawTriangle()
	{
		Window.DeviceContext.IASetPrimitiveTopology(D3DPrimitiveTopology.D3D11PrimitiveTopologyTrianglelist);
		Window.DeviceContext.Draw(3, 0);
	}

	private void FreeSemanticNames()
	{
		foreach (var semanticName in unmanagedSemanticNames)
		{
			SilkMarshal.Free(semanticName);
		}

		unmanagedSemanticNames.Clear();
	}

	private void LoadShader()
	{
		shader = new Shader(Window, Factory.Get<IShaderLoader>(), "pass-through");

		try
		{
			shader.Load(DescribeVertexLayout());
		}
		finally
		{
			FreeSemanticNames();
		}
	}
}
```

What changed and why, beyond the obvious move:

- **`CleanUp()` is gone; `Dispose()` is the one teardown.** Buffer first, then shader — the reverse of creation, which is the habit to build even though these two don't depend on each other.
- **The semantic-name strings are freed right after `Load`, not at teardown.** `CreateInputLayout` copies everything it needs out of the description into the `ID3D11InputLayout` object — D3D11 never keeps a pointer into caller memory past a `Create*` call. Once `Load` returns those strings are dead weight, and holding unmanaged memory for the whole run "just in case" is the kind of thing 4.3's leak report would make you explain. `finally` so a compile failure doesn't leak them either.
- **`PreLoadShaders()` is gone.** It existed to warm the loader's cache one call before the compile read it. Now the `Shader` reads it once. `IShaderLoader.PreLoadShader` is therefore unused — leave it if you want a load-screen hook later, delete it if unused code bugs you; either is fine.
- **`DescribeVertexLayout` returns the array instead of storing it.** The drawer never needs it after `Load`; the shader doesn't keep it either. Nothing holds the description once the layout object exists.

## Per-value justification

| Value / call | Why |
|---|---|
| `(ID3D11ClassInstance**)null` in `VSSetShader` / `PSSetShader` | Selects the raw-pointer overload so D3D receives an actual `NULL` for `ppClassInstances` — the documented value for "this shader uses no interfaces." A bare `null` resolves to the `ref readonly` overload, which passes the *address of a temporary* (non-null → null) and earns `CS9193`. Count stays `0`. |
| `isDisposed` guard | `ComPtr<T>.Dispose()` = `Release()` with `Handle` left dangling (2.23.0 IL). Without the guard, a second `Dispose` is a second `Release` on a possibly-destroyed object. Cheapest insurance in the codebase. |
| Release order `inputLayout` → `pixelShader` → `vertexShader` | Reverse of creation. Nothing here *requires* it (these three don't reference each other), but the discipline is free and it's the order that matters once objects do (views before textures in 7.1, everything before the device). |
| Bytecode blob disposed in each stage's `finally` | The blob is only needed until `Create*Shader` (and, for the vertex stage, `CreateInputLayout`) copies it. Each stage owns its own blob, so a pixel-stage compile failure cannot leak the vertex blob. |
| `errors.Dispose()` in `Compile`'s `finally` | On success the error blob is usually null (safe to dispose — `Release` no-ops on a null handle); on failure it holds the message you just read into a string. Either way it's released before the exception leaves. |
| `compiler.Dispose()` in `Load`'s `finally` | `D3DCompiler.GetApi()` is a native-library handle wrapper; releasing it is the polite thing at load time. It's load-time only — no per-frame cost. |
| `FreeSemanticNames()` after `Load`, in `finally` | The layout object owns copies of the semantic strings from the moment `CreateInputLayout` returns; the unmanaged originals have no further reader. Freed on the failure path too. |
| Topology set in `DrawTriangle`, not `Shader.Bind` | Topology is a property of the vertex data being drawn (list vs strip vs lines), not of the program that shades it. Keeping it beside `Draw` is what lets 5.1 reuse a shader for `LineList`. |
| `Shader` constructed with `new`, loader via `Factory.Get` | `Shader` is data-plus-COM-objects owned by the drawer, not a swappable service — constructing it inline is the repo rule. Its *dependency* (`IShaderLoader`) is injected, resolved once at the construction site. |

## ✅ Checkpoint

Exactly the 2.6 picture: the red / green / blue triangle on the cycling background, **Space** pauses the background, **V** cycles sync, **Esc** (or Start on the pad) exits. Three things you *can't* see are the actual deliverable:

1. `dotnet build` still reports **0 warnings** — the `CS9193` fix survived the move into `Shader.Bind`.
2. The process exits cleanly on Esc — no access violation, no hang — with `Dispose` having run once for the drawer and once for the shader.
3. `TriangleDrawer` has no `using Silk.NET.Direct3D.Compilers` and no `System.Text`. If it still needs either, something didn't move.

## 🐛 Common failure modes

1. **Triangle vanished.** `shader.Bind()` isn't being called between `BindVertexBuffer()` and `DrawTriangle()`, or `IASetPrimitiveTopology` got lost in the move. Same symptom as 2.6's failure modes 1–2, same fix: every bind before the trigger.
2. **Crash or `AccessViolationException` at exit.** Double release. Check that `LearningGame.OnCleanUp` calls `Dispose()` and that `CleanUp()` no longer exists anywhere — a leftover call means both ran. If you kept `CleanUp` as an alias, make it call `Dispose()` and rely on the guard, or delete it.
3. **`CreateInputLayout` fails with `E_INVALIDARG` (`0x80070057`) and the exception comes from `LoadVertexStage`.** The description array reached the shader with already-freed semantic names — most likely `FreeSemanticNames()` got called before `shader.Load(...)` instead of after. The `finally` ordering is load-bearing.
4. **Compile exception whose message names the shader** — e.g. ``Compiling `pass-through` `vertex_main` failed: ...``. That's the new, better message; the HLSL is actually broken. If you renamed the entry points in the `.hlsl`, update the constants in `Shader`.
5. **`Factory.Get<IShaderLoader>()` throws.** Unchanged from 2.5: the container isn't initialized before `LearningGame.Run`, or `pass-through.hlsl` lost its `EmbeddedResource` build action.

## 🔧 Exercises

1. **Break the HLSL on purpose.** Misspell `positon` in `pass-through.hlsl`, run, and read the exception. It now says *which shader* and *which stage* failed, plus the compiler's line number. Fix it. (You'll do this by accident in 2.8; nice to have seen the message once on purpose.)
2. **Prove the double-release story.** Comment out the `isDisposed` guard in `Shader.Dispose`, and in `TriangleDrawer.Dispose` call `shader.Dispose()` twice. Run, press Esc, and watch what happens at exit — on most drivers it's an access violation or a hard crash, on some it's silent. Silent is the scary one; that's the case 2.10's debug layer turns into a readable message. Restore the guard.
3. **Two shaders, one file.** Construct a second `Shader` from the same `"pass-through"` source, load it, and bind *it* instead of the first. Same triangle — the objects are independent. Now count what you just did: two compiles, two vertex shaders, two layouts, for identical bytes. That waste is the exact problem 4.4's resource manager exists to solve, and you've now felt it rather than been told about it.
4. **Argue with the design.** Move `IASetPrimitiveTopology` into `Shader.Bind` and make the triangle still draw (it will). Then write down, in one sentence, what breaks when 5.1 wants to draw a line list with this same shader. Put it back. Deciding where state *belongs* is most of what an engine is, and this is the first real one.
