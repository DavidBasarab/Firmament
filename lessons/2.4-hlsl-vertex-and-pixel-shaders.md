## Divergences from your committed code

Read your own files first. Two things to reconcile — both fine as written.

- **`Vertex` kept its auto-properties, and you added `Pack = 4`.** The 2.3 doc pushed `readonly struct` + public fields; you kept `public float X { get; set; }` and stamped `[StructLayout(LayoutKind.Sequential, Pack = 4)]`. Both are fine and nothing in 2.4 cares. `Pack = 4` is a no-op here — every field is a 4-byte float, so natural alignment already packs them at 0, 4, 8, 12, 16 with no gaps. It's harmless belt-and-suspenders. The one thing that still matters is **field order**: the shader input struct below declares `POSITION` then `COLOR` because your struct is `X, Y, R, G, B` in that order. Reorder the struct and the shader's semantics are describing the wrong bytes.

- **Your semantic-name helper is `AllocatedSemanticName`, and it calls `SilkMarshal.StringToPtr(semanticName)` with no explicit encoding.** The name is cosmetic. The encoding is correct — see the box below for *why*, because the reason is exactly the thing this lesson wires up on the shader side.

- **The method is wired into `OnLoad` and `Dispose` already.** Good — nothing structural changes this lesson. You're only adding string constants.

### ✅ Why the semantic name marshals correctly (and the trap you avoided)

`InputElementDesc.SemanticName` is a `byte*` to an **`LPCSTR`** — a null-terminated **single-byte ANSI** C string. That's what `CreateInputLayout` reads in 2.5 when it matches your description against the shader's declared inputs.

Your code calls `SilkMarshal.StringToPtr(semanticName)` with no `encoding` argument, so it takes the parameter's default. In the version of Silk.NET this project references, that default is **`NativeStringEncoding.Ansi`**:

```csharp
public static unsafe nint StringToPtr(string? input, NativeStringEncoding encoding = NativeStringEncoding.Ansi)
```

`Ansi` (equivalently `LPStr`) marshals `"POSITION"` as the eight ASCII bytes plus a terminator — exactly the `LPCSTR` the API wants. So the GPU sees the full `"POSITION"` / `"COLOR"`, and `CreateInputLayout` in 2.5 will match them against the shader's reflected input signature cleanly. Nothing to fix.

The trap worth knowing: had the default been `NativeStringEncoding.LPTStr` — the *platform-auto* encoding, which on Windows is **UTF-16**, two bytes per character — `"POSITION"` would marshal as `50 00 4F 00 53 00 ...`. Read back as an ANSI C string, the first `00` is a null terminator, so the GPU would see the semantic name `"P"` (and `"COLOR"` → `"C"`). Still distinct, so nothing crashes and the app runs exactly as it does now — but in 2.5, `CreateInputLayout` would compare `"P"` / `"C"` against a signature that says `POSITION` / `COLOR`, find no match, and fail with `E_INVALIDARG`. You'd stare at a correct-looking input layout for an hour.

You're safe because the default is `Ansi`. If you want that safety to be load-bearing rather than implicit — a guard against the default ever changing — pass it explicitly:

```csharp
var pointer = SilkMarshal.StringToPtr(semanticName, NativeStringEncoding.Ansi);
```

That's a robustness choice, not a required fix. The behavior is already correct.

## Concept: two small programs that run on the GPU, millions of times

A shader is not configuration. It is a program — a real function with parameters and a return value — that the GPU compiles to its own instruction set and runs in massive parallel. Between your bound vertex buffer and a lit pixel sit two of them, and 2.1's pipeline diagram is where they live:

**The vertex shader runs once per vertex.** Three vertices in the buffer → three invocations, conceptually simultaneous. Its job is to take one vertex's attributes and produce, at minimum, that vertex's **clip-space position** — the coordinate the rasterizer needs to place it in the [-1, 1] box. It can also pass along or compute anything else the later stages want (here: the color). It cannot see other vertices, cannot see the triangle; it sees one vertex and answers "where does this corner go, and what data rides along with it."

**The pixel shader runs once per pixel** the triangle covers — hundreds of thousands of times for a full-screen triangle. Its job is to return the final color for that one pixel. It never sees a vertex. It sees the *interpolated* values the rasterizer manufactured for its exact pixel location, and returns four floats: red, green, blue, alpha.

Between them sits the **rasterizer**, which is fixed-function — not programmable, you don't write it. It takes the three clip-space positions, works out which pixels fall inside the triangle, and for each such pixel *interpolates* every value the vertex shader passed along. That's how three corner colors become a smooth gradient across the face: the rasterizer blends them per pixel. (The mechanics of that blend — perspective-correct interpolation — are 2.8. For now, "it smoothly mixes the corner values" is the whole model you need.)

So the data path this lesson sets up is: **vertex buffer bytes → [input layout] → vertex shader input → vertex shader output → [rasterizer interpolates] → pixel shader input → pixel shader output → render target.** You already built the first arrow (2.3). This lesson writes the two boxes labeled "shader."

### Semantics are the wiring, and now you see the other end

In 2.3 you tagged bytes with names — `POSITION0`, `COLOR0` — and I said D3D matches attributes *by name*, not by slot number, and that the match happens at `CreateInputLayout`. This lesson writes the other side of that match.

An HLSL shader parameter carries a **semantic** after a colon: `float2 position : POSITION`. That semantic is the exact string D3D pairs with your `InputElementDesc.SemanticName`. Your input layout says "the 8 bytes at offset 0 are `POSITION0`"; the vertex shader says "give me a `float2` called `POSITION`"; D3D wires the two together. Get the names wrong on either side and the wiring fails — which is precisely why the semantic-name *encoding* above matters *here* and not before: the name your `InputElementDesc` carries must be the same bytes the shader declares.

Semantics also carry the value *out* of the vertex shader and *into* the pixel shader. The vertex shader outputs a `COLOR`; the pixel shader inputs a `COLOR`; the rasterizer interpolates it in between. The name is the through-line.

### The one output the pipeline actually requires: `SV_POSITION`

Most semantics are names you invented — `COLOR`, `TEXCOORD`, `NORMAL`. A few are reserved **system-value** semantics, prefixed `SV_`, that mean something specific to the fixed-function hardware.

The vertex shader **must** output one value tagged `SV_POSITION`. This is the clip-space position the rasterizer consumes — it's not optional decoration, it's the contract. It is a `float4`, even though your input position is a `float2`, because clip space is four-dimensional (x, y, z, w). You'll supply the missing two:

- **z = 0.** Depth. Asteroids is 2D and flat; everything sits on the same plane. z gets meaning in Part 8 with a depth buffer. For now, 0.
- **w = 1.** The homogeneous coordinate. The rasterizer divides x, y, z by w to get final screen position (the "perspective divide"). Dividing by 1 changes nothing, which is exactly what you want when there's no perspective projection yet (that arrives in 3.6). Setting w = 1 means "this position is already final, don't warp it."

One trap worth naming now so it doesn't confuse you later: `SV_POSITION` on the vertex shader *output* is clip space, but the *same* semantic as a pixel shader *input* holds something different — the pixel's screen-space coordinates in actual pixels (e.g. `(640.5, 360.5)`), because the rasterizer overwrites it on the way through. We don't read it in the pixel shader this lesson, so it won't bite you today. Just don't assume the two ends mean the same thing.

The pixel shader has a required output semantic too: **`SV_TARGET`**, the color written to render target 0 (your back buffer). A `float4` — RGBA.

## Steps — what to write and where

### Step 1 — Write the shader source as an in-line string

One HLSL source string holds both stages. That's deliberate and it's how a real `.hlsl` file works: one file, two entry-point functions, compiled twice — once as a vertex shader, once as a pixel shader (2.5 does exactly that). Add this field to `FirmamentWindow`:

```csharp
	private const string ShaderSource = """
		struct VertexInput
		{
			float2 Position : POSITION;
			float3 Color : COLOR;
		};

		struct VertexOutput
		{
			float4 Position : SV_POSITION;
			float3 Color : COLOR;
		};

		VertexOutput VertexMain(VertexInput input)
		{
			VertexOutput output;
			output.Position = float4(input.Position, 0.0f, 1.0f);
			output.Color = input.Color;
			return output;
		}

		float4 PixelMain(VertexOutput input) : SV_TARGET
		{
			return float4(input.Color, 1.0f);
		}
		""";
```

That's the entire lesson's code. Read it against the concept:

- **`VertexInput`** mirrors your `Vertex` struct, in the same field order, tagged with the same semantics your `InputElementDesc[]` uses. `float2 Position : POSITION` binds to the `POSITION0` element at offset 0; `float3 Color : COLOR` binds to `COLOR0` at offset 8. This struct *is* the shader side of the 2.3 input layout.
- **`VertexOutput`** is what travels to the rasterizer: the required `SV_POSITION`, plus the `COLOR` we want interpolated and handed to the pixel shader.
- **`VertexMain`** promotes the 2D input position to a 4D clip-space position with `float4(input.Position, 0.0f, 1.0f)` — HLSL lets you build a `float4` by concatenating a `float2` with two scalars — and passes the color straight through untouched. No math, no transform: the vertices are already in clip space (2.3), so this shader's only real work is the `float2 → float4` promotion.
- **`PixelMain`** takes the interpolated `VertexOutput` (it ignores the `SV_POSITION` field and reads only `Color`), and returns it as a `float4` with alpha 1.0 (fully opaque). The `: SV_TARGET` after the parameter list tags the *return value*, not a parameter — that's the HLSL syntax for "this function returns the render-target color."

Reusing `VertexOutput` as the pixel shader's input type is not a shortcut — it's the requirement. The pixel shader's input signature must match the vertex shader's output signature by semantic, and sharing the struct guarantees it. In 2.7, when this becomes a real `.hlsl` file, that shared struct is what keeps the two stages honest.

### Step 2 — Confirm nothing else changed

You do **not** touch `OnLoad`, `OnRender`, or `Dispose` this lesson. No `CreateVertexShader`, no `CreatePixelShader`, no `VSSetShader`. The string is inert C# data — it's not HLSL to the compiler, it's a sequence of characters. It becomes a shader only when `D3DCompile` turns it into bytecode in 2.5.

If you want to prove to yourself the string is well-formed HLSL before 2.5, that's exercise 3.

## Per-value justification

| Value | Why |
|---|---|
| `float2 Position : POSITION` | Two floats, matching the `FormatR32G32Float` / offset-0 element from 2.3. The `POSITION` semantic is the name D3D pairs with that `InputElementDesc`. |
| `float3 Color : COLOR` | Three floats, matching `FormatR32G32B32Float` at offset 8. `COLOR` pairs with the second element. |
| `float4 Position : SV_POSITION` | The one mandatory vertex-shader output. `float4` because clip space is homogeneous (x, y, z, w). Not writing it is a compile error in 2.5. |
| `float4(input.Position, 0.0f, 1.0f)` | Promotes 2D → 4D clip space. **z = 0**: flat 2D, no depth yet (Part 8). **w = 1**: no perspective divide, position is already final (projection arrives in 3.6). |
| `output.Color = input.Color` | Pure pass-through. The vertex shader does no color work; the *rasterizer* turns three corner colors into a per-pixel gradient (2.8). |
| `PixelMain(...) : SV_TARGET` | `SV_TARGET` tags the return value as the color for render target 0 — your back buffer. `float4` = RGBA. |
| `float4(input.Color, 1.0f)` | Appends alpha = 1.0 (opaque) to the interpolated `float3` color. Blending against that alpha is 5.6; here it's just "fully solid." |
| `VertexMain` / `PixelMain` names | Entry-point function names. 2.5 passes these strings to `D3DCompile` to say which function to compile for each stage. Any names work as long as 2.5 uses the same ones — these are self-documenting. |
| Raw string literal `"""` | Keeps the HLSL readable with real newlines and no `\n` noise. The leading whitespace to the closing `"""` is stripped by C#, so the indentation shown doesn't end up in the compiled source. |

## 🐛 Common failure modes

1. **You tried to compile it and there's no compiler.** If you jumped ahead and called `D3DCompile`, note that `Silk.NET.Direct3D.Compilers` isn't a package reference yet — that's a 2.5 step, on purpose. This lesson stops at the string.
2. **Semantics don't match your actual `InputElementDesc[]`.** If you renamed `POSITION`/`COLOR` in 2.3 (or changed their order or formats), the HLSL here must match *your* names, not the doc's. The match is validated in 2.5; get it right now while both sides are in front of you.
3. **Forced `AllocatedSemanticName` to `LPTStr` (or a Silk.NET version whose `StringToPtr` defaults to it).** Your committed code takes the `Ansi` default and is fine. But if you ever pass `NativeStringEncoding.LPTStr` explicitly — or a library update changes the default — nothing breaks this lesson; it breaks in 2.5 as an `E_INVALIDARG` from `CreateInputLayout` with a semantic mismatch that's invisible in the debugger (the layout looks fine). See the ✅ box for why `Ansi` is the correct encoding.
4. **`Vertex` field order was edited since 2.3.** The shader's `VertexInput` order and the input layout offsets both encode `X, Y, R, G, B`. Reorder the struct and both lie. No warning until you see wrong colors in 2.6.
5. **Expecting the string to *do* something.** It doesn't. No `Draw`, no `VSSetShader`. A blank-but-cycling screen is the correct, complete result of 2.4.
