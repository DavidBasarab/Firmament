# Lesson 1.2 — The Game Loop and Delta Time

> Part 1 — A Window and a Heartbeat
> *The game loop: `OnUpdateFrame` vs `OnRenderFrame`, what delta time actually is*

That `Run()` is *already* a live game loop — it's been ticking since 1.1, you just haven't hooked anything into it. This lesson hooks in, and makes the loop prove it's alive.

## Concept: two clocks, not one

A game loop is not "draw as fast as you can." It's two jobs that happen to share a `while (running)`:

1. **Update** — advance the simulation. Move the ship, integrate physics, run AI, poll input. This is your *world* getting one tick older.
2. **Render** — take the world as it is *right now* and turn it into a picture. This touches the GPU. It must not change game state.

OpenTK hands you these as two overrides on `GameWindow`: `OnUpdateFrame` and `OnRenderFrame`. Its internal loop calls update, then render, then swaps the buffers, then loops. Why split them at all, when today they fire back-to-back every iteration? Because **they don't have to run at the same rate, and eventually they won't.** Lesson 4.2 ("Fix Your Timestep") decouples them hard: physics on a fixed 60 Hz clock so collisions are deterministic, rendering as fast as the monitor allows with interpolation to smooth the gap. Keeping the two jobs in separate methods from day one means that lesson is a rewiring, not a rewrite. Treat the rule as absolute now: **`OnUpdateFrame` may mutate game state; `OnRenderFrame` may not.**

### Delta time is "how much world-time this frame represents"

Each callback's `FrameEventArgs args` carries one number: `args.Time`, a `double`, the **seconds elapsed since the last time that same callback ran.** On an uncapped loop that's a tiny fraction — maybe `0.0004` (0.4 ms). Under load it balloons.

Why you care: frame rate is not constant, so *anything that moves must move as a function of time, not per frame.* "100 units per second" becomes `position += 100 * args.Time` — 0.4 ms later that's a nudge, 40 ms later it's a big step, and the ship crosses the screen in the same wall-clock second on a 3000 fps gaming rig and a 30 fps laptop. Skip the `* dt` and you've hard-coded your game's speed to the player's hardware. That's the bug lesson 3.11 is named after; we're planting the habit now, before anything moves.

One honesty note up front: with the default settings your loop runs **uncapped** — no VSync, no frequency limit — so it'll spin a CPU core to 100% and report thousands of updates per second. That's expected and a little obscene. Lesson 1.8 (VSync) is where you put a lid on it. Don't fix it early.

## Step 1 — hook the loop

Edit **`Firmament.Core/FirmamentWindow.cs`**. It's a one-liner today; give it a body with three fields and two overrides:

```csharp
using OpenTK.Windowing.Common;
using OpenTK.Windowing.Desktop;

namespace Firmament.Core;

public class FirmamentWindow(GameWindowSettings gameWindowSettings, NativeWindowSettings nativeWindowSettings)
	: GameWindow(gameWindowSettings, nativeWindowSettings)
{
	private double secondsSinceLastReport;
	private int updatesSinceLastReport;
	private int rendersSinceLastReport;

	protected override void OnUpdateFrame(FrameEventArgs args)
	{
		base.OnUpdateFrame(args);

		secondsSinceLastReport += args.Time;
		updatesSinceLastReport++;

		if (secondsSinceLastReport < 1.0)
		{
			return;
		}

		Console.WriteLine(
			$"{updatesSinceLastReport} updates, {rendersSinceLastReport} renders in {secondsSinceLastReport:F2}s"
		);

		secondsSinceLastReport = 0.0;
		updatesSinceLastReport = 0;
		rendersSinceLastReport = 0;
	}

	protected override void OnRenderFrame(FrameEventArgs args)
	{
		base.OnRenderFrame(args);

		rendersSinceLastReport++;
	}
}
```

What each piece is doing, and why it's shaped this way:

| Piece | Why |
|---|---|
| `base.OnUpdateFrame(args)` / `base.OnRenderFrame(args)` | `GameWindow` raises its public `UpdateFrame`/`RenderFrame` events from these. Skip the base call and anything subscribed (nothing yet, but you will) goes silent. Call base first, then do your work. |
| The `secondsSinceLastReport < 1.0` guard | We accumulate `args.Time` and only print **once per real second**. A 60 FPS loop calling `Console.WriteLine` every frame would flood the terminal and tank the frame rate — your `errors-and-logging` rule bans per-frame logging for exactly this reason. This is a guard clause / early return, per house style. |
| Counting updates *and* renders separately | This is the whole point of the lesson made visible. Right now the two counts will track each other almost exactly. In the exercises you'll pull them apart and watch them diverge — proof they're genuinely two clocks. |
| No `SwapBuffers()` call | The base loop swaps for you *after* `OnRenderFrame` returns (the 1.1 checkpoint mentioned this). Calling it yourself here would present twice per frame. Leave it to the base. |
| No `GL.*` anywhere | Rendering is lesson 1.4 (`GL.Clear`). Today `OnRenderFrame` only counts. The window's contents stay undefined — exactly as they were in 1.1. |

`Console` needs no `using` — `ImplicitUsings` is `enable` in the `.csproj`, so `System` is already in scope.

> The `Console.WriteLine` heartbeat is a **teaching scaffold, not permanent code.** It exists to prove the loop ticks. Lesson 1.3 replaces it with a proper rolling FPS/frame-time readout in the **title bar** — delete the console line when you get there. Don't let it calcify.

`Program.cs` needs no changes — it already constructs the window and calls `Run()`.

## ✅ Checkpoint

- The same 1280×720 window from 1.1 opens (contents still undefined — that's correct until 1.4).
- **The terminal prints one line per second**, e.g. `4127 updates, 4127 renders in 1.00s`. The exact number depends entirely on your CPU; it will be large and it will jitter frame to frame.
- Update count ≈ render count. On the default uncapped loop they run in lockstep — one update, one render, repeat.
- Close the window; printing stops and the process exits 0. The loop lived and died with the window.
- One CPU core sits pegged near 100% while it runs. Expected — you're spinning uncapped. 1.8 fixes it.

## 🐛 Common failure modes

1. **No lines print, but the window is open.** Your override isn't being called — almost always a signature mismatch so you *shadowed* instead of *overrode*. It must be exactly `protected override void OnUpdateFrame(FrameEventArgs args)`. Wrong accessibility (`public`), a missing `override`, or the wrong args type gives you a brand-new method the base loop never calls.
2. **A line prints far more often than once per second.** You reset `secondsSinceLastReport` but forgot the counters, or vice versa — the accumulator never crosses the threshold cleanly. Reset all three together at the bottom, only inside the `>= 1.0` branch.
3. **Window contents flicker / show garbage.** Not a bug. You're not clearing or drawing, so you're staring at uninitialized back-buffer memory getting presented every swap. Lesson 1.4.
4. **`updates` and `renders` differ by a lot with no changes.** If you copy-pasted and put the increment *before* `base.OnRenderFrame`, or double-incremented, the counts drift. Each callback should bump its own counter exactly once.
5. **Terminal print rate is fine but the number looks impossibly high (tens of thousands).** That's a fast CPU on an uncapped loop, not a bug. Confirm by capping — see exercise 2.

## 🔧 Exercises

1. **Print delta time in milliseconds.** In `OnUpdateFrame`, before the guard, keep the largest `args.Time` you've seen this second and print it too: `... max delta {worstMilliseconds:F2} ms`. The *max* is the honest number — average hides the hitches. (You're pre-inventing lesson 1.3's argument that ms beats FPS.)
2. **Cap the update rate and watch the clocks split.** In `Program.cs`, set `window.UpdateFrequency = 30;` before `Run()`. Now updates settle near 30/sec while renders stay uncapped and huge. That gap is *why* the two callbacks exist. Then also set `window.RenderFrequency = 5;` and watch renders drop to ~5 while updates hold at 30. Put both back to `0` (uncapped) when done.
3. **Force a stall and read the spike.** Add `System.Threading.Thread.Sleep(100);` at the top of `OnUpdateFrame`. Your loop drops to ~10 updates/sec and `args.Time` jumps to ~0.1s. This is the "big step" delta from the concept section — feel how much the number moves. Remove it after.
4. **Prove `OnRenderFrame` must not mutate state.** Add a field `int tick;`, increment it in `OnRenderFrame`, and use it as if it were game logic. Then do exercise 2 (different update/render rates) and watch your "logic" run at the render rate instead of the update rate. This is the exact class of bug the update/render split prevents — break it once so you recognize it.
