# Lesson 2.1 — The Graphics Pipeline, End to End

> Part 2 — The Pipeline and the First Triangle
> *The graphics pipeline, end to end, no code — a mental model to hang everything else on*

**Where you already are:** `FirmamentWindow` is ~380 lines that open a Win32 window, create a D3D11 device and an `IDXGISwapChain1`, rebuild the back buffer and viewport on resize, bind a render target, clear it to a time-interpolated color, and present it under a sync interval you can cycle at runtime with **V**. Eight lessons, and the result is a rectangle of solid color.

Here is the uncomfortable fact that opens Part 2: **none of that has touched the graphics pipeline.** Not one stage of it. `ClearRenderTargetView` is a resource operation — the driver writes the clear value into the texture (usually by scribbling compression metadata rather than actual pixels) and never launches a single shader. `OMSetRenderTargets` binds the *destination* the pipeline would write to, if the pipeline were running. `RSSetViewports` configures a stage that has nothing to rasterize.

You have built the plumbing on both ends of the pipeline and nothing in between. This lesson is the map of the in-between. **No code. Read it, then reread it after 2.6 when the triangle appears — it will land differently.**

## Concept: the pipeline is an assembly line you configure, not a function you call

A GPU does not draw a triangle. It runs a **fixed sequence of stages**, some programmable and some hard-wired in silicon, and each stage consumes what the previous one produced. You do not call the stages. You *configure* them — bind buffers, bind shaders, set state — and then issue one command, `Draw`, which turns the crank. Everything currently bound to the device context participates; everything not bound is either off or a bug.

That is the single most important sentence in Part 2, and it explains a category of failure you are going to hit repeatedly: **nothing appears, nothing errors.** You didn't call the wrong function. You called the right one with something unbound.

The stages, in order, with the hard-wired ones marked:

```
        vertex buffer + index buffer + input layout
                          │
   [IA]  Input Assembler          ◄── fixed function
                          │  vertices
   [VS]  Vertex Shader            ◄── you write this (HLSL)
                          │  vertices in CLIP space
   ( HS / Tessellator / DS / GS — skipped; see below )
                          │
   [RS]  Rasterizer               ◄── fixed function
                          │  pixels, with interpolated attributes
   [PS]  Pixel Shader             ◄── you write this (HLSL)
                          │  colors
   [OM]  Output Merger            ◄── fixed function
                          │
              render target (your back buffer)
                          │
                    Present  ◄── you already own this, since 1.8
```

Two of eight boxes are yours to program. The other six are configured through state and then obeyed. Part 2 fills in IA, VS, RS, PS, OM and leaves the tessellation and geometry stages permanently dark.

## The stages, one at a time

### [IA] Input Assembler — bytes become vertices

You hand the GPU a `ID3D11Buffer` full of floats. On its own that is a meaningless blob; the buffer does not know it contains positions. The IA needs three things to make sense of it:

| Input | What it answers | Curriculum |
|---|---|---|
| **Vertex buffer** | where the bytes are | **2.2** |
| **Input layout** (`ID3D11InputLayout`) | what each vertex's bytes *mean* | **2.3** |
| **Primitive topology** | how vertices group into shapes | **2.6** |
| **Index buffer** (optional) | which vertices, in what order, reused | **2.9** |

The **input layout** is an array of `InputElementDesc` — one entry per attribute, each naming a semantic (`"POSITION"`, `"COLOR"`), a `Format` (e.g. `FormatR32G32B32Float` for three floats), an input slot, and a **byte offset into the vertex**. That last number is the one everybody gets wrong, and it's why 2.3 exists as its own lesson. If your vertex is `{ float3 position; float4 color; }`, the color's offset is `12` — three floats × four bytes — and getting it wrong doesn't crash, it just draws garbage geometry.

**Topology** is how consecutive vertices become primitives. Six vertices are two separate triangles under `TriangleList` and four overlapping ones under `TriangleStrip`. The enum lives in `Silk.NET.Core.Native.D3DPrimitiveTopology` — not in the D3D11 namespace, which is a Silk.NET quirk that will waste ten minutes of your life at 2.6 if nobody tells you now. `D3DPrimitiveTopologyLinelist` is the one Asteroids actually wants; **5.1** builds the line renderer on it.

### [VS] Vertex Shader — once per vertex, and its job is to produce a clip-space position

The vertex shader runs **once per vertex**, in parallel, with no knowledge of any other vertex. It receives the attributes the input layout described and must output a 4-component position tagged `SV_POSITION`. Anything else it outputs (color, texture coordinates, a normal) is passed down to be interpolated.

Its actual job is coordinate-space transformation: take a position expressed in whatever space your model is authored in, and transform it into **clip space**. That is the *entire* purpose of the matrix math in Part 3 — 3.4 through 3.7 exist to build the matrix this shader multiplies by. At 2.4 you will hand the vertex shader positions already in clip space and have it do nothing, precisely so the triangle appears before the math does.

### Clip space, NDC, and the thing you must not carry over from OpenGL

The vertex shader emits `float4(x, y, z, w)`. That is **clip space** — homogeneous coordinates, not yet a location on screen. The rasterizer then performs the **perspective divide**, dividing x, y, z by w, and what comes out is **normalized device coordinates (NDC)**: an API-defined box that the visible region always maps onto, regardless of window size.

Geometrically: NDC is the screen with its corners pinned to fixed numbers. Whatever your window size, the same NDC coordinate lands in the same *relative* place. That is why your triangle in 2.6 will survive a window resize without you doing anything — the RS applies the viewport transform from NDC to pixels, and 1.7 already taught the viewport its size.

**The box is not the same box in D3D as in OpenGL:**

| Axis | OpenGL NDC | Direct3D NDC |
|---|---|---|
| x | −1 (left) … +1 (right) | −1 … +1 — same |
| y | −1 (**bottom**) … +1 (top) | −1 (bottom) … +1 (top) — same |
| z | −1 (near) … +1 (far) | **0 (near) … 1 (far)** |

The z range is the divergence, and it is not a detail — it changes your projection matrix. Every orthographic and perspective matrix formula you find on LearnOpenGL, in a StackOverflow answer, or in a textbook maps z to **[−1, 1]**. Feed one of those to D3D and everything nearer than the midpoint of your view volume is clipped away. **3.6** and **8.1** are where this bites; note it now.

Two related traps, both from the same family. Screen and texture coordinate origins are **top-left in D3D**, bottom-left in GL — which is why your `Viewport.TopLeftY = 0` means the top of the window, and why a PNG loaded at 5.4 will appear upside down if you copy a GL tutorial's UV math. And OpenTK's `Matrix4` helpers build GL-convention matrices; **3.8** is going to have to say something honest about that, because `Firmament.Rendering` still has an `OpenTK` package reference sitting in it (see the stale note at the bottom).

### [HS / Tessellator / DS / GS] — the stages we are skipping

Between VS and RS sit four more stages: hull shader, fixed-function tessellator, domain shader (subdividing patches into more geometry on the GPU), and the geometry shader (emitting or discarding whole primitives). They are real, they are always present, and leaving them unbound means the vertex output flows straight through to the rasterizer.

**Nothing in this curriculum uses them.** Not the 2D game, not the 3D game. They are named here once so that when you see them in a pipeline diagram you know they are deliberately dark and not something you forgot. Compute shaders — a separate pipeline entirely, not a stage in this one — show up at **13.1**.

### [RS] Rasterizer — geometry becomes pixels

The most work happens in the stage you cannot program. In order:

1. **Clipping** against the view volume — triangles crossing the edge are cut into smaller triangles.
2. **Perspective divide** — clip space ÷ w → NDC. Note this is the *rasterizer's* job, not the vertex shader's; a common misreading of shader code.
3. **Viewport transform** — NDC → pixel coordinates, using the `Viewport` you set in 1.7. This is where your window's dimensions finally enter the math.
4. **Back-face culling** — triangles whose vertices wind the wrong way on screen are discarded. Off by default in the sense that you configure it via `ID3D11RasterizerState`; **8.7** is the "half my model is invisible" lesson.
5. **Scan conversion** — for each pixel whose center falls inside the triangle, emit a pixel. Coverage is determined by a tie-break called the top-left rule, which exists so that two triangles sharing an edge neither double-shade nor leave a gap.
6. **Attribute interpolation** — every non-position value the VS emitted is blended across the triangle's interior, weighted by distance from each vertex, and **corrected for perspective** so that a texture on a floor receding into the distance compresses correctly.

Step 6 is worth staring at. It is why **2.8**'s three-colored triangle produces a smooth gradient: you specified a color at three corners and the hardware invented every color in between, for free, because interpolation is what the rasterizer does to everything anyway.

Note that RS state in D3D11 is an **immutable object** — you create an `ID3D11RasterizerState` describing fill mode, cull mode, scissor enable, and bind the whole thing with `RSSetState`. There is no `glEnable(GL_CULL_FACE)` equivalent. More on why that matters below.

### [PS] Pixel Shader — once per pixel, and there are more of them than you think

Called the **fragment shader** in OpenGL and in this repo's curriculum wording. Same stage. It runs once per rasterized pixel, receives the interpolated attributes, and returns a color to `SV_TARGET`.

Three things that are not obvious and that will explain performance numbers later:

- **Pixels are shaded in 2×2 quads, always.** The hardware needs neighbouring values to compute derivatives (how fast a texture coordinate is changing between adjacent pixels — that's how mipmap level selection works at 5.4). A triangle covering a single pixel still costs four pixel-shader invocations; three are computed and thrown away. This is why thousands of tiny triangles are disproportionately expensive, and it is the real cost behind **9.8**'s level-of-detail lesson.
- **The GPU executes in lockstep groups** of 32 or 64 lanes. If half the lanes in a group take the `if` and half take the `else`, the hardware runs *both* branches and masks the results. A branch in a shader is not free the way a branch in C# is.
- **The depth test can run before the pixel shader** ("early-Z"), skipping shading for pixels that are already hidden — but only if the shader doesn't `discard` or write its own depth. Doing either silently disables the optimization. **8.2** is the depth-buffer lesson; that's where this becomes actionable.

### [OM] Output Merger — deciding what actually gets written

The final stage takes the pixel shader's color and merges it into the render target. Three things happen:

- **Depth/stencil test** — is this pixel in front of what's already there? (`ID3D11DepthStencilState`, **8.2**.)
- **Blending** — combine with the existing pixel instead of replacing it. (`ID3D11BlendState`, **5.6** for alpha and additive glow.)
- **Write masks** — which channels are allowed through.

You already call `OMSetRenderTargets` every frame, which is the "where does this go" half of the OM. The other half is entirely unconfigured, which is correct — with no depth state and no blend state, D3D11 uses sane defaults: depth testing off, blending off, opaque overwrite. That is exactly what a 2D line game wants, and you will not touch it until 5.6.

## Direct3D 11 ↔ OpenGL: what Part 2's curriculum wording means here

Part 2's lesson titles were written before the 1.5 pivot and are still spelled in OpenGL. The **stages are identical** — this lesson needed no rewrite for that reason — but the object model is genuinely different in three ways worth internalizing before 2.2. Use this table as the translation key for the rest of Part 2.

| Curriculum says (OpenGL) | Direct3D 11 / Silk.NET | Lesson |
|---|---|---|
| VBO | `ID3D11Buffer` with `BindFlag.VertexBuffer` | 2.2 |
| VAO + `glVertexAttribPointer` | `ID3D11InputLayout` built from `InputElementDesc[]` | 2.3 |
| GLSL | HLSL | 2.4 |
| Vertex shader | Vertex shader (`ID3D11VertexShader`) | 2.4 |
| **Fragment** shader | **Pixel** shader (`ID3D11PixelShader`) | 2.4 |
| `glCompileShader` + `glLinkProgram` | `D3DCompile` — **and no link step at all** | 2.5 |
| Shader *program* object | doesn't exist; VS and PS are bound independently | 2.5 |
| `glDrawArrays` | `deviceContext.Draw(vertexCount, startVertex)` | 2.6 |
| EBO / `glDrawElements` | `BindFlag.IndexBuffer` + `DrawIndexed` | 2.9 |
| `glGetError`, `KHR_debug` | the **debug layer** (`CreateDeviceFlag.Debug`) + `ID3D11InfoQueue` | 2.10 |
| Uniform, `glUniform4f` | **constant buffer** — `BindFlag.ConstantBuffer`, `VSSetConstantBuffers` | 2.11 |
| `glEnable(GL_BLEND)`, `glBlendFunc` | `ID3D11BlendState` object + `OMSetBlendState` | 5.6 |
| Texture + its sampling parameters | `ID3D11ShaderResourceView` **and a separate** `ID3D11SamplerState` | 5.4 / 5.5 |
| FBO | render target view (you already have one) | 7.1 |

**The three differences that actually change how you'll write code:**

1. **There is no program object and no link step.** In GL you link a vertex and fragment shader into a program and the linker checks that the fragment shader's inputs match the vertex shader's outputs. D3D11 binds `VSSetShader` and `PSSetShader` independently and never cross-checks them. The one validation you *do* get happens at `CreateInputLayout`, which is handed the compiled vertex-shader bytecode and verifies your input layout against the signature the shader actually expects. That is the D3D analogue of linking, it happens in a place you would not guess, and 2.5's "read the error log" advice applies there as much as to the compiler.
2. **Render state is immutable objects, not toggles.** GL has a hundred `glEnable` switches mutated one at a time. D3D11 makes you describe a complete blend / rasterizer / depth-stencil configuration up front, create an object from it, and swap the whole object in one call. This is more ceremony for one state and dramatically less for forty, and it is why **5.6**'s "render-state management" is a much smaller lesson here than the curriculum implies — the API already did the hard part.
3. **Uniforms are buffers, not individual setters.** There is no `glUniform1f`. You define a `cbuffer` in HLSL, create a matching struct in C#, and update the whole thing. There is no such thing as setting one uniform, which makes **2.7**'s "cache uniform locations" advice obsolete on this stack — there are no locations to cache. The equivalent discipline is grouping constants by update frequency (per-frame, per-object) into separate buffers, and that's **8.11**.

## The bit that isn't in the diagram: none of this happens when you call it

`deviceContext.Draw(...)` does not draw. It appends a command to a buffer. The driver batches those, hands them to the GPU when it feels like it, and the GPU works through them asynchronously — typically **one to three frames behind** your CPU. `Present` is the synchronization point where that latency becomes visible and, under a non-zero sync interval, where your thread waits.

Three consequences to carry forward:

- **Your `delta` measures the CPU's frame, not the GPU's.** The title bar you built in 1.3 reports how fast your loop is spinning. If the GPU is the bottleneck, the CPU eventually blocks in `Present` and the numbers converge — but "16.7 ms" tells you nothing about *which* processor spent it. **11.2** adds GPU timer queries, which is the only honest way to know.
- **You cannot free a resource the GPU might still be reading.** D3D11 tracks this for you via reference counting, which is why every `ComPtr` in your file matters and why **4.3** is a whole lesson on GL/D3D object lifetimes.
- **A `Draw` per object is expensive on the CPU side**, not the GPU side — it's the command submission and state validation that costs. That is the entire argument of **5.2** and **5.3**, and the reason a batcher exists.

## 🐛 Common failure modes

There's no code to break, so these are the **misconceptions** — in the order they actually cost people a day, each with the lesson where the bill comes due.

1. **"The vertex shader outputs screen coordinates."** It outputs clip space, and it's four components because the w is load-bearing. Every "my perspective projection looks flat" bug is this one. → **3.7**, **8.1**
2. **"NDC z is −1 to 1."** True in OpenGL, false in Direct3D. Copy an ortho or perspective matrix off the internet and half your scene vanishes behind the near plane, with no error and no warning. → **3.6**, **8.1**
3. **"Nothing drew, so something must have errored."** The pipeline's default failure mode is silence. An unbound vertex shader, an input layout with a wrong byte offset, a triangle wound the wrong way, a vertex outside NDC — all produce a correct, empty frame. Turn the debug layer on early (**2.10**) rather than guessing; it's the difference between a five-minute fix and an evening.
4. **"`Draw` draws."** It queues. Your frame time measures the CPU. Anyone reasoning about GPU performance from `delta` is measuring the wrong processor. → **11.1**, **11.2**
5. **"Fragment shader and pixel shader are different things."** Same stage, two vendors' names. The curriculum says fragment because it was written for GL; the API says pixel. (Pedants will tell you a fragment is a *candidate* pixel, pre-depth-test — which is true and never matters.)
6. **"The clear goes through the pipeline."** It doesn't, which is why your 10,000 FPS from 1.8 means nothing about rendering performance. You have been measuring an empty pipeline at full speed.
7. **"Interpolation is something I'll implement."** The rasterizer does it to every VS output, unconditionally, whether you wanted it or not. At 2.8 you get gradients for free; the surprise later is a value you *didn't* want smoothed. → **2.8**
8. **"Blending is a switch."** In D3D11 it's an object you create ahead of time. Reaching for `glEnable`'s equivalent and not finding it is the single most common GL-to-D3D stumble. → **5.6**
