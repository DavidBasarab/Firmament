# Lesson 2.6 — `Draw`: Bind the Pipeline, Set the Topology, and the Triangle Appears

> Part 2 — The Pipeline and the First Triangle
> *`Draw` — bind the pipeline, set the topology, and the triangle appears*

**Where you already are:** `FirmamentWindow` stands up the device / context / swap chain, clears to a time-interpolated color, and every frame in `OnRender` it already does `OMSetRenderTargets` → `ClearRenderTargetView` → `BindVertexBuffer()` → `Present`. ## Concept: the device context is a state machine, and `Draw` is the trigger

You do not pass the shaders, the buffer, and the layout *to* `Draw`. That's the mental model to unlearn coming from an immediate-mode or retained-mode API. D3D11's `ID3D11DeviceContext` is a **state machine**: you flip switches one at a time — "the input layout is *this*," "the vertex shader is *this*," "the topology is triangles" — and each switch stays flipped until you flip it again. `Draw` doesn't take that state as arguments; it fires the pipeline using whatever state is *currently set*. It's closer to setting a bunch of global variables and then calling a parameterless `go()`.

So a draw is really "**bind everything the pipeline will read, then pull the trigger.**" 2.1's pipeline diagram is the checklist — every programmable and fixed-function stage that needs an input has to have been handed one before `Draw`:

| Pipeline stage | What it needs bound | The call |
|---|---|---|
| Input Assembler | which buffer the vertices come from | `IASetVertexBuffers` *(already done — `BindVertexBuffer`)* |
| Input Assembler | what the bytes in that buffer *mean* | `IASetInputLayout` |
| Input Assembler | how to group vertices into primitives | `IASetPrimitiveTopology` |
| Vertex Shader | the program that runs per vertex | `VSSetShader` |
| Pixel Shader | the program that runs per pixel | `PSSetShader` |
| Output Merger | where pixels get written | `OMSetRenderTargets` *(already done — top of `OnRender`)* |

Two of the six are already in your loop. This lesson adds the middle four, then calls `Draw`.

### Topology: three vertices are not automatically a triangle

The input assembler has three vertices. It does **not** assume they form a triangle — they could be three separate points, or the start of a line strip. `IASetPrimitiveTopology` is where you tell it. `TriangleList` means "read vertices in groups of 3, each group is one filled triangle." Three vertices → one triangle. (Six would be two; a strip would reuse shared edges — that's a 2.9-era optimization, not now.) Without setting this, the IA has D3D's default of *undefined* topology and the draw produces nothing.

### `Draw(3, 0)`: vertex count, and where to start

`Draw(VertexCount, StartVertexLocation)` = "pump 3 vertices through the pipeline, beginning at index 0 in the bound vertex buffer." That's the whole call. The IA walks vertices 0, 1, 2; the input layout slices each one into `POSITION` + `COLOR`; the vertex shader promotes each to clip space; the rasterizer fills the triangle and interpolates the three corner colors per pixel (2.8 explains *how* it interpolates); the pixel shader returns a color per covered pixel; the output merger writes them to the back buffer. Then `Present` (already there) flips it to the screen.

### Why you won't get a culled (invisible) triangle

You never set a rasterizer state, so D3D uses its default: **cull back faces, front faces are clockwise** (`FrontCounterClockwise = false`). Your 2.3 vertices — top `(0, 0.5)`, bottom-right `(0.5, -0.5)`, bottom-left `(-0.5, -0.5)` — wind **clockwise** on screen, so they're front-facing and survive the cull. That's luck-you-arranged, not luck-you-got: reverse two vertices and half your triangle vanishes, which is the exact bug 8.7 is about. For now the default state does the right thing and you draw nothing to configure it.

## Steps — what to write and where

### Step 1 — Add a method that binds the pipeline and draws

Everything new is a single private method next to `BindVertexBuffer` (same file, same style). It sets the four remaining pieces of state and pulls the trigger:

```csharp
	private void DrawTriangle()
	{
		deviceContext.IASetInputLayout(inputLayout);
		deviceContext.IASetPrimitiveTopology(D3DPrimitiveTopology.D3D11PrimitiveTopologyTrianglelist);

		deviceContext.VSSetShader(vertexShader, null, 0);
		deviceContext.PSSetShader(pixelShader, null, 0);

		deviceContext.Draw(3, 0);
	}
```

`D3DPrimitiveTopology` lives in `Silk.NET.Core.Native`, which `FirmamentWindow` already imports — no new `using`.

### Step 2 — Call it in `OnRender`, after the vertex buffer is bound and before `Present`

`OnRender` already has the buffer bound. Insert the draw between `BindVertexBuffer();` and the `Present` call:

```csharp
		BindVertexBuffer();

		DrawTriangle();

		SilkMarshal.ThrowHResult(swapChain.Present(presentSyncInterval, GetPresentFlags()));
```

That's the entire code change for the lesson. Build and run.

## Per-value justification

| Value / call | Why |
|---|---|
| `IASetInputLayout(inputLayout)` | Binds the 2.3/2.5 layout so the IA knows the bound buffer's bytes are `POSITION` (offset 0) + `COLOR` (offset 8). Without it the vertex shader reads garbage. |
| `D3D11PrimitiveTopologyTrianglelist` | "Every 3 vertices = 1 filled triangle." Default topology is *undefined* → nothing draws. `Trianglestrip`/`Trianglefan` are for shared-edge meshes (later); a list is the honest choice for one triangle. |
| `VSSetShader(vertexShader, null, 0)` | Binds the per-vertex program. `null` = no class-instance array (dynamic linkage, unused here); `0` = zero of them. `null` selects the `ID3D11ClassInstance**` overload, and `ComPtr<ID3D11VertexShader>` implicitly converts to the pointer the overload wants. |
| `PSSetShader(pixelShader, null, 0)` | Same, for the per-pixel program. |
| `Draw(3, 0)` | 3 = vertex count (your buffer holds exactly 3); 0 = start at the first vertex. Not `DrawIndexed` — you have no index buffer until 2.9. |
| Placed **after** `ClearRenderTargetView`, **before** `Present` | Clear first (or the triangle is wiped), draw onto the cleared target, then present the finished frame. Order is the frame. |
| State set **every frame** | Simplest correct thing. The context keeps this state between frames, so re-setting unchanging state each frame is redundant work — a real renderer caches state and only rebinds on change. It's cheap for one triangle; Part 5's batcher is where it starts to matter. Said out loud per the performance-honesty rule. |

## ✅ Checkpoint

A triangle sits in the middle of the window: **red** at the top vertex, **green** bottom-right, **blue** bottom-left, blended smoothly across the face (that gradient is the rasterizer interpolating the three `COLOR` values — the thing 2.8 dissects). The background still cycles color, **V** still cycles sync, **Space** still pauses the background — and the triangle sits on top of all of it, unchanging, because its vertices are fixed in clip space and its colors come from the buffer, not the clock.

If you paused the background (Space) you'd see the triangle is rock-steady while everything behind it stops — proof the draw is independent of the clear.

## 🐛 Common failure modes

1. **Black/empty triangle area, background still cycles.** Most likely the topology: if `IASetPrimitiveTopology` is missing or set to something other than a triangle type, the IA can't assemble a triangle and `Draw` emits nothing. Confirm `D3D11PrimitiveTopologyTrianglelist`.
2. **Nothing draws, no error.** A shader isn't bound. Verify both `VSSetShader` and `PSSetShader` run *before* `Draw`, and that `vertexShader`/`pixelShader` were non-null after `OnLoad` (that was 2.5's checkpoint). An unbound vertex shader means the IA has nowhere to send vertices.
3. **Triangle is there but colors are wrong / swapped.** The input layout or the `Vertex` field order disagrees with the shader's `vertex_input`. The bytes are being sliced at the wrong offsets. This is a 2.3/2.4 mismatch surfacing at last — check `POSITION` is offset 0 and `COLOR` offset 8, and that `Vertex` is still `X, Y, R, G, B` in that order.
4. **Half the triangle is missing, or the whole thing vanished after you edited the vertices.** Winding/backface culling. Default state culls clockwise-back... err, culls *back*, and back is counter-clockwise by default. If you reordered the vertices into counter-clockwise order you flipped the triangle to back-facing and the cull ate it. Reverse two vertices back, or wait for 8.7 to set an explicit rasterizer state.
5. **`Draw` throws or the context faults.** `inputLayout` is null because `CreateInputLayout` actually failed in 2.5 (you may have only checked the shaders). Re-run 2.5's checkpoint: all three handles non-null.
6. **Triangle flickers or tears.** That's the present path (1.8), not the draw. Toggle **V**; unrelated to this lesson.

## 🔧 Exercises

1. **Move the trigger, break the frame.** Temporarily put `DrawTriangle()` *before* `ClearRenderTargetView`. Predict what you'll see before you run it, then run it. (The clear wipes the triangle every frame → back to a blank cycling window.) Put it back. This nails down that `Draw` writes into the current target *now*, and order is everything.
2. **Comment out one bind at a time.** Remove `IASetInputLayout`, run, restore. Then the same for `IASetPrimitiveTopology`, then `VSSetShader`, then `PSSetShader`. Watch exactly how each failure *looks* — some vanish silently, some may trip the debug layer if you have it on. You're building a fault-symptom map you'll use for the rest of Part 2.
3. **Draw fewer vertices.** Change `Draw(3, 0)` to `Draw(2, 0)`. With `TriangleList`, 2 vertices is an incomplete triangle — the IA needs a full group of 3, so it draws nothing. Now try `Draw(3, 1)` (start at vertex 1) and reason about why that also can't form your triangle. Restore `Draw(3, 0)`.
4. **Prove state persists across frames.** Move `IASetInputLayout`, `IASetPrimitiveTopology`, `VSSetShader`, and `PSSetShader` out of `DrawTriangle` and into `OnLoad`, right after `CreateShaders();` — leave only `Draw(3, 0)` (and the vertex-buffer bind, which the resize path can disturb) in the per-frame path. The triangle should still draw: the context remembers the bindings. This is the first taste of the state-caching idea Part 5's renderer is built on. Decide for yourself whether you like it here or want to keep binding per-frame for clarity — both are defensible this early.
