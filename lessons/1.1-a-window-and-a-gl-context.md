## Concept: a window is not a window

You're about to ask the OS for a window. That part is boring. The part that matters is what comes *with* it.

A GPU won't talk to you directly. Everything you'll do for the next 110 lessons — uploading vertices, compiling shaders, issuing draw calls — happens through an **OpenGL context**: a big blob of driver-side state (which buffers are bound, which shader is active, what the clear color is, whether depth testing is on) that the driver owns and you mutate through function calls. OpenGL is a state machine you poke, not an object graph you hold.

That context has to live somewhere, and it has to be attached to a surface it can present pixels to. On the desktop, that surface is a window. So "open a window" really means: ask the OS for a window, ask the driver for a context of a specific OpenGL version and flavor, bind the two together, and then load the function pointers for every GL entry point — because outside of a tiny 1.1-era core, GL functions aren't in a library you link against, they're pointers you query from the driver at runtime. GLFW does the window and context part; OpenTK does the function-pointer loading (`AutoLoadBindings`, on by default).

Two more things arrive with the context, and both matter:

**Double buffering.** The driver hands you two color buffers. You draw into the back one; the front one is what the monitor scans out. When you're done with a frame you call `SwapBuffers` and they trade places. This is why you never see a half-drawn frame. `GameWindow.Run()` calls `SwapBuffers` for you at the end of each render frame — for now, invisibly.

**The version and profile you asked for.** You don't get "OpenGL." You get a specific contract. We ask for **3.3 Core**:

- **3.3** is the oldest version with everything modern GL needs (VAOs, instancing, `layout(location=)` in GLSL) and is available on essentially any GPU made after 2010. The README says bump only when a lesson needs it — 4.3 in lesson 2.10 for `KHR_debug`, 4.3+ again in 13.1 for compute.
- **Core** profile means the fixed-function pipeline of 1990s OpenGL — `glBegin`, `glVertex3f`, the built-in matrix stack — is *deleted*, not deprecated. Calling one is an error instead of silently working. That's the point: it forces you to learn the real pipeline, and it means every StackOverflow answer written in 2004 will fail loudly instead of teaching you something obsolete.
- **ForwardCompatible** is the macOS tax. Apple's driver will only ever give you a 3.3+ context if you ask for forward-compatible core. On Windows and Linux the flag is a no-op. You have a stated cross-platform constraint, so it goes in now.

## Step 1 — the window class

New file: **`Firmament.Core/Windowing/FirmamentWindow.cs`**

```csharp
using OpenTK.Windowing.Desktop;

namespace Firmament.Core.Windowing;

public class FirmamentWindow(GameWindowSettings gameWindowSettings, NativeWindowSettings nativeWindowSettings)
	: GameWindow(gameWindowSettings, nativeWindowSettings) { }
```

That's the whole file, and yes — **it currently adds nothing over `GameWindow`.** I'm going to argue for it anyway, and you should push back if you disagree:

1. Your `CLAUDE.md` puts OpenTK/OpenGL in `Firmament.Core`. Constructing a raw `GameWindow` in `Program.cs` drags OpenTK into the game project on day one and inverts that boundary.
2. Every remaining lesson in Part 1 is an override on this type — `OnUpdateFrame`/`OnRenderFrame` (1.2), `OnRenderFrame` clear (1.4), `OnUpdateFrame` keyboard (1.6), `OnResize` (1.7). The class is empty for exactly one lesson.

The counter-argument is real: an empty subclass is a subclass you'll regret if you later want composition instead of inheritance (`GameWindow` is a fat base class — 1.2 onward you're inheriting its whole event surface whether you want it or not). Lesson 4.1 is where that bill comes due. I'd take the inheritance now and revisit it there, but it's your engine.

Note the settings come in through the constructor rather than being hard-coded here. Window size and title are a *game* decision, not an engine one — and 4.9 (config from JSON) will thank you.

## Step 2 — compose and run

Replace **`Firmament.Game/Program.cs`** entirely:

```csharp
using Firmament.Core.Windowing;
using OpenTK.Mathematics;
using OpenTK.Windowing.Common;
using OpenTK.Windowing.Desktop;

namespace Firmament.Game;

public class Program
{
	public static void Main()
	{
		var nativeWindowSettings = new NativeWindowSettings
		{
			ClientSize = new Vector2i(1280, 720),
			Title = "Firmament",
			API = ContextAPI.OpenGL,
			APIVersion = new Version(3, 3),
			Profile = ContextProfile.Core,
			Flags = ContextFlags.ForwardCompatible,
		};

		using var window = new FirmamentWindow(new GameWindowSettings(), nativeWindowSettings);

		window.Run();
	}
}
```

Every value, justified:

| Line | Why |
|---|---|
| `ClientSize` | The *drawable* area, excluding title bar and borders. `Size` is obsolete in OpenTK 4.9 precisely because people kept getting a framebuffer smaller than they asked for. |
| `1280, 720` | 16:9, fits any laptop, and 1280 is a round number to sanity-check against in lesson 1.7 (viewport/aspect). No deeper meaning. |
| `API` / `APIVersion` / `Profile` / `Flags` | The context contract from above. |
| `new GameWindowSettings()` | Not `GameWindowSettings.Default` — that's a shared mutable static. It works fine today, but in 1.8 when you set `UpdateFrequency` you'd be mutating global state. Sidestep it now. |
| `using var` | `GameWindow` is `IDisposable` and owns the GLFW window plus the GL context. Lesson 4.3 is entirely about how GL handles get leaked; start clean. |

`Run()` blocks until the window closes, then returns. Inside it, GLFW pumps OS events and OpenTK dispatches `OnLoad` → `OnUpdateFrame`/`OnRenderFrame` in a loop → `OnUnload`. That loop is lesson 1.2.

## ✅ Checkpoint

- A 1280×720 window titled **Firmament** appears.
- Clicking the ✕ closes it, and the process exits with code 0 — no hang, no exception.
- **Its contents are undefined.** Solid black, flickering garbage, or a smear of whatever was behind it. That is *correct* right now: you have a color buffer nobody has written to, so you're seeing uninitialized GPU memory. Lesson 1.4 (`GL.Clear`) fixes it. Don't chase it.
- Alt-Tab away and back — the contents may go stale or garbage again. Same reason. Still fine.

## 🐛 Common failure modes

1. **`GLFWException: Failed to create window` / "requested version not available"** — most likely cause by far. Your GPU driver can't give a 3.3 Core context. Real culprits: running inside RDP or a VM with only a software GL 1.1 renderer; a laptop routing to Intel integrated graphics with stale drivers; or Windows' fallback rasterizer kicking in. Update your GPU driver first. Confirm with `dotnet run` on the machine's physical display, not a remote session.
2. **`DllNotFoundException: glfw3` (or `libglfw`)** — OpenTK ships the native GLFW binary as a runtime asset. If you see this, restore didn't lay it down. `dotnet clean` then `dotnet build` — check `Firmament.Game/bin/Debug/net10.0/` actually contains `glfw3.dll`.
3. **Window opens then instantly closes** — you called `Run()` on the wrong object, or not at all. If the process exits with code 0 in under a second, `Main` fell off the end.
4. **Window is unresponsive / "not responding" but visible** — `Run()` isn't pumping. This one basically can't happen yet, but it will the first time you block inside `OnUpdateFrame` in a later lesson. Remember the symptom.
5. **Window is 1280×720 but the framebuffer isn't** — high-DPI display. macOS Retina and Windows display scaling can give you a backing buffer larger than the client size. You won't notice until lesson 1.7, when `GL.Viewport` needs the *framebuffer* size, not the client size. Filing this now so it's not a mystery then.

## 🔧 Exercises

1. **Change `ClientSize` to something non-16:9** — 800×800. Confirm the window is square. (In 1.7 you'll discover what ignoring aspect ratio does to your geometry; establish the baseline now.)
2. **Set `APIVersion = new Version(1, 1)` and run.** It'll probably still work — drivers are lenient about *older* than requested. Now try `new Version(9, 9)`. Read the exception. That's the failure mode from #1 above, on demand, so you recognize it in the wild.
3. **Set `Profile = ContextProfile.Compatability`** (yes, OpenTK misspells it) and run. Nothing visibly changes — which is the lesson: compatibility profile silently permits 1990s GL. Put it back to `Core` and leave it there for the rest of the project.
4. **Add `StartVisible = false` plus `WindowState = WindowState.Minimized`,** run, and watch it *not* appear while the process still runs and exits cleanly on its own only if you kill it. Useful intuition for lesson 11.7 (headless/shipping) and for understanding that the window and the loop are separable things.
