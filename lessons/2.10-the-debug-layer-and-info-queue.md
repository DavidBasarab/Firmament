# Lesson 2.10 — The D3D11 Debug Layer and `ID3D11InfoQueue`

> Part 2 — The Pipeline and the First Triangle
> *The D3D11 debug layer and `ID3D11InfoQueue`: turn HRESULTs and silent state errors into something you can read*

**Where you already are:** a spinning quad. `QuadDrawer` owns an immutable index buffer (`[0, 1, 2, 0, 2, 3]`, `R16Uint`), a `Shader`, and a vertex buffer that it **rebuilds every frame**: it rotates four `Vertex` structs on the CPU, disposes the old buffer and calls `CreateBuffer` again with `Usage.Immutable`. `FirmamentWindow.OnLoad` creates the device with `CreateDeviceFlag.None`. Every `Create*` is wrapped in `SilkMarshal.ThrowHResult`. Every bind and draw returns `void`.

That last fact is the reason for this lesson. 2.9's failure-mode list was almost all **silent**: no index buffer bound, the wrong index format, a `BaseVertexLocation` that reads past the end. None of these return anything, because `DrawIndexed` returns `void`. The failures that *do* return something give you `E_INVALIDARG` and no explanation. This lesson turns on the part of D3D11 that explains them.

## Concept: a second, slower D3D11 that checks your work

The D3D11 runtime you've been using is built for speed. When you call `DrawIndexed`, it hands the call to the driver with almost no checking, because a shipped game makes thousands of draw calls a frame and validating every argument would cost real milliseconds. Bad state isn't rejected. It's treated as "undefined behavior", which in practice means a black screen, garbage geometry, or reading zeros from a slot you forgot to bind.

The **debug layer** is a separate DLL (`D3D11_1SDKLayers.dll`) that sits between your code and the runtime when you create the device with `CreateDeviceFlag.Debug`. Every call goes through it first. It checks arguments against the spec, tracks every bound resource, and at each draw call checks the whole pipeline state for consistency: an index buffer is bound, it's large enough for `IndexCount`, the input layout matches the bound vertex shader, and so on. When something is wrong, it writes a message in English that names the method, the argument, and the rule you broke.

It does *not* change behavior. A draw that would have silently drawn nothing still draws nothing. The debug layer only explains. It's also **slow**: the validation can easily double your CPU frame time. That's why it is `#if DEBUG` only, and why you never profile a Debug build (11.1).

**Where the messages go.** By default the layer sends each message to `OutputDebugString`, the Win32 debugger channel. Rider's or Visual Studio's Debug Output window shows it. A console started with `dotnet run` doesn't. That's what **`ID3D11InfoQueue`** is for. The layer also stores every message in an in-memory queue that hangs off the device, and you can read it programmatically. You get the info queue by `QueryInterface` on the device, the same move you made in 1.8 to go from `IDXGIFactory2` to `IDXGIFactory5`. On a non-debug device that `QueryInterface` fails with `E_NOINTERFACE` (`0x80004002`, which I verified on your machine), and that failure is how the reporter below knows to stay quiet in Release.

**Severities**, from worst to mildest:

| Severity | Meaning |
|---|---|
| `Corruption` | Memory is already damaged. Stop. |
| `Error` | You broke an API rule. A `Create*` that returns `E_INVALIDARG` always has an `Error` message explaining it. |
| `Warning` | Legal but almost certainly a bug, like drawing with no index buffer bound. |
| `Info` | Bookkeeping. The layer logs **every object create and destroy** at this level. |
| `Message` | Free-form text. Rare. |

`Info` matters to you specifically. Your `QuadDrawer` creates and destroys a buffer every frame, so unfiltered, the queue gets two `Info` lines per frame, more than a hundred a second, and drowns out everything else. So the reporter installs a **storage filter** that drops `Info` and `Message` before they're stored.

**The key idea: an HRESULT tells you *that* something failed, and the info queue tells you *why*.** `0x80070057` (`E_INVALIDARG`) out of `CreateBuffer` could be any of a dozen bad fields. The `Error` message stored at the same moment names the one it was.

## Steps — what to write and where

### Step 0 — Install the debug layer (once per machine)

The SDK layers ship as an optional Windows feature, not with the OS and not with Silk.NET:

- **Settings → System → Optional features → View features → "Graphics Tools"**, or
- from an **elevated** pwsh: `Add-WindowsCapability -Online -Name Tools.Graphics.DirectX~~~~0.0.1.0`

When it's installed, `C:\Windows\System32\D3D11_1SDKLayers.dll` exists. If you skip this step, `CreateDevice` with the debug flag fails with `DXGI_ERROR_SDK_COMPONENT_MISSING` (`0x887A002D`). Step 2 handles that by printing a warning and continuing without the layer, so a machine without Graphics Tools (a friend's machine, a CI box) still runs a Debug build.

### Step 1 — New file: `Firmament.Core/Diagnostics/InfoQueueReporter.cs`

New folder, new namespace, matching the path. It has one job: drain the queue to the console.

```csharp
using FatCat.Toolkit.Console;
using Silk.NET.Core.Native;
using Silk.NET.Direct3D11;

namespace Firmament.Core.Diagnostics;

public unsafe class InfoQueueReporter(ComPtr<ID3D11Device> device) : IDisposable
{
	private readonly ComPtr<ID3D11InfoQueue> infoQueue = OpenInfoQueue(device);

	public bool IsAvailable
	{
		get { return infoQueue.Handle is not null; }
	}

	public void Dispose()
	{
		infoQueue.Dispose();
	}

	public void ReportMessages()
	{
		if (!IsAvailable)
		{
			return;
		}

		var messageCount = infoQueue.GetNumStoredMessagesAllowedByRetrievalFilter();

		for (ulong index = 0; index < messageCount; index++)
		{
			ReportMessage(index);
		}

		infoQueue.ClearStoredMessages();
	}

	private static ConsoleColor ColorFor(MessageSeverity severity)
	{
		return severity switch
		{
			MessageSeverity.Corruption => ConsoleColor.Magenta,
			MessageSeverity.Error => ConsoleColor.Red,
			MessageSeverity.Warning => ConsoleColor.Yellow,
			MessageSeverity.Info => ConsoleColor.Gray,
			MessageSeverity.Message => ConsoleColor.Gray,
			_ => throw new ArgumentOutOfRangeException(nameof(severity)),
		};
	}

	private static string Describe(Message* message)
	{
		var description = SilkMarshal.PtrToString((nint)message->PDescription);

		return $"D3D11 {LabelFor(message->Severity)} #{(int)message->ID}: {description}";
	}

	private static void IgnoreChatter(ComPtr<ID3D11InfoQueue> infoQueue)
	{
		var ignoredSeverities = stackalloc MessageSeverity[] { MessageSeverity.Info, MessageSeverity.Message };

		var filter = new InfoQueueFilter
		{
			DenyList = new InfoQueueFilterDesc { NumSeverities = 2, PSeverityList = ignoredSeverities },
		};

		SilkMarshal.ThrowHResult(infoQueue.PushStorageFilter(ref filter));
	}

	private static string LabelFor(MessageSeverity severity)
	{
		return severity switch
		{
			MessageSeverity.Corruption => "CORRUPTION",
			MessageSeverity.Error => "ERROR",
			MessageSeverity.Warning => "WARNING",
			MessageSeverity.Info => "INFO",
			MessageSeverity.Message => "MESSAGE",
			_ => throw new ArgumentOutOfRangeException(nameof(severity)),
		};
	}

	private static ComPtr<ID3D11InfoQueue> OpenInfoQueue(ComPtr<ID3D11Device> device)
	{
		if (device.QueryInterface(out ComPtr<ID3D11InfoQueue> infoQueue) < 0)
		{
			return default;
		}

		IgnoreChatter(infoQueue);

		return infoQueue;
	}

	private void ReportMessage(ulong index)
	{
		nuint messageLength = 0;

		SilkMarshal.ThrowHResult(infoQueue.GetMessageA(index, (Message*)null, &messageLength));

		var messageBytes = new byte[messageLength];

		fixed (byte* messagePointer = messageBytes)
		{
			var message = (Message*)messagePointer;

			SilkMarshal.ThrowHResult(infoQueue.GetMessageA(index, message, &messageLength));

			ConsoleLog.Write(ColorFor(message->Severity), Describe(message));
		}
	}
}
```

Three things in here aren't obvious:

**The two-call `GetMessageA`.** A `Message` is a small struct (`Category`, `Severity`, `ID`, `PDescription`, `DescriptionByteLength`) whose `PDescription` points at text of variable length. D3D doesn't allocate that text for you. You allocate **one block** big enough for the struct and the string together, and D3D writes both into it, with `PDescription` pointing *inside your own buffer*, just past the struct. So: call once with a null `Message*` to get the total size, allocate, call again to fill. That's why the buffer stays pinned with `fixed` the whole time you read it. Move it and `PDescription` points at nothing. (On x64 a `byte[]`'s data is 8-byte aligned, which is what the struct's pointer field needs.)

**`LabelFor` instead of `severity.ToString()`.** Silk.NET's enums define every value twice, as `Error` and as `MessageSeverityError`, and `ToString()` on a duplicated value is free to return either. I checked: you get `MessageSeverityError` but `Execution`. Hence the explicit label switch. The `#` number is the stable `MessageID` (for example 357), which is what you'd filter on.

**The `readonly ComPtr` field and the `QueryInterface` refcount.** `QueryInterface` **does** `AddRef`, unlike copying a `ComPtr` (2.7). The info queue is the *same COM object* as the device seen through another interface, so while this reporter holds its reference, the device can't be destroyed. That's why Step 2 disposes the reporter *before* the device. The `ComPtr<ID3D11Device>` passed into the constructor and the `infoQueue` passed into `IgnoreChatter` are plain struct copies: no `AddRef`, so nothing to release.

	if (result == SdkComponentMissing)

	return d3D11.CreateDevice(
		default(ComPtr<IDXGIAdapter>),

		0,

		null,
		0,

		null,

The reporter is created immediately after the device, so anything that goes wrong from the next line on gets captured.

Drain once per frame, **after** `Present`, so a draw from this frame and any complaint from `Present` itself show up the same frame:

```diff

+
+		infoQueueReporter.ReportMessages();
 	}
```

When the queue is empty this costs one COM call per frame (`GetNumStoredMessagesAllowedByRetrievalFilter`). In Release it's a null check. Nothing is logged when nothing is wrong, so this isn't the per-frame logging the repo rules ban.

And in `Dispose`:

```diff
 	public void Dispose()
 	{
+		infoQueueReporter?.ReportMessages();
 		CleanUp?.Invoke();
+		infoQueueReporter?.Dispose();
 		renderTargetView.Dispose();
 		swapChain.Dispose();
 		deviceContext.Dispose();
 		device.Dispose();
-		input.Dispose();
+		input?.Dispose();
 		SilkWindow.Dispose();
 	}
```

The order matters:

1. **Report first.** If you got here because a `Create*` threw, the explanation is in the queue right now. Print it before anything else in `Dispose` can fail.
2. **`CleanUp`** releases the game's objects (the quad's buffers and shader) while the device is still alive.
3. **Release the reporter before the device.** That's the `QueryInterface` reference from Step 1.

The `?.`s are there because `Dispose` can now run after `OnLoad` died partway through, when the reporter or input context may not exist yet. These are the only places that can happen. `ComPtr` fields left at `default` are safe to dispose (I checked: `Dispose()` on a null `ComPtr` is a no-op), so they don't need it.

### Step 3 — `LearningGame.Run`: actually dispose the window

```diff
-		Window.Run();
+		try
+		{
+			Window.Run();
+		}
+		finally
+		{
+			Window.Dispose();
+		}
```

`finally`, not `using`, because the window is a property that `Run` assigns, and the call site reads plainly this way. On a normal close, `Run` returns and the `finally` disposes everything, for the first time in this project's life. On a crash, the exception passes through the `finally`, `Dispose` prints the info queue, and then the exception carries on.

**One thing to know about that crash path:** I verified that .NET 10 runs `finally` blocks for an unhandled exception, but only *after* it has printed `Unhandled exception…` and the stack trace. So the D3D11 explanation appears **below** the stack trace. Scroll down.

### Step 4 — `QuadDrawer.Dispose`: survive a half-finished `Load`

```diff
 		vertexBuffer.Dispose();
 		indexBuffer.Dispose();
-		shader.Dispose();
+		shader?.Dispose();
```

`Load` builds the index buffer *before* it creates the `Shader`. If `CreateIndexBuffer` throws, which is exactly what Exercise 3 makes it do, `shader` is still null when `Dispose` runs. Without the `?.`, that `NullReferenceException` would replace the exception you actually wanted to see.

### Deliberately not in this lesson

- **`ID3D11Debug::ReportLiveDeviceObjects`.** That's the leak detector: "here's every COM object still alive, with its refcount". It needs the lifetime story to be correct first, and that's 4.3.
- **The DXGI debug layer** (`CreateDXGIFactory2` with `DXGI_CREATE_FACTORY_DEBUG`, and `IDXGIInfoQueue`). It's a separate queue for swap-chain and factory errors. Your swap chain has been stable since 1.8, so 4.3 picks it up alongside live-object reporting.
- **Naming objects** with `SetPrivateData(WKPDID_D3DDebugObjectName, …)` so messages say `"QuadIndexBuffer"` instead of `Addr=0x…`. It pays off with RenderDoc and PIX in 11.3.
- **A callback instead of polling.** D3D11's info queue has no callback (D3D12's `ID3D12InfoQueue1` does), so polling is the only option here, not a shortcut.

## Per-value justification

| Value / call | Why |
|---|---|
| `CreateDeviceFlag.Debug` (= `0x2`) | Loads `D3D11_1SDKLayers.dll` between you and the runtime. Debug builds only, because validation costs real CPU time. |
| `0x887A002D` | `DXGI_ERROR_SDK_COMPONENT_MISSING`: the debug flag was requested but the SDK layers aren't installed. The one `CreateDevice` failure we handle instead of throwing. `unchecked((int)…)` because HRESULTs are signed and this one has the high bit set. |
| `QueryInterface` → `ID3D11InfoQueue` | The queue is another interface on the device object. Returns `E_NOINTERFACE` (`0x80004002`) on a non-debug device, which is how Release silently gets no reporter. |
| `PushStorageFilter` with `DenyList` | A *storage* filter drops messages before they're stored. A *retrieval* filter would only hide them, while they still filled the queue. |
| `NumSeverities = 2` | The length of `ignoredSeverities`: `Info` and `Message`. `Info` is mostly object create/destroy logging, which your per-frame `CreateBuffer` turns into 120+ lines a second. |
| `stackalloc` | The filter needs a pointer that's valid only for the `PushStorageFilter` call, which copies it, so stack memory is enough. As a direct local initializer in an `unsafe` context, `var` infers `MessageSeverity*` (verified), not `Span<T>`. |
| `GetNumStoredMessagesAllowedByRetrievalFilter` | `GetMessageA`'s index runs over *this* count, not `GetNumStoredMessages`. The two only differ when a retrieval filter is pushed, but this is the correct pair. |
| `GetMessageA(index, null, &length)` | The first call reports the size of struct + string. The second fills your buffer. `PDescription` points into that buffer. |
| `ClearStoredMessages()` | Without it, the next frame would report the same messages again. The queue also has a default cap (`GetMessageCountLimit`) and discards the oldest beyond it. |
| `ReportMessages()` after `Present` | Covers everything issued this frame, including `Present`'s own validation. |
| Reporter disposed before `device` | `QueryInterface` added a reference to the device object. |

## 🐛 Common failure modes

1. **The dark-yellow "not installed" warning even though you installed Graphics Tools.** The optional feature finished but `D3D11_1SDKLayers.dll` isn't in `System32` yet. It usually needs a reboot, and sometimes the install silently failed because it didn't have admin rights. Check for the DLL.
2. **Nothing ever prints, even with `BindIndexBuffer()` removed.** You're running Release (no flag requested), or `infoQueueReporter.ReportMessages()` isn't in `OnRender`, or it's *above* `Render?.Invoke(delta)`. In that last case the messages print one frame late and you'd still see them, so check the first two first. Quick test: `Console.WriteLine(infoQueueReporter.IsAvailable)` once in `OnLoad`, then delete it.
3. **The console floods with gray lines.** The storage filter isn't installed, or `NumSeverities` is 0, and you're seeing your per-frame buffer creates. Check `IgnoreChatter` is called and its `HRESULT` is checked.
4. **`NullReferenceException` from `Dispose` hides the real exception.** Something in the teardown path dereferences an object `OnLoad` never got to create. The usual suspect is a missing `?.` on `shader`, `input`, or `infoQueueReporter`.
5. **Garbage or a crash inside `ReportMessage`.** You read `message->PDescription` after leaving the `fixed` block, or you allocated `sizeof(Message)` instead of `messageLength`. The string lives in your buffer, so the buffer must be big enough and still pinned.
6. **The frame rate dropped noticeably in Debug.** That's expected: the debug layer validates every call. Compare Release before concluding anything (11.1).

## 🔧 Exercises

1. **Make 2.9's silent failures talk.** One at a time, and revert each: (a) bind the index buffer as `Format.FormatR32Uint`. The *format mismatch itself* isn't detectable, since a `ushort` buffer is just bytes, but six 4-byte indices need 24 bytes and your buffer has 12, so you get `#359` `DEVICE_DRAW_INDEX_BUFFER_TOO_SMALL`. (b) Change `DrawIndexed(6, 0, 0)` to `DrawIndexed(9, 0, 0)`: the same warning, reached a different way. Write down which of 2.9's seven failure modes the layer catches and which it can't. The ones it can't (wrong winding, scrambled colors) are *legal*, which is a useful distinction to have in your head.
2. **Watch your per-frame buffer churn.** Temporarily change `NumSeverities` to `1` so only `Message` is denied. Now every frame prints `#2097228` (`CREATE_BUFFER`) and `#2097230` (`DESTROY_BUFFER`), gray, at full frame rate. That's the debug layer describing your rotation approach. Count lines per second against your FPS. Then put the filter back, and remember this when 5.1 introduces `Map`/`Unmap`.
3. **Read an `E_INVALIDARG`.** In `CreateIndexBuffer`, add `CPUAccessFlags = (uint)CpuAccessFlag.Write` to the `BufferDesc`. `Usage.Immutable` forbids CPU access, so `CreateBuffer` fails, `ThrowHResult` throws, and the app dies at load. Scroll **past** the stack trace (Step 3 explains why it's below): a red `D3D11 ERROR #63` (`CREATEBUFFER_INVALIDCPUACCESSFLAGS`) names the exact field. Before this lesson, all you had was `0x80070057`. This exercise also tests Steps 3 and 4: if you see a `NullReferenceException` instead, one of them is wrong.
4. **Break into the debugger on errors.** Add `SilkMarshal.ThrowHResult(infoQueue.SetBreakOnSeverity(MessageSeverity.Error, true));` to `OpenInfoQueue`, guarded by `System.Diagnostics.Debugger.IsAttached`, and repeat Exercise 3 under the debugger. The layer issues a native breakpoint *inside* `CreateBuffer`, before it returns, so the call stack shows the exact managed call that broke the rule. **Caveat:** that breakpoint is a native `int 3`. In a managed-only debug session (Rider's and Visual Studio's default for .NET) it can surface as an unhandled `0x80000003` and end the process instead of stopping on it. Turn on native/mixed-mode debugging first. This is why it's an exercise and not in the main code. Never set it without the `IsAttached` guard: with no debugger attached, a breakpoint exception just kills the process.

## 📎 What this unlocks

2.11's constant buffers come with a byte-alignment rule (`ByteWidth` must be a multiple of 16) that fails as `E_INVALIDARG` at create time, and that you'll almost certainly break at least once. With the debug layer on, that's a red line naming the field instead of a hex code.
