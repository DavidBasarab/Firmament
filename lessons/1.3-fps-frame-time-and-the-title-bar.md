# Lesson 1.3 — FPS, Frame Time, and the Title Bar

> Part 1 — A Window and a Heartbeat
> *FPS: frame counter, rolling average, frame-time in ms (ms is the honest number, FPS is the vanity number) — display in the title bar*

**Where you already are:** you didn't stop where 1.2 stopped. Your committed `FirmamentWindow` already accumulates `runTime`, computes an `updateDelta` and a running `updateAverage` (as `TimeSpan`s off `DateTime.Now`), and prints a per-second line to the console. That's most of the *machinery* of this lesson invented early — good instinct. This lesson keeps the idea and fixes three things: it measures time from the loop's own delta instead of `DateTime.Now`, it reports **frame time in milliseconds** as the primary number, and it moves the readout off the scrolling console and into the **title bar**, which is where it lives until there's a real on-screen overlay (that's 4.8, and text-on-screen is 5.8).

## Concept: one frame's time is noise; the honest unit is milliseconds

Two ideas, and they're independent.

**A rolling average, because a single frame is a lie.** Frame times jitter violently — one frame is 0.2 ms, the next is 8 ms because the garbage collector ran or the OS scheduled something else on your core. If you print the *instantaneous* frame time, the title bar is an unreadable strobe. So you average over a window. We use a one-second window: count the frames and sum their time over one real second, then report. That's a rolling average — it trades responsiveness (you see a change a second late) for a number a human can actually read. Averaging also lets you carry the **peak** frame time in the window alongside the average, and the peak is where the truth hides: the average can say a comfortable 2 ms while a 30 ms hitch every second is what the player actually feels.

**Milliseconds are honest; FPS is vanity.** FPS is just `1 / frametime`, and the reciprocal makes it nonlinear and non-additive. A "10 FPS drop" is 0.01 ms when you fall 1000→990, but 3.3 ms when you fall 60→50 — same headline, two orders of magnitude apart. You cannot add FPS ("the shadow pass cost me… 12 FPS?"), but you *can* add milliseconds: the clear costs 0.1 ms, the batch costs 2 ms, and they sum into your frame budget. And the budget is a fixed millisecond number — **16.67 ms at 60 Hz, 6.94 ms at 144 Hz.** Every optimization decision for the rest of this project is "did that cost or save milliseconds," never "did that add FPS." So we compute FPS because everyone expects to see it, but we lead with `ms avg` and `ms peak`.

**Why the title bar.** The 1.2 console line was a scaffold — it scrolls, so you read a *history* when what you want is one always-current value in place. The title bar gives you exactly one line that overwrites itself. The one rule: update it at a human rate (~1 Hz), **not every frame**. Setting `Title` is an OS call into GLFW; doing it thousands of times a second is pure waste and buys you nothing a human can read.

## Step 1 — rewrite `FirmamentWindow` around render-frame timing

Replace the body of **`Firmament.Core/FirmamentWindow.cs`**. This drops the `DateTime.Now` / `TimeSpan` fields and the `Console.WriteLine` from 1.2 (that scaffold was always meant to be deleted here) and drives the report from `OnRenderFrame`, because "frames per second" means *render* frames — what the display actually shows:

```csharp
using OpenTK.Windowing.Common;
using OpenTK.Windowing.Desktop;

namespace Firmament.Core;

public class FirmamentWindow(GameWindowSettings gameWindowSettings, NativeWindowSettings nativeWindowSettings)
	: GameWindow(gameWindowSettings, nativeWindowSettings)
{
	private const double ReportIntervalSeconds = 1.0;

	private double secondsSinceLastReport;
	private int updatesSinceLastReport;
	private int rendersSinceLastReport;
	private double peakRenderSeconds;

	protected override void OnUpdateFrame(FrameEventArgs args)
	{
		base.OnUpdateFrame(args);

		updatesSinceLastReport++;
	}

	protected override void OnRenderFrame(FrameEventArgs args)
	{
		base.OnRenderFrame(args);

		secondsSinceLastReport += args.Time;
		rendersSinceLastReport++;

		if (args.Time > peakRenderSeconds)
		{
			peakRenderSeconds = args.Time;
		}

		if (secondsSinceLastReport < ReportIntervalSeconds)
		{
			return;
		}

		ReportPerformance();
		ResetWindow();
	}

	private void ReportPerformance()
	{
		var framesPerSecond = rendersSinceLastReport / secondsSinceLastReport;
		var averageMilliseconds = secondsSinceLastReport / rendersSinceLastReport * 1000.0;
		var peakMilliseconds = peakRenderSeconds * 1000.0;

		Title =
			$"Firmament — {framesPerSecond:F0} FPS  |  {averageMilliseconds:F2} ms avg  {peakMilliseconds:F2} ms peak  |  {updatesSinceLastReport} updates/s";
	}

	private void ResetWindow()
	{
		secondsSinceLastReport = 0.0;
		updatesSinceLastReport = 0;
		rendersSinceLastReport = 0;
		peakRenderSeconds = 0.0;
	}
}
```

Every non-obvious choice, justified:

| Piece | Why |
|---|---|
| Timing from `args.Time`, not `DateTime.Now` | `args.Time` **is** the loop's own measured seconds between frames — the thing you actually want to know. `DateTime.Now` is the wrong tool for frame timing on three counts: coarse resolution (system clock ticks ~1–16 ms on Windows, so sub-millisecond frames read as 0), it does timezone/calendar work on every call, and it can jump when the wall clock is adjusted. If you ever need a manual timer instead of the callback's delta, reach for `System.Diagnostics.Stopwatch` (monotonic, high-resolution), never `DateTime.Now`. |
| Report driven from `OnRenderFrame` | FPS is a property of the frames the monitor shows — render frames. Counting updates separately (and printing `updates/s`) keeps the two-clocks lesson from 1.2 visible: right now they lockstep, but the metric is honest the day 4.2 splits them. |
| `averageMilliseconds = seconds / renders * 1000` | The average frame time over the window is just total window time ÷ frames. It's the exact reciprocal of FPS — leading with it is the whole point of the lesson. `* 1000` converts seconds → ms. |
| `peakRenderSeconds` (max, not sum) | The worst single frame in the window. This is the number that exposes hitches the average smooths away — your 1.2 exercise-1 instinct, made permanent. |
| `ReportIntervalSeconds = 1.0` | Human-readable cadence. Report faster and the numbers blur; slower and you miss transient spikes. One second is the convention. Named constant so it isn't a mystery `1.0`. |
| Setting `Title` only inside the `>= 1.0` branch | `Title` is a GLFW/OS call. At uncapped thousands of FPS, setting it every frame is thousands of pointless syscalls a second. Gate it to ~1 Hz. |
| `{framesPerSecond:F0}`, `{...:F2}` | FPS as a whole number (the fractional part is noise); milliseconds to two decimals because at high frame rates the honest value is a fraction of a millisecond and `F0` would just print `0`. |

`Program.cs` needs **no changes** — it still constructs the window and calls `Run()`. And note `Title` starts as `"Firmament"` (set in `NativeWindowSettings` back in 1.1); we're now overwriting it once a second.

## ✅ Checkpoint

- The window's **title bar** updates once per second. It reads something like:
  `Firmament — 5231 FPS  |  0.19 ms avg  3.44 ms peak  |  5231 updates/s`
- The exact numbers depend entirely on your CPU. Uncapped, expect thousands of FPS and a sub-millisecond average — that's correct and still a little obscene (1.8/VSync is the lid).
- `ms avg` ≈ `1000 / FPS`. Sanity-check it: 5231 FPS → 1000/5231 ≈ 0.19 ms. If those two don't agree, your math is off.
- `ms peak` is always **≥** `ms avg`, usually several times larger — that gap is the jitter the average hides.
- The **console is now silent** (the 1.2 heartbeat is gone). All the signal is in the title bar.
- Window contents are still undefined garbage — correct until 1.4 (`GL.Clear`). Don't chase it.

## 🐛 Common failure modes

1. **Title bar never changes / still says plain `Firmament`.** Your report branch isn't firing. Either you left the report logic in `OnUpdateFrame` but never accumulate `secondsSinceLastReport` there, or you reset the accumulator without ever crossing `1.0`. Accumulate `args.Time` and gate on it in the *same* callback.
2. **`ms avg` prints `0.00`.** You're timing with `DateTime.Now` (or `DateTime.UtcNow`) instead of `args.Time`. Its resolution is coarser than a sub-millisecond frame, so every frame rounds to zero. Use `args.Time`.
3. **FPS and `ms avg` disagree** (e.g. `5000 FPS` but `2.00 ms avg`). You're averaging the wrong window — usually dividing by `updatesSinceLastReport` while counting renders, or resetting one counter and not the other. Reset all four fields together in `ResetWindow`, only in the report branch.
4. **The whole app is visibly slower / stutters after this change.** You're setting `Title` every frame instead of once per second — the `if (secondsSinceLastReport < ReportIntervalSeconds) return;` guard is missing or below the assignment. Thousands of OS title calls a second will actually cost you.
5. **`ms peak` equals `ms avg` exactly.** You reset `peakRenderSeconds` every frame, or compare against the wrong field. It must persist across the whole window and reset only in `ResetWindow`.

## 🔧 Exercises

1. **Show the frame budget headroom.** 60 Hz is a 16.67 ms budget. Append ` {averageMilliseconds / 16.67 * 100:F0}% of 60Hz` to the title and watch how little of the budget you're using uncapped. (You're building the intuition 1.8 and every perf lesson leans on.)
2. **Cap the render rate and read real numbers.** In `Program.cs`, set `window.RenderFrequency = 60;` before `Run()`. Now FPS settles near 60 and `ms avg` near 16.67 — the honest identity, live. Try `144` if your setup allows, then put it back to `0` (uncapped).
3. **Inject a hitch and catch it with `peak`.** Every ~60th render frame, do `System.Threading.Thread.Sleep(10);`. Your `ms avg` barely moves but `ms peak` jumps to ~10 ms — proof that the average lies and the peak tells the truth. Remove it after.
4. **Add a rolling *worst-second* readout.** Keep a field for the largest `peakMilliseconds` you've ever seen across all windows, and show it as ` (worst {allTimePeak:F2} ms)`. Now a single hitch leaves a mark you can't miss — the seed of a real profiler (11.1).
